## 日期/时间组件小程序端不弹选择器（用户真机反馈）✅ 已修
- **根因**：`SuperFormRender.vue` 的日期/时间用 `<input type="date"/"time">` —— 这是 **H5 专属属性**，
  **小程序端 input 不支持、不弹选择器**。H5 原生 input 支持所以 H5 一直正常 → **只在 H5 验证会漏掉小程序端**。
- **修**：全部改 uni `<picker>`（复用 select 组件既有范式，两端一致、无需条件编译）：
  时间点→`mode="time"`；时间段→双 picker+`~`；单个日期→`mode="date"`；日期范围→双 picker+`~`；
  支付「参与日期」同样改 picker（共 7 处）。新增 `onDateTimePick(id, ev, part)`：
  part 空=单值写 `values[id]`，part=start/end 复用 `setRangePart` 写 '起~止'。值格式/校验正则不变。
- 面板只提供 time/timerange/date/range（**无 datetime**）→ `timeType()` 的 datetime 分支本就不可达，删死函数。
- **验证**：SFC 编译 OK；72 测试通过；H5 实测渲染为 `uni-picker`（请选择日期/请选择时间）；
  小程序重建后产物 4×mode=date + 3×mode=time、0 残留 type=date/time、2.4M。
- 🔴 **教训（跨端必查）**：`input type=date|time|datetime-local` 是 H5-only；小程序端任何"选择器"都要
  `<picker mode=date|time|selector>`。**C 端组件改动必须在 H5 与小程序两端都验**（此前只验 H5 是漏检根因）。
- ⚠️ gen-mp-sicons 耗时 ~4min（渲染 482 PNG 后清理）。若 `src/utils/sicons-base64.js` 已完整且 SIcon.svgMap
  未变，**可跳过该步**（uni build 会直接打包已有 base64），大幅加快重建。

## 八轮：宫格图标"变得很难看" —— 根因是产物分辨率，不是图标路径

**用户反馈**：「首页 9 宫格的内置图标和之前设计规范都不一样，变得很难看」+ 附当前截图。

**排查中的一次重要纠偏**：我最初怀疑是 `b91ef52`「名片宫格图标定稿」把 9 个图标路径改得过于密集
（apps 从 200→471 字符、dynamic 116→294），正准备回退。用户随后贴出「这个是之前的」旧截图，
裁同一个「我的名片」图标做像素级放大对比后结论被推翻：

> **两张图的图标形状完全相同，差别只在清晰度。** 左（当前）模糊发虚、描边有毛刺；右（之前）锐利干净。

→ 假设"路径退化"被证伪。**已撤销那次回退**（`git checkout SIcon.vue`），改走分辨率路线。

**真正的根因**：`scripts/gen-mp-sicons.js` 固定渲染 24×24 PNG，而名片宫格 `iconSize` 默认 **40px**
（`gridIconSize` 读 `props.iconSize || 40`）—— 24px 图拉伸 1.67 倍显示，密集细节糊成一团。
两张截图分辨率不同（716×614 vs 942×404，来自不同时机/设备）也印证是渲染质量问题。

**修复：分级渲染**（避免全量提到 72px 导致主包爆掉）
- PNG 面积随边长**平方**增长，24→72 是 **9 倍像素** → 全量 base64 会从 175KB 涨到~1.5MB，主包必爆。
- 策略：`GRID_ICONS`（宫格/应用中心经iconSize 数值驱动的 29 个图标）出 **72px**；
  其余 31 个保持 **24px**（≤32px 显示场景够用）。
- 判定依据两处：① 静态 `<SIcon size="...">` 中 `SIZE_PRESETS{small:18,default:20,large:24,xlarge:32}`
  且 `px >= 32`；② 宫格类组件运行期由 props 决定大小，只能靠白名单 `GRID_ICONS` 覆盖。
- 实测：高清 29 个 / 常规 31 个，base64174.6→ **259.7KB（+85.1KB）**，481 条签名全部合法。

**🔴 主包体积统计口径（第二次踩坑，务必记牢）**：
- 首次统计得 1824KB「超标 288KB」，与历史记录的 1355KB 差 469KB，远超本次 +85KB → 判定脚本有误。
- 错因：按 `static/` + `pages/` + `components/` 分组统计时，**`static/sicons` 目录被重复计入**
  （PNG 已被 gen 脚本清理、运行时只用 base64，但目录仍参与遍历）。
- 正确口径：**只按"排除 4 个分包前缀"这一个条件统计全部文件**，不做目录分组**。两种算法实测对比：
  错误算法 1824KB / 正确算法 **1441KB**。
- 正确结果：主包 **1441KB = 1.41MB < 1.5MB ✓ 通过**（余量 95KB），分包 407KB。
  与历史 1355KB 对得上：1355 + 85 = 1440，实测 1441（误差 1KB）。
- 结论：`du -sh` 因块对齐虚高不可用；统计脚本**只能算一次总量**，不要按目录分组二次加工。

**设计规范文档现状（重要事实）**：

  明确不含名片宫格：三层蜜桃橙、**填充为主非描边**、透明底、**❌ 绿/紫/蓝分类方块底**。
  按该条判定，现状宫格（渐变方块底 + 白描边）恰好是"违规"的，但适用范围不含宫格。
- 其余文档（`小程序 UI 借鉴方案`、`人脉集市+我的名片 前端独立开发文档.md`、
  `设计中心模块-完整详细开发方案`）关于图标仅一句「复用 SIcon，保持风格统一」，无具体参数。
