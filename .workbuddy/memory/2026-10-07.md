## 按钮「没有居中」——作废上一轮的负 margin 方案（用户第二次反馈）
上一轮 `28e7095` 的解耦实现**本身是错的**：用 `marginLeft:-LR` + `width:calc(100% + 2*LR)` 让按钮溢出抵消容器边距。
🔴 **该方案只在容器无 padding 时成立**；本项目容器有 `MIN_BG_PADDING=8` → 按钮**盖住容器底色并溢出容器**，视觉上比满行更宽且偏左；且 `pct<100` 时宽度被收窄却仍带负 margin → 双偏。
正确解法：**百分比宽度 + `margin:0 auto`**。百分比参照容器内容宽，容器 marginLR 左右对称 → 容器中心==页面中心 → auto 边距即居中；按钮大小只由 `widthPercent` 决定，与容器边距无关。
- 整行：`width:pct%` + `margin:0 auto`
- 自适应：`display:block` + `width:fit-content` + `margin:0 auto`
  🔴 两个实测坑：① `inline-block` 的 `margin:auto` **不居中**（两侧 auto 被当 0）—— 这正是用户看到的现象；② 改 `block` 后 `width:auto` 又**撑满**容器 → 唯一正解是配`fit-content`。

🔧 **本轮最大教训：单测全绿 ≠ 视觉正确。** 我第一版改动 9 例单测全过、真机却偏左。
CSS 几何问题必须**像素实测**：写独立 HTML 复刻真实结构（容器 padding/背景色/有无 `text-align` 全还原），无头 Chrome 截图肉眼看 or `getBoundingClientRect()` 打印。
⚠️ 无头 Chrome `--dump-dom` 读 `<pre>` 多次拿到空内容（脚本时序早于虚拟时间耗尽）→ **优先 `--screenshot`**。
实测五场景：A(LR=0,100%) 与 B(LR=20,100%) 净宽相等 → 解耦成立；C(50%)/D(LR=40,50%) 居中；E(自适应) 内容宽且居中。
单测新增 3 条回归锁：不得出现 `calc`/负 margin、auto 必须 `fit-content`、不得 `inline-block`。web-app 257 例通过；三端构建通过；MP 主包 1450KB。提交 `706ca7e`。

## 按钮整行模式不居中 —— 第三次修法（漏了 `display:block`）

|写法 | 中心偏移 |
|---|---|
| inline-block + 50%（修复前） | **-179px**（贴左边）|
| block + 50%（修复后） | -8px（8 = 容器 padding，非偏移）|
| block / inline-block + 100% | 两者都是 -8px（100% 看不出差别）|

1. 🔴 **「同一函数内两分支写法不一致」= 高危信号**。修 A 分支时顺手看了 B 分支一眼，

2. 🔴 **组件自带 CSS 类里的 `display` 会吃掉内联的 `margin:auto`**。

**原生组件（`native-*`）不走共享 `containerStyle.js`**（那份输出 marginLeft/marginRight），

| 组件 | marginLR |
|---|---|
| native-search / radar / market | 7 |
| native-mycard | 6 |
| **native-grid** | **0** ← 唯一贴边的 |

1. `nativeMargin()` 补 `marginLeft/marginRight`（**用 `??` 而非 `||`**，0 是合法值=故意通栏）。

2. `componentRegistry.js` 宫格 schema **补`marginLR` 字段**（原来面板也调不出来）+ defaultProps 默认 12。
3. 存量迁移 `scripts/migrate-native-grid-marginlr.mjs`（预演/`--apply`、幂等、定向只动等于旧默认 0 的），

1. 🔴 **原生/特例组件不走共享样式函数时，边距必须逐个显式下发**——
   判据：「这个组件的容器边距是谁输出的？」答不上来就是漏。
2. 🔴 **「一端有、一端没有」先查存量数据里哪个值是异类**（本例 grid=0 而其他都 6~7），
   比读代码快 10 倍。别一上来就复刻 DOM。
3. 🔴 **admin 画布的容器内缩会掩盖数据缺失** → 画布「看起来对」不等于 C 端对。
   跨端问题**必须看真机/开发者工具截图**，不能只看设计器。
4. ⚠️ **SQLite 里 `datetime("now")` 双引号会被当标识符**（`no such column: "now"`）→必须单引号。
5. ⚠️ `tenant_page_version` **没有 `page_id` 列**（只有 tenant_id/page_type/version/design_json/created_at），
   写版本快照要按 tenant_id+page_type 取 MAX(version)。
6. ⚠️ **`.mjs` 迁移脚本里 `import { DatabaseSync } from '.../xxx.db'` 会报 ERR_UNKNOWN_FILE_EXTENSION**
   —— 必须 `from 'node:sqlite'`。另ESM 顶层 `await` 之外别混 CJS require。

## 小程序端原生组件样式与后台不一致（圆角缺失 + 内缩多一层）

**用户反馈**（两图对比）：「四个角没有圆角，搜索框也是没有按后台设计的显示。」

**问题 1 · 宫格四角是硬直角**
- `.grid-section { background:#fff; padding:32rpx 16rpx }` —— **完全没写 `border-radius`**；
  而 admin 的 `.r-native-grid{...border-radius:8px}` 硬编码有→ 设计器有圆角、真机没有。
- 修：`.grid-section` 补 `border-radius:16rpx`（= 8px，与 `.section` 同量级）。

**问题 2 · 搜索框比后台多缩一层**
- `.top-bar { padding: 24rpx }` 写死横向内边距，**与 `nativeMargin()` 内联的 marginLeft/Right 叠加**
  → 搜索框左右共缩 12px+marginLR，而后端 `.pe-comp{padding:0}` **没有**任何内缩。
- 修：`.top-bar` 改 `padding: 24rpx 0`（横向交给 marginLR）。

**问题 3 · `.section` 硬编码 margin 抢属性**
- `.section { margin: 0 24rpx 16rpx }` 与内联 `marginLeft/Right` 抢同一属性，
  且 `marginBottom` 锁死在 16rpx → 运营在后台调「上下边距」时**只有一半生效**。
- 修：CSS 改 `margin: 0`，全部交给 `nativeMargin()`；为不丢卡间白缝，
  `nativeMargin` 里 `marginBottom` 给 `?? 8`（= 原 16rpx）兜底。

**元规则（重要）**：
1. 🔴 **「两端不一致」先对 CSS 里的写死值**：`padding:24rpx` / `margin:0 24rpx` / `border-radius` 这类
   硬编码是跨端不一致的头号来源。判据：**把两端同名 class 的 CSS 并排比一遍**。
2. 🔴 **CSS 写死 margin/padding 与「面板可调参数」冲突时，CSS 赢不了就等于参数被架空**。
   参数若允许 0，CSS 就**不要写死**；兜底值放JS（schema 默认值）。
3. 🔴 **原生组件（`native-*`）的 CSS 与 admin 的 `.r-*` 是两套独立实现**，
   改样式必须两端同时看；只看 admin 会漏掉真机侧的缺失（本轮圆角就是这样漏的）。
4. 🔧 **admin 画布 `.pe-comp{padding:0}` 没有任何内缩** —— 这是「对齐基准」。
   C 端凡有 `padding:24rpx` 之类写死，都是额外多缩的。

## 装修画布：操作条定位推翻重做（顶部空白带是自找的）

**用户反馈三连**（一次把三件事说清）：
1「容器左右边距为 0，页面上还是有间距」
2「搜索框也是没有圆角，没有上下间距」
3「蓝色边条，不会自动识别是最顶端的组件，还是出现向上移的箭头，而且从装修预览上看，
   被蓝色边条占了位置，上部会有间隔，**会误导用户**，这个要优化修复」

**🔴 病根：上一轮那个「修复」本身就是错的。**
为解决「首组件操作条被裁」给 `.pe-canvas` 加了 `padding-top:22px`——
虽然确实让操作条不被裁（overflow 裁 padding box），但**代价是画布顶部凭空多一条空白带**：
- 被误读成「容器上下边距没生效」（反馈 1、2）；
- **真机根本没这段留白** → 预览位置与线上不符（反馈 3 明确说「会误导用户」）。

**✅ 正解：操作条改贴组件上沿内侧 `top:0`**（原`top:-22px`）。
从根上不需要任何留白 → 零溢出、零占位、零裁剪，首尾组件一致。
像素实测对比：`top:0` 两个组件均完整可见；`bottom:100%` 首组件仍被裁。

**三种绕法的失败结论（勿复活）**：
| 做法 | 结果 |
|---|---|
| ① `.pe-canvas{padding-top:22px}` | 能不裁，但顶部空白带 → **误导用户，已否决** |
| ② 首组件 `padding-top:22px` | **无效**：padding 只推内容不推边框盒，工具条定位基准是边框盒 → 照样被裁（实测工具条顶 44 < 画布顶 65）|
| ③ 首组件 `margin-top:22px` | 有效，但首组件位置与真机不符 |
| ④ 首组件操作条翻到 `bottom` | 破坏「操作条贴着选中组件」直觉，**用户否决** |
| ✅ ⑤ `top:0` 内侧 | **采用**：零占位零裁剪，首尾一致 |

**元规则**：
1. 🔴 **「修裁剪」的方案要先问「它会不会在别处留下痕迹」**。
   overflow 裁 padding box 确实能解决裁剪，但**把留白搬到容器 padding 上 = 制造假间距**。
   **预览工具类UI 的任何留白都会让运营误读数据**（边距/间距/底色），宁可让浮层贴内侧。
2. 🔴 **padding 推不动边框盒** —— 任何靠「给元素加 padding 让绝对定位子元素不溢出」的思路都是错的，
   定位基准是**边框盒**（`top` 从边框上沿算），只有 margin 能移动边框盒。
3. 🔴 **预览工具的像素必须与真机一致**。真机没有的东西（额外留白、装饰）一律不要在预览里加；
   运营是靠预览判断线上效果的，不一致=误导（用户原话「会误导用户」）。
4. ⚠️ 用户一次给多个现象时，**要找出它们的共同根因**（本轮三条反馈其实都是那条padding-top），
   而不是逐条单独修—— 逐条修会把同一处改动拆成三次提交、三次验证。

## 原生组件容器底色「参数被架空」（搜索栏，button 老问题重演）

**用户反馈**：「这个名片搜索框组件的参数是有问题的，跟之前的『按钮』有同样的问题，
背景设置，也是设置按钮本身，对于容器的背景设置是没有地方设置的。」

**🔴 病根：面板控件存在，但渲染层根本不消费它。**
通用项里有「组件背景色 `compBgColor`」，key 与组件自身的 `bgColor` 不同 → **不会被 ownKeys 去重**，
面板正常显示该控件。但两端 `nativeMargin()` **只输出边距，从不读 `compBgColor`** →
运营拖了色块、预览纹丝不动 → **参数被架空**。
⚠️ 这与 button 当年「一个『背景色』两层含义」是同一类病的**另一种形态**：
那次是**两个字段撞成一个**（去重后只剩一个），这次是**字段不撞但没人消费**。
**共同判据：控件能否设置 ≠ 生效。去渲染层 grep 这个 key 有没有被读。**

**🔴 更大的坑：两端 `nativeMargin()` 同源手写、互不共享**，已因此「只修一端」两次：
- admin `ComponentRender.vue: nativeMargin()` —— 本轮发现它 marginLR/compBgColor 全都没读
- C 端 `pages/cardMain/home.vue: nativeMargin()` —— 上一轮只修了它

**修法**：
1. 两端 `nativeMargin()` 补齐容器层四字段：`marginLR` / `compBgColor` / `radiusContainer`（+ 上下兜底）。
   - `compBgColor` **仅在有值时**输出 background —— 各组件自身都有白底，无条件输出会盖掉。
   - `radiusContainer` 用独立 key，与组件自身 `radius`（搜索框圆角）**不撞名**，避免「调一个动两个」。
2. 面板 label 明确作用层：`bgColor` → **「搜索框色」**+ tips；`radius` → 「搜索框圆角」；
   新增「容器圆角」「容器左右边距」。
3. 两端上下边距统一为 `marginBottom ?? 8`（保卡间白缝）、`marginTop ?? 0`。

**🎯 新增 `nativeContainerStyle.test.js`（13 例）—— 从 .vue 源码正则提取函数 + new Function 执行**：
- 🔴 **抄副本锁不住真实实现**（改了真实代码测试照样绿），必须**从源码提取再执行**；
- 含一条「两端实现一致」用例（跑 8 组入参逐字段比对）—— 立刻抓到 admin `marginBottom` 缺省 0
  而 C 端是 8px 的不一致，当场修掉。
- 🔧 这类「同源手写、跨 .vue、无共享模块」的函数，**测试层面强制两端比对**，
  比靠人肉记得改两边可靠。

**元规则**：
1. 🔴 **「控件能设置但预览不变」= 参数被架空**，判据：去**渲染层** grep 该 key 有没有被读，
   不要在面板/schema 上找（面板有控件恰恰是问题的一部分）。
2. 🔴 **新增可调字段前先问「组件自身有没有同名/近义字段」** → 需要独立 key（如 radiusContainer）
   或明确 label+tips，否则「调一个动两个」「改了不知道改哪层」。
3. 🔴 **同源手写跨文件的函数，用测试强制两端一致**，别靠注释提醒。

## 搜索框宽度与容器边距解耦（button 老病第二次重演，抽成通用模块）

**用户反馈**：「搜索的问题还是没有解决，跟之前的按钮一样的问题，容器左右边距调了会同步调小搜索框，
这个是之前的坑。没有单独调搜索框大小的了。」

**🔴 病根与 button 完全同源，只是撑满方式不同**：
| 组件 | 撑满机制 | 症状 |
|---|---|---|
| button | `width:100%` | 容器边距一变，按钮跟着变 |
| 搜索框 | **CSS `.search-box{flex:1}`** | 容器边距一变，搜索框跟着变 |
两者都让「容器边距」与「子组件大小」**缠死在一个参数上**。

**🔴 新增的关键坑（按钮那一轮没遇到，因为按钮不在 flex 容器里）**：
搜索框是 **flex 子项**（`.top-bar{display:flex}` + 右侧铃铛），
**只内联 `width` 完全无效 —— `flex:1` 会把width 压掉** → 表现为「宽度百分比滑块完全没反应」，
极易误判成「功能没实现」而去查面板。
正解：必须同时下发 **`flex:none` + `width:%` + `margin:0 auto` + `max-width:100%`**。
像素实测确认：`flex:none` 时 computed `flex=0 auto`、width 生效；不覆盖 flex 时 width 被压。

**✅ 抽成通用模块 `web-app/src/utils/containerChildSize.js`**（避免第三次各写一份）：
- `containerChildSizeStyle(p, {flexChild})` — 统一实现，`flexChild=true` 时额外覆盖 flex；
- `buttonSizeStyle(p)` / `searchBoxSizeStyle(p)` — 两个薄封装；
- `btnSize.js` 改为 **纯转发**（保持既有 import 路径不破），并注释「勿再私藏副本」。
- 两端（admin `ComponentRender.vue` / C 端 `home.vue`）都从这一个模块 import。

**面板**：搜索栏补 `widthMode`（整行/自适应）+ `widthPercent`（20~100，only full 时显示），
tips 写明「与容器左右边距互不影响」；`marginLR` label 改「容器左右边距」+ tips。
存量数据无这两个字段 → `clampPercent` 缺省 100 → 视觉不变，无需迁移。

**🎯 新增 `containerChildSize.test.js`（10 例）**，重点锁：
① flex 子项必须 `flex:none`；② 两分支都要 `display:block`；
③ 宽度与 `marginLR` 无关；④ auto → `fit-content`+`flex:none`；
⑤ `max-width:100%`；⑥ 不得复活负 margin / calc；⑦ 无 undefined 残留。
验证：web-app **282 例**（19 文件）通过、admin 53 例通过、两端构建通过、MP 主包 1450KB。

**元规则**：
1. 🔴 **凡「容器内子组件大小」要独立可调，先问它靠什么撑满**：
   `width:100%` / `flex:1` / `flex:1 1 auto` / `position:absolute+inset` —— 每种解法不同。
   🔴 **flex 子项必须显式覆盖 `flex`**，否则 width 无效（按钮那轮没这坑，因为按钮不在 flex 里）。
2. 🔴 **同一类病第三次出现 → 该抽模块了**。本轮把 button/search 的宽度逻辑合并到
   containerChildSize.js，并让 btnSize.js 转为转发（注释写明「勿再私藏副本」）。
3. 🔴 **存量无该字段时视觉须不变**（clampPercent 缺省 100），否则老页面全变样。

## 第二轮：搜索框文字对齐/垂直居中 + 铃铛 + 蓝色边条回到上方（用户第 3 组反馈）

### 用户诉求（verbatim）
> 1、框中的文字，没有垂直居中，增加可设置居中、居右、居左参数。搜索框右边的信息提示图标，现在这个方式不好，一直居左，看一下你有什么好的优化方案，现在给人的感觉是多余的。我记得之前是有这个功能的：有新的信息的时候，这个图标是有动效的。
> 2、组件框的蓝色边条，现在边条在内部，对于调节参数是有大的影响的，还是要跟最初的一样，放在组件的上方，并且要是置顶，最顶部的组件不要被手机壳挡到。还有就是要优化一下鼠标滑动到组件框的时候，那个预选边框的颜色要明显一点。

### 🔴 本轮最大收获：上一轮「padding 留位」结论是**错的**
上一轮结论写的是「`.pe-canvas{padding-top:22px}` 让操作条落进padding 区不被裁」。本轮为避免假间距试了「留白挂 `.pe-phone`」，**像素实测直接证伪**：
- 写独立 HTML 复刻 `.pe-canvas-wrap > .pe-phone > .pe-canvas(overflow-y:auto) > .pe-comp > .pe-comp-tools(top:-22px)`，A 组 phone 加 padding-top、B 组不加。
- 截图结果：**A 组工具条完全不显示（被裁），B 组正常显示**。
- 根因：**裁剪边界属于滚动容器自己**（`.pe-canvas`），父级/祖先加多少 padding 都不影响它。记忆里「overflow 裁 padding box、padding 区可见」这句本身没错，但**只在滚动容器自己有 padding 时才成立** —— 之前把它误推到了祖先身上。
- ⚠️ 无头 Chrome **`:hover` 不触发**，第一轮截图两个方案都没显示工具条，误以为 A 生效；加 `.active` 强制显示才看出差异。**教训：验证 hover 元素改用 `.active` 或把 rect 数值渲染到页面**。

### 最终方案：操作条移出画布 + JS 定位（唯一同时满足三条约束的做法）
三条约束互相冲突：①在组件上方 ②不被裁 ③画布内零假间距（预览=真机）。留位类做法①②③只能满足二个。
- `PageEditor.vue` 模板：删掉 `.pe-comp` 内嵌的操作条，在 `.pe-canvas` **之后**加平级 `<div class="pe-tools-layer">`，内含**唯一一条**操作条（`v-if="toolsComp"`）。`.pe-comp` 加 `:data-cid="c.id"` 供定位、加 `@mouseenter/@mouseleave` 改`hoverCompId`。
- CSS：`.pe-tools-layer{position:absolute;inset:0;pointer-events:none;z-index:60}`；`.pe-comp-tools` 去掉 `top/right` 定位（由 JS 下发），保留 `pointer-events:auto`。
- JS：`toolsComp = hoverCompId || selected`（hover 优先）；`positionCompTools()` 用组件 rect 算 `top = cr.top-lr.top-tr.height-2`，`top<2` 时翻到组件内侧顶（首组件上方是状态栏，不能被壳遮住 = 用户「不要被手机壳挡到」）；`left` 右对齐并夹在壳内。触发点：`watch(toolsComp)` / `watch(props, deep)` / `watch(components, deep)` / `.pe-canvas` scroll / `.pe-canvas-wrap` scroll / window resize。

### 文字对齐 + 垂直居中

## 第三轮：容器边距解耦（第二次返工）+ 文字垂直居中 + 两端同步（用户第 4 组反馈）

### 用户诉求（verbatim）
> 1、容器左右边距还是会影响搜索框的大小，还是之前的坑，2、搜索框中的文字还是没有垂直居中，还是偏上。3、搜索框的宽度，现在的百分比调节，是左边位置固定的，没法做到跟别的组件左边对齐，这个要优化。4、开发者工具的预览还是和设计中心的预览不同步

### 🔴🔴 核心：前两轮的「百分比解耦」方案**从根上就是错的**
像素实测（写独立 HTML 复刻 `.top-bar(flex) > .search-box(60%)`，改容器 marginLR，用 getBoundingClientRect 量）：
```
marginLR=0  → 宽 225px，左 0
marginLR=20 → 宽 201px，左 20   ← 掉了 24px
marginLR=40 → 宽 177px，左 40   ← 又掉了 24px
```
**百分比永远参照「容器内容宽」** → 容器一变窄，子组件必然跟着变窄。调margin/auto 边距都改变不了。
- 第一轮「负 margin 抵消 marginLR」失败（盖底色/溢出/偏左）
- 第二轮「百分比 + auto 边距」失败（就是上面这个）
- ✅ 第三轮才换**视口单位**：C 端发 `60vw`、admin 按 375px 设计稿发 `225px` → 实测 300/300/300px 完全一致。
- **元规则：用户说「还是之前的坑」= 方案层面选错了，不要在同一个错方案上继续加声明，先质疑方案本身。**

### 🔴 `max-width:100%` 是残留的耦合源（差点又漏）
换成 vw 后实测发现 marginLR=40 时宽 300→295px 被压5px —— **`max-width:100%` 同样参照容器内容宽**，是「解耦后又引入的耦合」。防溢出只能用 `max-width:100vw` / `375px`（视口基准）。auto 分支那处也一起改了。
🔴 教训：解耦类改动要**回头扫一遍所有百分比声明**（width / max-width / min-width / 左右百分比 padding），别只改 width。

### 🔴 问题 2「文字还是偏上」的真因：行盒，不是对齐
`align-items:center` 一直在，居中的对象是**行盒**，而行盒高 = `line-height`。实测（框高36/字号13）：
| line-height | 上间距 | 下间距 | 结论 |
|---|---|---|---|
| `1`（上一轮我加的） | **-1px** | 22px | 文字顶出框外，**最偏** |
| `normal` | 2px | 19px | 仍偏 17px |
| `= 框高` | 10px | 11px | ✅ 真居中 |
→ ✅ 正解：**`line-height` 等于搜索框高度**，由 `placeholderStyle()` 按height 参数内联下发（C 端 `(h*2)rpx`、admin `h px`），CSS 类里**不写 line-height**（写死会覆盖内联值）。上一轮加的 `line-height:1` 是**反向优化**。

### 问题 3：加 `boxOffsetX`（组件自身左边偏移）
宽度改成视口单位后，搜索框左边 = 容器左边（跟容器边距走），没法单独微调去跟宫格/卡片对齐 → 新增滑块 `boxOffsetX`（px 语义，C 端 ×2 转 rpx，admin 直接 px），独立于宽度。
🔴 **命名带 `box` 前缀**：悬浮组件（客服/购物车）已占用 `offsetX` 且语义是「距右偏移」，不能同名不同义。auto 分支也要生效（曾漏掉，已补测试）。

### 🔴 问题 4：抓到两处真实不同步
新增 `nativeSearchParity.test.js`（8 例），用「rpx ÷ 2 === px」逐项比对，当场抓到：
1. **容器 gap**：C 端 `.top-bar{gap:12rpx}`=6px vs admin `.r-native-search{gap:8px}` → 改 6px
2. **CSS兜底高度**：C 端 `.search-box{height:72rpx}`=36px vs admin `.r-search{height:38px}` → 在 `.r-native-search .r-search`（更高特异性）覆盖成 36px，不动基础类（基础类给通用 `search` 组件用）

### 🔴 写「两端一致性测试」的三条纪律（本轮踩全）
1. 函数实现要**正则从 .vue 源码提取 + `new Function` 执行**，抄副本锁不住。
