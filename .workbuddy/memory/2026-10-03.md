## C 端超级表单改为「原地内嵌可填表单」（不再预览+跳转）

用户指出：**画布预览这样没问题，但 C 端/小程序端不能是「预览再点击跳转」** —— 同一份字段信息展示两次，中间那次点击零价值。已确认这是设计上的偷懒并改造。

### 方案（用户拍板：直接内嵌全部字段 + 保留全部复杂能力 + 只留表单标题）
抽出共享组件 `web-app/src/components/SuperFormRender.vue`，两种 mode：
- `mode='page'`：独立填表页（`/pages/superForm/fill`），整屏灰底 + 显示表单名
- `mode='embed'`：装修组件内嵌，**不吃整屏页面底色与内外边距**，保留白底卡片；不重复显示表单名（由外层组件标题承担）

`fill.vue` 改为 33 行薄壳（只做「取路由参数 + 引用组件」），`DesignPage.vue` 的 superform 分支改为直接内嵌。**表单逻辑从此只有一份**，不存在两套实现不同步。

### 依赖搬迁（连带一个隐藏跨项目依赖）
- `web-app/src/pages/superForm/componentStyle.js` → `web-app/src/utils/sfComponentStyle.js`
- `web-app/src/pages/superForm/regionData.js` → `web-app/src/utils/sfRegionData.js`
- 原因：组件从 pages 分包挪到 `src/components/` 后，引不到 pages 下的模块
- **隐藏依赖**：web-admin 的 `apps/superForm/components.js` 跨项目 import 了 web-app 这个文件（相对路径 `../../../../../../web-app/...`）。grep「引用方」时要连web-admin 一起 grep，否则单测会报 `Cannot find module`（表现为「1 failed | 10 passed」但 123 个用例都过，容易误判成用例失败）。

### 踩坑1：v-if / v-else / v-else 三段链会吃掉后续分支
最初写成 `v-if(formName)` / `v-else(未绑定提示)` / `v-else(SuperFormRender)`，结果 formName 有值时中间那个 else 不渲染、**第三个 else 也不渲染**，页面只剩标题（高度 21px、无任何控件）。
**修法**：改成 `v-if(!formId)` 一个条件 + `<template v-else>` 包住标题和渲染器。教训：多个 `v-else` 之间是**互斥的同级链**，不是「前一个不显示就走后一个」。

### 踩坑 2：embed 模式必须剥离整屏样式
`pageBgStyle`（表单的页面底色）和 `globalStyle` 的内外边距是给独立填表页整屏用的，照搬会盖掉宿主页面的底色与装修风格 → embed 模式返回 `{}` / 全 0，仅保留颜色变量与圆角。同时 embed 下给 `.sf-form` 加 `background:#fff; border-radius:8px`，否则输入框直接贴在店铺底色上看不清。

### 踩坑 3：H5 下 eval 触发的事件 uni-app 收不到
`el.click()` / dispatchEvent('click') 对 `.sf-submit` 无效；选项/评分要发完整序列 `pointerdown→mousedown→pointerup→mouseup→click` 才行。最可靠的是 `agent-browser click <CSS选择器>`（真实鼠标事件）。另外提交有二次确认弹窗（`settings.submit.secondConfirm` 默认开启 → `uni.showModal`），不点「确定」就看不到落库，容易误判为提交失败。

## 链接选择器动态化（超级表单 + 全景方案）

### 问题
`linkCatalog.js` 的「超级表单」硬编码唯一一条 `/pages/superForm/fill?formId=1`，desc 写「示例链接：按实际表单替换 formId」——把参数替换的活儿推给用户。有多少表单就只能选 1 个，且 formId=1 几乎必然指错。「全景应用」的 `?planId=1` 同病。

### 方案：静态目录 + `dynamic` 标记
`LINK_CATALOG` 增加 `dynamic: '<key>'` + `items: []`；新增 `DYNAMIC_SOURCES`（key → `path(row)` 模板）与 `parseDynamicLink(key, link)`（回显解析 `?formId=`/`?planId=`）。`LinkPicker.vue` 按 key 分发数据源，骨架沿用已有 `goods` 模式范式。**配置驱动骨架没变，以后任何接后端数据的分类只需加一行。**

### 后端新增 `GET /api/design/plans`（design.js）
**踩坑：不能用现有的 `GET /api/plans`**（`routes/plans.js:69`）—— 它只过滤 `published=1 AND share_enabled=1`，**没有客户维度**，客户后台直接调会把所有客户的方案都列出来（跨租户泄漏）。新接口挂在 `tenant` 中间件下，`plans JOIN projects ON c.id=p.project_id WHERE c.id=?`。

**踩坑：`projects` 表没有 `customer_id` 列**，`projects.id` 本身就是客户 id（`user.customerId` / `req.customerId` 对应的就是它）。第一版写成 `WHERE c.customer_id = ?` 被实跑抓出 `no such column`。**凡是 JOIN projects 做租户过滤，只能用 `c.id`。**

实测隔离：造第 2 个客户(999)+其私有方案(888)后，客户1 结果只含自己的 1、3，不含 888。

### 草稿/停用：全部列出 + 灰显（用户选定口径）
`disabled: true` 的项 `opacity .6`、点击不响应，副信息写明「草稿 · C 端不可访问」（C 端 `/super-form/:id/public` 只返回已发布）。状态标签 `已发布/草稿/已停用`，方案侧 `可访问/未开放`。
副作用是用户能看到「我建了表单但这里灰着」——正好解决此前商品侧下拉为空却不知原因的问题。

### 回显兼容（最易翻车处）
静态目录已不含动态项，历史链接必然匹配不到。顺序：
1. 静态匹配 → 命中走老逻辑
2. 未命中 → `parseDynamicLink` 解析，先切分类并回填 `pick`
3. `await preloadDynamic()` 后 `syncDynamicPick` 校正：目标已删则**回退自定义链接 + 原样保留 value**，并 `ElMessage.warning` 提示（不能静默清空，否则用户点「确定」丢配置）

**踩坑：`dynCache` 只加载一次导致兜底失效。** 组件存活期间删掉表单，列表里该表单仍在 → `syncDynamicPick` 误判「仍存在」，不触发回退（实测复现）。修法：`preloadDynamic` 传 `force=true`，**每次打开弹窗都绕过缓存重拉**。用户随时可能新建/删除，缓存即过期数据。

## 装修画布超级表单按钮与 C 端同步（用户报「装修与小程序按钮不同步」）

### 根因
C 端提交按钮（`.sf-submit`）的文字/样式来自**表单里 submit 组件自身的配置**（文字=`content.label`；样式=`componentStyleVars` → `--c-input-bg/--c-input-radius/--c-border-color/--c-title-color`），而画布预览（`ComponentRender.vue`）渲染的是装修组件自己的 `btnText/btnColor` props（默认「立即填写」/#F0503A、36px 高、8px 圆角）。**装修里怎么改按钮，C 端都不会变** —— 两套数据源必然不同步。

### 修复（所见即所得，同一数据源）
1. **PageEditor**：新增 `sfMetaMap`（formId → `{ label, btn:{bg,radius,border,color} }`，**仅运行时缓存，不写装修草稿 JSON**）+ `ensureSfMeta()`（getSuperForm → `extractSfMeta`：找 submit 组件 → `componentStyleVars(submit, settings.globalStyle)` 挑 4 个按钮变量）；watch 画布组件的 formId 串（immediate），历史草稿/切页/新绑定都自动补拉；失败占位 `null` 防反复请求。跨项目 import `componentStyleVars`（与 `superForm/components.js` 同款路径）。
2. **ComponentRender**：加 `sfMeta` prop；superform 按钮改 `sfBtnLabel()/sfBtnStyle()`——有 meta 渲染真实样式（padding 12px + 16px 字号，对齐 `.sf-submit`），无 meta 回退旧 props 渲染（兼容存量草稿/表单已删）。
3. **componentRegistry**：**删除 schema 里 `btnText`/`btnColor` 两个控件**（C 端本就不生效，留着只会造成「改了没反应」的误解），defaultProps 保留兼容存量读取。

## 按钮大小不一致 + 万能表单跳页（用户二次报「修复无效」）

### 用户澄清（三个关键事实）
1. 「装修页面」= **admin 装修画布**（电脑端编辑器，左边组件库+中间手机预览）
2. 同步方向 = **装修跟随表单**（装修里显示表单真实按钮样式，改样式去表单设计器）
3. 万能表单跳页发生在 **手机端/小程序里的装修首页**，点表单区域就跳走

### 根因1：按钮高度差 22px（画布 48 vs C端 67）
C 端 `.sf-submit` 用的是 `<button>` → uni-app 渲染成 **uni-button，内部元素自带 line-height:2.55（≈40.89px）**，宿主 class 上的 `line-height` **覆盖不到内部**，所以：
`12*2(padding) + 40.89 + 2(border) ≈ 67px`，而画布用 div（line-height normal）只有 48px。
**修法：改用 `<view>` 渲染提交按钮**（样式完全自控），并给 `.sf-submit` 显式 `line-height:1.2; box-sizing:border-box`；画布 `.r-sf-btn` 用完全相同的数值（padding 12/font 16/line-height 1.2/border-box）。
实测修复后两端逐项一致：高 45px / 行高 19.2 / padding 12 / 字号 16 / 圆角 22 / #0076F0 / 文字「确认」。

### 根因2：万能表单「跳页」= 用户小程序包是旧的
源码里 `DesignPage.vue` 的 form-pro **本来就是原地可填的 input/picker + submitForm**（不跳转），H5 实测确认可填、提交不跳页。用户看到旧行为是因为**小程序没重新打包**。
已重打小程序包：`web-app/dist/build/mp-weixin`（含 view 版 sf-submit、form-pro 可填分支）。

### 🔴 本轮最大的坑：改了源码但测的是旧产物

之前一直用 `web-app && npm run build:h5` + 浏览器验证 → **服务目录还是 19:16 的旧产物**，看到的是旧行为（67px、button），误以为修复无效！
