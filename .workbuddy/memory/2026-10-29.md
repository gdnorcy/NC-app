### 🔴 本轮踩的坑（zip 相关）
- **ZIP local header 漏拼 `data` 本体** → 产出文件里没有数据，`unzip -t` 报 "bad CRC"，但 **CRC 值本身是对的**（zlib.crc32 与标准 IEEE 一致，Python 交叉验证过）→ 极易误判成「CRC 算法写错」而去改算法，方向就跑偏了。**先看文件总长 vs 内容长度**。
- **supertest 读二进制响应**必须 `.buffer(true)` + 自定义 `.parse((r,cb)=>{...})` 收集 chunk；默认按 utf8 解析 → `res.body` 是被破坏的对象（报 `ERR_INVALID_ARG_TYPE`）。
- `node:zlib` 的 `crc32` **就是**标准 IEEE CRC-32（与 Python `zlib.crc32` 一致），可直接用，不要另写表驱动实现。

- 措辞纪律：说「A 系统有 bug」前，先分清「A 自己用」与「搬到 B 用」两种语境。

## 生成评估三轮问答（数量/速度/安全，2026-10-29 晚）

用户三问，已落到代码实证 + 真实跑分（Node v22，`qrcode` 依赖正常解析，无生产缺口）。结果写入 `docs/防伪溯源-对标与补齐方案.md` §11。

- **数量上限**：会受限，但全分层合理。单次正式单码封顶 **1 万**（试印 1 千 / 套标 100 套）；单批次流水号空间硬上限 **10^m3 − 1000**（默认 m3=6 → ≈999k/批）；租户批次空间 10^m2；cocom 库存（−888=不限）为业务天花板。要做单批上千万→把 m3 调到 8/9。
- **速度（实测）**：txt 路径几乎无感（10 万码 380ms / 2MB）；**HTML-QR 路径是真实瓶颈**——单次封顶 1 万就要 6.9s，10 万 = 67.6s 单请求 + **1.2GB 单 HTML 文件**（浏览器/排版软件打不开、易超时）。根因：每码一张内联 SVG base64 全塞进一个 HTML。
- **安全**：可吸收对标 = k1~k5 校验位算法 / cocom 库存 / SN 不入库 / 48001 提示。必须修正（已修）= 印刷后锁码制 / 试印分区 / 激活闸门 / 二维码自包含 SVG（替代 url2qr 裂图）/ 每租户 crypto.randomInt 密钥 / zdl+激活 PIN 限流。
- **待补增强（对标也没有）**：H1 HTML-QR 大批量改 ZIP 分文件导出（已有 makeZip+qrcode，零新依赖，体积降到约 120MB、可断点）；H2 k 落库加密（当前 rule_json 明文存 k）；H3 套标维度校验（批次无 bbox/sbox 时静默 0 码）。

> 注意：套标 benchmark 我最初测出 0 码，是因为测试批次 bbox/sbox=0 → 当前逻辑静默生成 0 行（H3 小坑，非产品主链路问题）。
