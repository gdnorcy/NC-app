## 租户会员套餐方案·可行性评估（用户新需求，产出 `docs/租户会员套餐方案评估.md`，已修订）

用户提：租户自建会员套餐（A/B/C…），套餐可逐应用编辑权益（含未来新增应用），会员归属租户自有应用。
**重要澄清（用户指正，修订版已采纳）**：初版误把 `member_package`+`benefits.js`+`quota.js` 当"平台全局 VIP、与租户套餐互不耦合"——**错**。实际规划：作品数/视频号数/留资配额/推送配额/语音/集市场席/折扣…这些权益维度本就打算让租户配进自己会员套餐；`member_package` 只是权益目录的**初版种子**，不是独立 VIP。

修订后模型（统一，非两套引擎）：
- 平台拥有**权益目录 catalog**（`benefit_catalog`：type/app_scope/kind/unit/default/label），把散落三处的权益维度（member_package 列 + benefits.js 常量 + member_levels.benefits）收敛登记；目录标注 `app_scope` → 天然按应用。
- 租户套餐 = `member_levels` 一行（保留 1-50 级/升级/付费/审核/有效期）；按应用落地到 `member_level_app_benefits(tenant,level,app_code,benefits)` 矩阵。
- `benefits.js`/`quota.js` 改造为消费 `resolveAppBenefits(tenant,user,appCode)`（读租户套餐权益）；`member_package` 退化为**新租户种子模板**；平台保留**不可配硬上限常量**作防爆天花板。
- 会员保持 `member_user(tenant×user)`；分叉1 推荐不拆 per-app。
- 目录治理归平台：租户只能配已有 type 的值、不能自建 type。
- 落地：P1a catalog / P1b 矩阵+种子 / P1c 解析器+引擎改造 / P1d 编辑器(按 catalog+应用渲染) / P1e 各应用接各自 type / P1f 存量迁移(platform_user.member_level→租户默认套餐)。
- 两分叉待拍板：①会员是否 per-app（推荐否）；②套餐是否等同等级（推荐是）。
- **分叉1 已确认：会员按租户统一（方案 X）**。分叉2 采用推荐默认（套餐=等级），待最终确认。
- **discount 语义已定：折扣百分比（0=无折扣，10=打9折）**，非折率。目录表 discount 行 unit=`%`、default=`0`。
- 已产出 `docs/租户会员套餐-数据模型草案.md`（P1a/P1b）：benefit_catalog 目录表 + 从 member_package 列/benefits.js 常量/member_levels.benefits 收敛的 21 项种子（works_limit/videos_limit/collect_limit/custom_works_label/voice_enabled/no_ads/all_template/badge/advanced_stats/priority_support/enterprise/ai_report/ai_words/point_rate/rebate/discount/price_visible/market_subject/lead_quota/push_quota）；member_level_app_benefits 矩阵表；member_package 降级为新租户种子模板；resolveAppBenefits 伪代码 + benefits.js/quota.js 改造点 + P1f 迁移草案。尚未落库，待评审。

## 租户会员套餐·P1a/P1b/P1c 基础层落地（已编码，未提交/未部署）

- **P1a `benefit_catalog` 表 + 20 项种子**（`server/src/db.js` 全局种子，member_package 段之后）：

## 租户会员套餐·P1d/P1e/P1f 落地 + P1g 测试（已编码+全量测试过，未提交/未部署）

### 落地内容
- `services/member.js` 模块级导出：`HARD_CAPS`(works500/videos50/collect500/lead1000/push5000)、`TIER_PKG`(free/silver/gold/diamond 四档×5应用)、`tenantOfUser`、`defaultBenefits`、`resolveAppBenefits`、**`effectiveMembership`**。
- **`effectiveMembership` = 全库唯一会员判据**：member_user(有效) → 事实来源；无 member_user → 回落旧镜像 platform_user.member_level；**有 member_user 但已过期 → 视为非会员（不回落旧镜像）**。

- 权益口径**逐档对齐旧 member_package**（存量不得降权）：旧 features 迁移 silver=+ai_report、gold=+ai_report/ai_words(旧种子还含 badge)、diamond=+enterprise/advanced_stats/priority_support；旧配额 gold.lead=50、diamond.lead=50/push=100；旧 voice_enabled silver/gold/diamond=1。TIER_PKG 首版把 silver/gold 的 ai_report 写成 0、gold 的 badge 写成 0 → **会剥掉存量用户权益，已修正**。

### 踩坑（都是"想当然"型，代价实测）
- 🔴 **`projects` 表没有 customer_id 列**（租户主键就是 `projects.id`）——首版 `seedTenantMemberPackages` 写 `SELECT customer_id FROM projects` → **createDb 直接抛 `no such column: customer_id`，所有调用 createDb 的测试全灭**。租户表一律用 `id`。
- 🔴 **`member_levels.id` 是全局 AUTOINCREMENT**（不是按租户）：播种"默认客户"占掉 id 1-4 → 测试里写死等级 id 1/2 全错位（openCard 返回"等级不存在"）。测试必须用 `addLevel` 返回的 id。
- 🔴 **resolver 早期把"旧镜像兜底"绑在 tenantId 存在的前提上** → 未入驻租户的存量 VIP（`migrateLegacyMemberVip` 会跳过 customer_id 为空的行）**权益直接归零**。旧镜像兜底必须与租户解耦，且**要带有效期判定**（旧 levelOf 口径=过期→free，只看档位名会让过期会员仍享银/金权益）。
- 🔴 **读路径与写路径租户维度不一致**（存量 bug，被新模型放大）：radar 写入用"卡片归属租户"（resolveTenant），但 `/radar/export`、`/radar/notifies` 读用 `req.customerId` → 用户后续加入租户就看不到自己名下的提醒/导出对不上。已统一为 `radarTenantOf(req)`。
- `benefits.snapshot` 丢了 `level` 字段（旧 levelOf 口径）→ 前端权益快照缺等级。已用 effectiveMembership 补回。
