# 租户级会员套餐方案 · 可行性评估（修订版）

> 评估对象：租户层面自建「会员套餐」（如 A/B/C 档，仅作说明），套餐可逐应用编辑会员权益（含未来新增应用），会员归属租户自有应用。
> 评估基准：当前仓库实际代码（`server/src/db.js`、`services/member.js`、`services/benefits.js`、`services/quota.js`、`routes/app-registry.js`、`MemberHome.vue`）。
> 结论先行：**可行，且应做成"平台定义权益目录 + 租户配置套餐（×应用）"的统一模型**，而非再叠一套独立引擎。

---

## 0. 重要澄清（基于用户指正）

初版评估把 `member_package` + `services/benefits.js` + `services/quota.js` 当成"平台全局 VIP、与租户套餐互不耦合"——**这是误读**。

实际规划是：作品数、视频号数、留资配额、推送配额、语音简介、集市场席、折扣……这些**权益维度本身就是打算让租户配进自己会员套餐的**。平台侧的 `member_package`（free/silver/gold/diamond）只是这套权益目录的**初版种子**，不是独立于租户套餐的 VIP。

因此本修订版把方案从"两套互不相干的引擎"改为"**平台定义权益目录 + 租户配置套餐（按应用落地）**"的统一模型。

---

## 一、需求复述

1. **租户自建会员套餐**：每个租户在自己后台定义若干套餐（A/B/C…），不等同于平台统一档位。
2. **套餐权益按应用编辑**：每个套餐分别配置"在名片 / 商城 / 集市 / 雷达 / 分销 … 各应用里"给会员什么权益。
3. **覆盖未来新增应用**：新增应用后，套餐编辑器自动能给它配权益，无需改代码。
4. **会员归属租户**：会员是租户私域的会员。

---

## 二、现状对齐（修正口径）

### 2.1 "权益维度"其实散落三处，本质是一个被拆开的目录

| 来源 | 承载的权益维度 |
|---|---|
| `member_package` 表列 | `discount`(折扣) / `collect_limit`(收藏上限) / `voice_enabled`(语音简介) / `group_limit`(建群数，已下架) / `lead_quota`(留资配额) / `push_quota`(推送配额) / `market_subject`(集市场席) / `features`(JSON：basic_card、advanced_stats、market_full、no_ads、badge、priority_support、ai_report、ai_words、enterprise…) |
| `services/benefits.js` 常量 `BENEFITS` | `worksLimit`(作品数上限) / `videosLimit`(视频号数上限) / `customWorksLabel`(自定义作品标签) |
| `member_levels.benefits` JSON | `discount` / `积分倍率` / `返比` / `价格可见`（租户级，但**零消费**） |

- 三处合起来才是"权益维度全集"，却分别被**平台级** `benefits.js`/`quota.js` 硬编码读取 + **租户级** `member_levels.benefits` 孤立。
- 消费方现状：`benefits.js`/`quota.js` 读 `platform_user.member_level`（平台账号级）；`member_levels.benefits` 无人消费。

### 2.2 应用模型（"应用"= 权益的天然归属）

- 应用 = `solutions` 表一行（`code`/`name`/`app_config`）；租户通过 `projects.solutions`（启用清单）+ `projects.config[code]`（逐应用配置）开通。
- 路由 `app-registry.js` 已提供：`/api/apps`、`/tenant/apps`、`/tenant/apps/:code/config`、`/tenant/apps/:code/check`。
- **新增应用 = 往 `solutions` 插一行**。绝大多数权益维度天然归属某个应用（见 4.1），因而"按应用配权益"几乎是目录的内生属性。

### 2.3 关键缺口（修正后）

1. **权益未被"目录化"**：想新增一个权益（如直播时长），要同时改 `member_package` 列 + `benefits.js` 常量 + 前端三处，极易漂移。
2. **租户侧 `member_levels.benefits` 配了没人消费**。
3. **平台 `benefits.js`/`quota.js` 把"平台账号等级"和"租户套餐权益"混在同一套词汇里**，却只服务平台账号，租户无法干预。

---

## 三、可行性判断（修正结论）

**可行，且应该做成"统一权益目录"，而不是"再加一套"。** 把散落三处的权益维度收敛成一个**平台拥有的权益目录（catalog）**，租户据此配置自己的套餐（A/B/C），并按应用落地。`member_package` 退化为新租户的**种子模板**，不再作为平台级独立 VIP。

---

## 四、推荐模型：平台目录 + 租户套餐 × 应用

### 4.1 权益目录（catalog，平台拥有 schema）

新增一张**平台统一定义**的目录表，把三处散落的维度收敛登记：

```
benefit_catalog (
  type         TEXT PRIMARY KEY,   -- 如 works_limit / videos_limit / lead_quota / push_quota
  app_scope    TEXT,               -- 归属应用：card / mall / market / radar / live ...
  kind         TEXT,               -- number / switch / text
  unit         TEXT,               -- 条 / % / 天 ...
  default_value TEXT,
  label        TEXT                -- 后台展示名："作品数上限"
)
```

种子数据（来自现有三处收敛）：

- **资源配额类**：`works_limit`(名片/作品) / `videos_limit`(视频号) / `collect_limit`(收藏) / `lead_quota`(留资) / `push_quota`(推送)
- **功能开关类**：`voice_enabled`(语音简介) / `market_subject`(集市场席) / `custom_works_label` / `no_ads` / `badge` / `all_template` / `advanced_stats` / `priority_support` / `enterprise` / `ai_report` / `ai_words` …
- **营销类**：`discount`(折扣) / `point_rate`(积分倍率) / `rebate`(返比) / `price_visible`(价格可见)
- **未来应用自由加 type**（如 `live_duration`）——新增应用时往目录登记自己的 key 即可。

`app_scope` 直接标注每个权益归属哪个应用，**天然就是"按应用"**：`works_limit`→名片、`lead_quota`/`push_quota`→雷达/留资、`market_subject`→集市、`discount`→商城。

### 4.2 租户套餐（member_levels 即套餐）

- **套餐 = `member_levels` 一行**（保留既有 1–50 级 / 升级模式 consume/apply / 付费 `buy_price` / 审核 `review_mode` / 有效期 `valid_days`）。
- 每套餐按目录配置权益、按应用落地：

```
member_level_app_benefits (
  tenant_id INTEGER, level_id INTEGER, app_code TEXT,
  benefits  JSON,                 -- 该套餐在该应用下的权益，如 {"discount":0.9,"booth":true}
  UNIQUE(tenant_id, level_id, app_code)
)
```

### 4.3 消费引擎改造（核心）

- 把 `benefits.js` / `quota.js` 从"读 `platform_user.member_level`"改为"读**租户解析后的套餐权益** `resolveAppBenefits(tenant, user, appCode)`"。
- **`member_package` 退化为种子模板**：每个新租户初始化时，把 free/silver/gold/diamond 作为默认套餐写入其 `member_levels`（名称/权益可改）。平台不再单独发 VIP。
- **平台保留一个不可配的"硬上限常量"**（防爆/防滥用，绝对天花板），与租户套餐权益分层：硬上限 = 天花板，租户套餐 = 软权益。这取代了原 `benefits.js` 里平台账号级的强制限额角色。

### 4.4 解析器

```
resolveAppBenefits(tenantId, userId, appCode)
  → 取该会员套餐在 appCode 的权益（来自 member_level_app_benefits，回退到套餐全局默认）
```

各应用只消费自己 `app_scope` 的 type：商城读 `discount`、集市读 `market_subject`、雷达读 `lead_quota`/`push_quota`、名片读 `works_limit`/`videos_limit`。前端 `MemberHome.vue` 套餐编辑弹窗**按目录 + 已开通应用自动渲染分组**，未来应用注册 key 后自动出现。

---

## 五、开工前必须先拍板的两个分叉

**分叉 1：会员是否 per-app？**
- 方案 X（推荐）：会员是**租户级统一身份**，`member_user(tenant×user)` 不变，权益按应用兑现。模型简单，契合现有数据。
- 方案 Y：会员按应用独立（用户在商城是会员、在雷达不是）。需把 `member_user` 改造成 `(tenant, user, app)` 或新增 per-app 会员表，复杂度高、与现有模型冲突。
- **建议 X**。

**分叉 2："套餐"是否等同"等级"？**
- 推荐：**套餐 = 会员档位（`member_levels` 的一行）**。保留既有能力，仅把命名/视角从"等级"升级为"套餐 A/B/C"。不建议引入与等级正交的另一维度（无额外收益、工作量翻倍）。
- **建议套餐即档位**。

## 六、落地路径（修订）

| 阶段 | 内容 |
|---|---|
| **P1a 目录化** | 建 `benefit_catalog`；从 `member_package` 列 + `benefits.js` 常量 + `member_levels.benefits` 收敛种子数据 |
| **P1b 矩阵 + 种子** | 建 `member_level_app_benefits`；新租户用 `member_package` 作模板初始化默认套餐（用 `schema_marks` 留痕防重启覆盖） |
| **P1c 解析器 + 引擎改造** | `services/member.js` 加 `resolveAppBenefits`；`benefits.js`/`quota.js` 改为消费租户解析权益；平台硬上限抽成常量 |
| **P1d 编辑器** | `MemberHome.vue` 按 catalog + 已开通应用渲染分组（零硬编码应用名/权益名） |
| **P1e 各应用接入** | 商城/discount、集市/market_subject、雷达/lead_quota+push_quota、名片/works_limit+videos_limit … 增量接 |
| **P1f 存量迁移** | `platform_user.member_level` → 映射到租户默认套餐（平台等级仅作新租户种子，之后租户自管）；`member_package` 列 → catalog 种子；`member_levels.benefits` 旧 JSON → 矩阵 |

**工作量粗估**：P1a+P1b+P1c（目录+矩阵+解析+引擎改造）约 4–5 天；P1d 编辑器约 2 天；P1e 按应用数量增量（每应用约 0.5 天）；P1f 迁移约 1–2 天。

## 七、风险与注意（修订）

1. **平台资源保护不能丢**：原 `benefits.js` 限制免费用户无限上传，是平台安全需要。改为租户套餐后，必须保留**平台硬上限常量**作为绝对天花板，否则租户把资源开到无限会拖垮平台。
2. **存量平台 VIP 用户如何映射**：现有 free/silver/gold/diamond 平台用户，迁移为"某租户的默认套餐"。推荐策略——**平台等级仅作新租户种子，之后租户完全自管**；存量平台用户按其等级落到对应租户默认套餐，平台不再单独维护 VIP。
3. **目录治理权归属平台**：`benefit_catalog` 由平台统一定义，租户**只能配已有 type 的值、不能自建 type**。保证跨租户词汇一致、前端可渲染、未来应用能自动认领。
4. **未来应用零改动**：新应用注册 catalog key + 声明 `app_scope` 后，编辑器与解析器自动支持，无需改会员代码。
5. **性能**：`resolveAppBenefits` 按 `(tenant, user, level, app)` 解析，可加轻量缓存。

---

## 八、一句话结论（修订）

**可行且推荐**，统一为「**平台权益目录（catalog）+ 租户套餐（member_levels）× 应用（matrix）**」。平台从"既当裁判又当运动员（自己发 VIP）"转为「**定规则（目录 + 不可配硬上限）+ 给种子（`member_package` 作模板）**」，租户在自己的套餐里配置权益并逐应用落地。这修正了初版"两套引擎互不耦合"的误读——它们本就是同一套权益，只是被拆开且没接上租户。先把**第五节两个分叉**拍板，即可从 P1a 开工。
