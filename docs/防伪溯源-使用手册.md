# 防伪溯源 · 使用手册（建立一套完整防伪码的全流程）

> 适用版本：P0（当前线上版本）
> 代码位置：后台 `web-admin/src/views/customer/apps/trace/index.vue`；服务端 `server/src/routes/trace.js` + `server/src/services/traceGenerate.js`；C 端 `web-app/src/pages/trace/index.vue`
> 入口：应用中心 → 高级功能 → 防伪溯源

---

## 0. 开始前必须知道的三件事

| 事项 | 说明 |
|---|---|
| **应用必须已开通** | 服务端对每个后台接口都做 `hasSolution(tenantId, 'trace')` 校验，未开通一律 403「未开通「防伪溯源」应用」。应用开通后首次访问会懒初始化一行 `trace_settings`，库存给「不限」。 |
| **码制一旦生成过码就锁定** | 前缀、各段长度改了，之前印出去的码全部失效。必须**先规划码制，再生码**。 |
| **批次默认「停用」，要激活才生效** | 消费者验真时要求 `batch.is_active = 1`，新建批次后必须回到列表点「激活」，否则扫码提示「防伪码不存在或已失效」。 |

---

## 1. 完整流程图（从零到消费者扫码）

```
① 开通应用
      ↓
② 防伪设置 → 码制配置      ← 定义「码长什么样」（前缀/各段长度/校验字符集）
      ↓
③ 防伪设置 → 功能设置      ← 溯源页域名、查询次数上限、开关（历史/验证码/窜货…）
      ↓
④ 防伪设置 → 回复设置      ← 验真页文案（首查/复查/超限提示）
      ↓
⑤ 防伪设置 → 企业设置      ← 厂家名称、电话、官网、Logo（验真页展示用）
      ↓
⑥ 批次管理 → 新增批次      ← 一批货一个批次：产品/厂家/品牌/产地/窜货策略/套标/奖励
      ↓
⑦ 批次列表 → 激活批次      ← 不激活扫码无效
      ↓
⑧ 批次列表 → 生成防伪码    ← 消耗库存，导出 .txt/.html，交付印刷
      ↓
⑨ 贴标/印刷 → 上市
      ↓
⑩ 消费者扫码 → C 端验真页 → 溯源码信息 + 展示位/商品链接
      ↓
⑪ 后台查：数据统计 / 查询历史 / 错误码
```

## 2. 逐步操作详解

### 步骤 ① 开通应用
服务端硬校验：未开通 `trace` solution 的租户，所有 `/api/customer/trace/*` 接口返回 403。

### 步骤 ② 码制配置（**最关键，先做**）
路径：防伪设置 → 码制配置 → 保存码制

| 字段 | 含义 | 约束 |
|---|---|---|
| 码前缀 m1 | 码开头的字母标识，如 `FW` | 最多 2 位，必填 |
| 批次号长度 m2 | 码中间代表批次的那一段 | 1–12 |
| 流水号长度 m3 | 自增序列长度，决定该批次可生成的码量 | 1–12 |
| 校验位长度 m4 | 防伪校验位长度 | 1–12 |
| 防伪码总长 m5 | 整串码的总长度 | 6–40 |
| 错误次数上限 | 同一 OpenID/IP 连续输错的次数上限，超过返回 429 | 1–999 |
| 校验字符集 k1–k4 | 计算校验位用的字符表，各 10 位，必填 | 10 位 |

> ⚠️ **为什么 k 不能留空**：k 是校验位的字符表，落空会导致校验位退化成常量，防伪码可被批量伪造。服务端会逐格回落到默认字符集（不会整表替换租户自定义值），但请勿留空。

### 步骤 ③ 功能设置
- **溯源页域名**：留空则用当前站点域名。⚠️ 填了就用填的这个，生成出来的二维码链接以它为准 —— **迁移域名时必须重新生码**，否则老码的二维码会指向错地址。
- **查询次数上限**：某批次被查询超过该次数且该码是首次出现时提示「查询次数已达上限」（填 `con_msg`），0 = 不限。
- **历史记录条数**：C 端「我的验真记录」返回多少条。
- 功能开关（已落库，`siteroot` / `upperlimit` / `history_limit` / `ishistory` 等）：
  历史查询、积分、外链跳转、码激活、窜货检测、生成习惯记录、防窜货提示、验证码、开放对外 API、抽奖。
  > 现状说明：开关值会保存，但**部分开关（积分/外链/抽奖/码激活）的后端消费逻辑后续才接入**，当前打开不会有对应行为。

### 步骤 ④ 回复设置（验真页文案）
- 商品模式：欢迎语、欢迎副文案、首查提示（如「验证通过」）、二次查询提示（如「请勿重复验证」）、三次查询提示、超限提示。
- 活动模式：同上六项的「活动」变体，待 C 端支持活动模式后生效。
- 公众号关注回复：关注后首条 / 第二条自动回复。

### 步骤 ⑤ 企业设置
企业名称、客服电话、厂家电话、常用快递、联系链接、官网、企业简介、名片链接、录入链接、Logo、主图 —— 这些会展示在 C 端验真/溯源页。

### 步骤 ⑥ 批次管理 → 新增批次
批次 = 一批货。字段：

| 字段 | 说明 |
|---|---|
| 批次号 | 长度必须与码制「批次号长度」一致（如 7 位） |
| 产品 / 厂家 / 品牌 / 原产地 / 省 / 市 / 区 | 溯源页展示信息；省市区同时是窜货检测的判断依据 |
| 窜货检测 | 关闭 / 按省 / 按市 / 按区县 |
| 活动类型 | 无奖励 / 积分奖励 1–5 / 实物商品（邮寄）/ 微信卡券 / 微信红包 / 专属抽奖 / 商品联动不发放 |
| 套标箱规 / 盒规 | 每箱盒数、每盒码数（0 = 不启用套标）；启用后生成的是**套标**（箱码+盒码+单码层级） |
| 奖励配置（四分区） | 积分上下限、微信卡券 cardId 列表、红包商户号、专属抽奖奖项（名称/权重/值） |

### 步骤 ⑦ 激活批次
批次列表 → 激活。验真接口强校验 `is_active = 1`，未激活扫码提示「防伪码不存在或已失效」。

### 步骤 ⑧ 生成防伪码
批次列表 → 生成防伪码：

| 项 | 取值 |
|---|---|
| 码型 | 1 = 普通文本码（含校验位，可扫码/手输）；6 = 纯数字码 |
| 生成数量 | 1–10000 |

生成后返回 `.txt`（HTML 型码返回 `.html`），每行一条；二维码型的一行是 `溯源链接,校验位` 形式。

**生成链接长这样**（也就是印在码里的 URL）：

```
{溯源页域名}/card/#/pages/trace/index?co={防伪码}&tid={租户ID}
```

**库存消耗规则**：每生成一个码扣 1 个库存（套标模式按「套数 × 每套码数」扣）。库存不足会报错，且**只生成库存允许的数量**。

### 步骤 ⑨–⑩ 印刷上市 / 消费者扫码
消费者用微信扫贴在商品上的码 → 落到 C 端 `pages/trace/index`（H5 走 `/card/#/pages/trace/index`，小程序走同名分包页面）→ 服务端 `POST /api/trace/public/verify` 校验：

1. 校验位不对 → 记 `trace_wrong_attempts`，按错误次数上限返回 429；
2. 码有效但批次未激活 / 不存在 → 「防伪码不存在或已失效」；
3. 首查 → 落 `trace_codes`（`num=1`），批次 `rcon + 1`，返回「验证通过」；
4. 复查 → `num` 累加，返回第几次查询 + 首次/上次查询时间；
5. 查询超过「查询次数上限」且该码首次出现 → 返回超限提示。

验真页下方会展示：**首页展示位**（防伪设置 → 通用设置，最多 8 个）和按「商城集成」配置跳转的商品链接。

### 步骤 ⑪ 后台运营与排查
- **数据统计**：累计查询次数、码总数、错误码数、批次数；地域分布（省/市）；查询趋势（按天）。
- **查询历史**：每条记录含时间 / 类型 / 摘要 / OpenID / IP / 备注（`recharge` 充值、验真查询等）。
- **错误码**：输错的码（OpenID/IP/码值/时间），用于发现批量试探或串货。
- **防伪码记录**：可对单个码「标记错误」。

## 3. 库存机制（回答「无限库存」与「充值库存」）

库存存在 `trace_settings.cocom` 这一列：

| cocom 值 | 含义 | 生成码时的行为 |
|---|---|---|
| `-888` | **不限**（后台显示「防伪码库存：不限」） | 直接放行，**不扣减** |
| `> 0` | 有限库存 | 按实际数量扣减，不足时只生成剩余允许的条数 |
| `0` | 无库存 | 抛出「防伪码库存不足，请先充值」 |

**新租户首次访问时会被初始化为 `-888`（不限）** —— 这是为了避免「应用开通后第一批码永远生成不出来」。

因此在「不限」状态下：
- 后台点「充值库存」+1000，结果仍然是「不限」，`next = current === -888 ? -888 : current + amount` 这条逻辑保证它不会把「不限」覆盖成有限数字；
- 换句话说：**在「不限」状态下，充值是一个空操作**，只会在查询历史里多一条 `recharge` 记录（如截图所示「充值防伪码库存：+1000，当前 不限」）。

只有当天平台把这个租户的 `cocom` 改成有限数值（例如 0），充值才会真正体现。

## 4. 商城集成

路径：防伪溯源 → 商城集成。决定验真页「查看商品」跳向哪里：

| 取值 | 含义 |
|---|---|
| 0 | 不关联商品 |
| 1 | 本平台商城商品（跳 `/mall` 里对应的 goods） |
| 2 | 外部商品链接 |

> 服务端刻意**不列**外部第三方商城的表 —— 我们库里没有那些表，列进下拉就变成「后台能选、服务端零消费」的空头权益。

## 5. 已知边界（当前 P0 版本）

| 能力 | 现状 |
|---|---|
| 红包真发 | **未接通**。需先配置租户级微信支付商户号与证书；未提供凭据前只保存文案与策略，不会实际发红包 |
| 积分发放 | 受会员积分体系影响，部分场景等待接线 |
| 微信卡券 / 专属抽奖 | 配置可存，发奖链路随奖励引擎逐步接入 |
| 部分功能开关（积分/外链/抽奖/码激活） | 值会保存，但后端消费逻辑后续批次接入 |
| 套标高级码型（含 HTML 二维码导出） | 已支持，产物是 `.html` 而非 `.txt` |
