# 动态发布能力增强 · 市场对标调研报告

> 项目：360全景 / 智能名片小程序
> 命题：**「发布动态的内容和方式太简单了」** —— 让「手动发布一条动态」这件事，可选的内容形态和发布方式都丰富起来
> 调研时间：2026-10-21
> 调研方式：WebSearch / WebFetch，微信生态为主，补充脉脉 / LinkedIn / 知乎 / 小红书

---

## 0. 调研边界（先说清不做什么）

本轮调研**明确排除**以下方向，这是上一轮已被否掉的：

- ❌ 自动发布 / 定时任务调度 / 机器人批量发帖 / 运营向自动化
- ❌ 服务商侧的「智能朋友圈批量运营」类 SaaS 能力（微盛、语鹦等第三方工具的能力，不属于我们要做的产品能力）

本轮**只调研**：单个用户在手动点「发布」这个动作时，能选什么内容形态、能选什么发布方式。

判定标准很简单：**用户手动的、一次性的、可选项变多** ＝ 本轮范围；**系统替用户自动跑的** ＝ 不在范围。

## 1. 现状盘点：我们现在有什么，缺什么

### 1.1 现状 5 个能力

| # | 能力 | 现状证据 |
|---|------|----------|
| 1 | 纯文字 | `web-app/src/pages/card/dynamic.vue:41` textarea `maxlength=500` |
| 2 | 图片（最多 9 张） | `dynamic.vue:44-55` img-picker，`MAX_DYNAMIC_IMAGES = 9` |
| 3 | 立即发布 | `dynamic.vue:162` 直接 POST，无任何时间选择 |
| 4 | 可见范围两档 | `dynamic.vue:58-61` 只有「公开 / 仅自己」两个按钮 |
| 5 | 点赞 + 评论 | `server/src/routes/card.js:2126-2160` |

### 1.2 关键缺口（含被浪费的存量字段）

| 缺口 | 说明 |
|------|------|
| **title 字段空转** | `card_dynamic.title` 字段存在（`db.js:1135`，且有 `db.js:1858` 的加列迁移），INSERT 也写了（`card.js:2118`），**但前端表单根本没有输入框** → 字段写了空串，等于零成本白捡的一个能力 |
| 视频 | 一条动态只能挂 9 张图，讲不了事、撑不起产品介绍 |
| 链接/小程序卡片 | 动态里挂不了任何可跳转的东西 → 名片最核心的「转化」能力完全没用上 |
| 话题标签 | 无。访客看到一条动态，无法通过话题找到同类内容，也没有聚合页 |
| @提及 | 无。无法在动态里点名某人 |
| 位置 | 无。名片场景下「门店/地址」是高价值信息 |
| 可见范围只有两档 | 无「部分可见」「不给谁看」，也没有任何分组体系 |
| 无草稿 | 写了半条动态退出 → 全丢 |
| 无定时 | 现在只能立刻发 |
| 发布后不可改、不可删、不可撤回 | `card.js` 只有 POST/GET，**没有任何 PUT / DELETE 动态的路由** |
| 无二次分发 | 发完就结束，动态详情页连 `onShareTimeline` 都没配，访客无法转发一条动态出去 |

### 1.3 我们的独特优势（对标产品给不了的）

我们是**小程序内的电子名片**，不是社交平台。这意味着三件事：

1. **点击即回到名片**：社交平台的链接卡片跳出到别人的地盘，我们的卡片点开还是名片，转化链路零损耗。
2. **受众是「谁来看我」而非「谁关注我」**：访客是一次性的、带着明确意图来的（他在找这个人），所以「分级可见范围」的价值比朋友圈高得多——但**前提是我们得有「访客身份」这个维度**，目前 visibility 只有一个 bool 语义。
3. **横切面已经存在**：名片本身已有产品/案例/服务等结构化数据，动态可以天然引用它们，不需要用户重打一遍。

### 2.1 表格里最值得抄的三件事

1. **LinkedIn 的元素化发布器**：官方文档明确列出 Post 的所有可选元素 —— 图片/视频、Poll、Document、Event、Celebrate、Person Tag、Brand Partnership，以及独立的时间钟（schedule）和受众下拉（Anyone / Connections only / Group）。这是一份「一条动态能承载什么」的权威清单，本报告第 3 节的候选清单基本照它 + 微信生态的结构来。
   来源：<https://www.linkedin.com/help/lms/answer/a522902>

2. **企微「attachments 三选一」的约束设计**：`shareToExternalMoments` / `发表内容到客户朋友圈` 接口的 attachments 明确「最多 9 张图片，或 1 个视频，或 1 个链接」**三选一**，传混合类型直接报错 `invalid attachments msgtype`。这是微信生态给出的答案：**多图和卡片互斥**。我们做设计时必须尊重这个惯例，否则用户会预期「9 图 + 1 链接」而产品给不了。
   来源：<https://developer.work.weixin.qq.com/document/path/94607>、<https://developer.work.weixin.qq.com/document/path/94608>

3. **「已发布不可撤回」是社交平台共识**：企微 `cancel_moment_task` 文档末尾一句「本接口无法撤回已经发表到客户朋友圈的信息」；公众号「立即群发不可撤回，定时可取消」；知乎「只有删除，无撤回」。结论：**我们不需要做「撤回」这个语义，要做的是「编辑 + 删除」**。撤回在名片场景下反而是伪需求（名片是主页性质，撤回等于主页开个洞）。

## 3. 内容形态候选清单（10 项）

> 适配度按「小程序 + 电子名片 + 单人手动发布」三个约束打分：✅高 / 🔶中 / ❌不适用

### ① 标题（title）
- **是什么**：独立标题字段 + 正文，列表页标题加粗单行展示。
- **参考**：小红书（标题+正文，标题权重高于正文）、LinkedIn（超 3000 字符自动引导写 Article）、知乎专栏。
- **适配度**：✅ **字段已经在库里了**（`db.js:1135` / `card.js:2118` 都已写入），前端加一个 input 而已。
- **成本**：**0.5 人日**（前端 input + 列表页渲染 title + `toDynamic` 确认已返回）。

### ② 视频
- **是什么**：一条动态挂一段短视频（封面 + 时长 + 播放）。
- **参考**：企微客户朋友圈（1 个视频，客户端 ≤30S/10MB，帧率 30FPS、码率 1.67Mbps）、朋友圈（2025-03-10 起支持最长 5 分钟长视频）。
- **适配度**：🔶 高价值但成本高。产品演示、公司介绍类动态，视频比 9 张图强得多。
- **成本**：**3 人日**。含 `chooseMedia` 选视频 → 服务端存文件 → 列表页 `<video>`/封面图 → 上传体积与超时处理。企业微信给的口径是 30S/10MB（小程序弱网更差，建议 ≤30S），可直接照抄这个阈值。
  来源：<https://open.work.weixin.qq.com/help2/pc/14767>

### ③ 链接预览卡片（link preview）
- **是什么**：正文下方一张卡片，含**封面图 + 标题 + 摘要（2 行）+ 来源域名**，点击进入对应页面。
- **重要澄清**：微信里那种自动抓 OG 标签的链接卡片，是**微信抓取你的 H5 页面**产生的，**不是小程序内可用的能力**。小程序里没有原生 link preview 渲染器。所以我们只能**自己做卡片 UI**，自己存标题/摘要/封面/目标 path。
- **参考**：企微 `link` 附件（`title` / `imgUrl` / `desc` / `url` 四个字段结构）、朋友圈的网页链接形态、LinkedIn 的 link preview（2025 年已改为更小的图预览）。
- **适配度**：✅ **这是本轮最高性价比的一项**。名片场景下，「这条动态附了一个案例详情页 / 一个产品页 / 一个预约入口」的转化价值，远高于多一张图。
- **成本**：**1.5 人日**（表加 4 个字段 + 前端卡片组件 + 点击跳 `web-view` 或内页）。注意目标 URL 若走 `web-view`，域名必须已在小程序后台配「业务域名」白名单，否则 WebView 也打不开 —— 建议**优先只支持跳自家小程序内页**。
  来源：<https://developer.work.weixin.qq.com/document/path/94607>、<https://zeeklog.com/wei-xin-xiao-cheng-xu-wai-lian-da-kai-yu-fu-zhi-dou-di-de-shi-yong-xie-fa>

### ④ 小程序卡片（跳自家小程序指定页）
- **是什么**：链接预览卡片的特殊形态，目标锁定自家小程序的某个 path，而不是 H5。
- **参考**：视频号挂载小程序组件（用户点击后**拉起小程序半屏卡片**，进入对应服务页面）；视频号主页挂小程序服务卡片。
- **适配度**：✅ 很高。这正是「动态 → 名片某模块 → 留资/预约」的转化闭环，且**不依赖任何外部域名白名单**。
- **成本**：**0.5 人日**（③ 的实现里多加一个 `targetType: 'page' | 'url'` 分支即可）。
  来源：<https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/industry/channels/components.html>

### ⑤ 名片模块引用（动态挂名片上的结构化内容）
- **是什么**：不是自由外链，而是从「我的产品 / 我的案例 / 我的服务」里挑一项，渲染成一张带图带标题的卡片。
- **参考**：企微挂「商品」、小红书商户版挂商品 SKU（正文语义识别后提示可插入商品，生成可追踪点击与转化的跳转链接）。
- **适配度**：✅✅ **这是我们独有的、竞品抄不了的一项**。别人的动态只能贴外链，我们可以直接引用名片里已有的结构化数据 —— 用户零成本，转化路径最短。
- **成本**：**1.5 人日**（需先确认名片侧有哪些可引用的实体表，复用其 id + 标题 + 封面图）。
  来源：<https://www.oppozhijia.com/wz/944463.html>

### ⑥ 话题标签
- **是什么**：正文里 `#话题#`，点击进入话题聚合页。
- **参考**：朋友圈 `#话题#`、视频号话题（建议加流量大的话题）、知乎 tag（优质内容会被收进专题合集）、脉脉话题、小红书话题。
- **适配度**：✅ 中等。**在名片场景里，话题的价值弱于在社交平台** —— 我们没有公域流量池，访客不会为了「话题」而来。但对「同行业名片聚合页」有价值。
- **成本**：**2 人日**（发布器 # 补全 + 解析 + 标签存储 + 聚合页 + 列表页标签筛选）。
  来源：<https://www.baike.com/wikiid/9044716702798321771>、<https://m.baike.haosou.com/doc/6271501-27994069.html>

### ⑦ @提及
- **是什么**：正文里 @某人，被 @ 的人收到提醒。
- **参考**：脉脉发内容时可「勾选相关人脉，让他们第一时间收到推送」；视频号可 @ 人；微信朋友圈有「提醒谁看」。
- **适配度**：🔶 中。技术不难但**通知链路是成本大头**（小程序订阅消息需要用户逐次授权，无法静默推送）。
- **成本**：**2.5 人日**（@ 选择器 + 文本内联标识 + 通知下发 + 订阅消息模板申请）。小程序 `@` 交互有成熟方案：用零宽字符 `'\u200B'` 作哨兵标记 mention 边界，避免用户改字后样式残留。
  来源：<https://developers.weixin.qq.com/community/develop/article/doc/000286725442a02824743acd666c13>、<http://www.ledanji.com/p/1924769.html>

### ⑧ 位置
- **是什么**：选择地理位置，展示在动态里。
- **参考**：企微「成员个人发布朋友圈还可以添加定位（支持选择 30 公里内的地址）」，官方话术就是「吸引客户到店」；视频号地址（触发地理推荐）；小红书位置。
- **适配度**：🔶 取决于用户是不是有实体门店。**无门店的用户（如远程服务、自由职业）价值为零**。
- **成本**：**1 人日**（`uni.chooseLocation` + 逆地址解析 + 存储）。可做成「名片上的地址」一键带入，而不是每次单独选。
  来源：<https://work.weixin.qq.com/nl/act/p/c06235bcb6b143b3?gray=0>

### ⑨ 投票 / 问答
- **是什么**：动态挂一个单选/多选投票，访客点一下。
- **参考**：LinkedIn Poll（官方列为 post 的标准元素，评论框常成为高质量互动金矿）；微信群投票（≤6 个选项，可匿名）。注：**朋友圈并未提供投票入口**，网上「朋友圈发投票」的文章多为第三方小程序工具，不足为凭。
- **适配度**：🔶 「名片动态投票」= 客户满意度调研 / 意向调研，在 to B 场景（360 全景本来就是 to B）**意外地合适**。
- **成本**：**2.5 人日**（投票表 + 投票交互 + 结果统计 + 防重复投票）。
  来源：<https://www.linkedin.com/help/lms/answer/a522902>

### ⑩ 文件 / 附件
- **是什么**：动态里挂 PDF/Word/图片集。
- **参考**：企微客户朋友圈支持「文件」（从微盘选）、群发助手支持文件（管理端 200M）。
- **适配度**：❌ **不适用**。访客看名片不需要收文件，且小程序内预览 PDF 体验差（必须走 `web-view` 或 `wx.openDocument` 受限）。这是「企业 IM 场景」特有的需求，不是名片场景的。
- **成本**：不评估。

## 4. 发布方式候选清单（8 项）

### ① 可见范围：扩到四档
- **参考**：朋友圈 —— 公开 / 私密 / 部分可见 / 不给谁看，后两者按**通讯录标签**筛选；LinkedIn —— Anyone / Connections only / Group；小红书 —— 公开 / 仅粉丝 / 私密；企微 —— 全部客户 / 按标签 / 部分客户。
- **适配度**：✅ 但**「部分可见」在我们这里语义不同**。朋友圈的标签是「人」，我们的「人」是**访客**（多数没登录）。所以可落地的版本是：
  - 公开
  - 仅自己
  - **仅登录用户可见**（把 bool 升级为三态，访客未登录看不到）
  - **仅互相关注者 / 仅被名片主人授权的客户可见**
- **成本**：**1.5 人日**（visibility 从 bool 升级为枚举 + `card.js:548` 的 `visibility='public'` 过滤条件要同步改；`:2116` 的归一逻辑 `visibility === 'private' ? 'private' : 'public'` 也要改）。⚠️ 改这里必须同步改测试 `server/test/card-voice-dynamic.test.js:64,70,80,93`。
- **注意**：不支持「不给谁看」。名单型黑名单在名片场景没有意义（访客不是你的好友，你也不知道他是谁）。
  来源：<https://kf.qq.com/faq/161223zaiQbm161223ziqym2.html>

### ② 客户分组（先把标签体系建起来）
- **参考**：企微按客户标签筛可见范围；朋友圈按通讯录标签；脉脉按人脉分组。
- **适配度**：✅ 若我们有「客户」概念（销售型名片场景大概率有），这是**to B 场景的核心能力**：把「产品更新」只发给老客户，把「招聘」只发给候选客户。
- **成本**：**2.5 人日**（标签表 + 名片管理端维护 UI + 发布时选择器 + 查询过滤）。**前置依赖：客户/访客身份体系是否存在**，需先确认。
- **前置风险**：如果我们的访客**根本不是可识别的身份**（无 openid 无关系），这一项无法落地，只能降级为「按内容分类而非按人分类」。

### ③ 定时发布（用户手动选未来时间）
- **参考**：公众号 —— 可设「5 分钟至 7 天内」任意时刻，**必须管理员扫码确认**，定时任务在发送前可随时改内容/改时间/取消，且**未发送不占群发次数**；小红书 —— 需创作中心/专业号，定时稿存在草稿箱里、发布前可改可取消；知乎 —— 发布页右上角小箭头选「定时发布」设日期时间；LinkedIn —— Clock 图标选日期时间。
- **适配度**：✅ **这就是本轮要的那个能力** —— 用户手动挑一个未来时间点，到点自动放出来。**不是**后台批量调度。
- **成本**：**2 人日**（`scheduled_at` 字段 + 状态 `pending` → 发布时改 `active`）。关键：**列表查询必须按 `created_at <= now AND status='active'` 过滤**，否则会出现「还没到时间的动态出现在名片页」。
- **必做的交互细节**（抄小红书/公众号）：定时稿在到点前**可改可取消**；未到点不占用任何配额。
  来源：<https://developers.weixin.qq.com/community/develop/doc/0004a6752c0a582053c3af7c266c00>、<https://www.17golang.com/article/527400.html>

### ④ 草稿箱
- **参考**：小红书草稿箱（定时稿也在里面）；微博草稿（**仅存本地、换手机即失、不云同步**）；企微「企业统一创建内容 → 通知成员确认发表」本质是企业侧草稿。
- **适配度**：✅ 高。小程序是**移动端场景**，用户填一半被打断（接电话、切微信）的概率远高于 PC。
- **成本**：**1.5 人日**（草稿表 + 「存草稿」按钮 + 草稿列表 + 续写）。**草稿应存服务端而非 localStorage** —— 这正是微博踩过的坑（换手机就没了），我们有服务端，没有理由不存。
- **取舍**：一期可先不做独立草稿箱，而是**发布弹窗关闭时自动存草稿 + 下次进入弹窗自动续写**，成本 0.5 人日，效果拿到 80%。

### ⑤ 发布后编辑
- **参考**：知乎**不限编辑次数，但每次修改保留编辑记录，他人可查历史版本**；小红书可改文字/标签/封面/可见范围但**不可换原图原视频**；朋友圈可改可见范围。
- **适配度**：✅ 需求明确（写错一个字不至于要删了重发）。
- **成本**：**1 人日**（`PUT /dynamics/:id`，需校验只能改自己的）。
- **建议**：**首期不做「编辑记录」**（那是知乎式的公共可查历史，对名片场景是隐私负担），只做「能改」。

### ⑥ 删除
- **参考**：全平台共识，且是不可逆的。企微成员可删已发表内容，管理员删不了成员发的。
- **适配度**：✅ 必备。名片场景下「误发一条」比「删掉一条」的损失小得多。
- **成本**：**0.5 人日**（`DELETE /dynamics/:id`，软删 `status='deleted'`）。⚠️ 列表查询已带 `status='active'` 过滤（`card.js:548`），软删可直接复用现有逻辑；硬删要注意 likes/comments 孤儿行。

### ⑦ 转发一条动态（发给微信好友 / 分享到朋友圈）
- **是什么**：动态详情页配 `onShareAppMessage` + `onShareTimeline`，访客能把这条动态转发出去，形成二次传播。
- **参考**：`onShareTimeline` 支持自定义 `title` / `query` / `imageUrl`。
- **适配度**：✅✅ **这是「一条动态」的天然传播属性，我们现在完全没做**。
- **成本**：**1.5 人日**（新建动态详情页 + 分享配置 + 卡片图自动裁切服务）。
- **⚠️ 微信平台硬限制（必须提前知道，否则会白做）**：
  - `imageUrl` **必须是 HTTPS 网络地址**，本地路径/相对路径无效；不传则微信自动截页面顶部，截图时机不对就会截到灰屏
  - 分享图**比例 5:4（好友）/ 1:1（朋友圈）**，且有体积限制，超了直接失败
  - `title` 朋友圈最多 **48 字符**，超长截断且不换行
  - **朋友圈卡片不支持 desc/摘要字段**，标题就是全部文案
  - 从朋友圈点开进入的是**单页模式**：无登录态（`wx.login` 不可用）、**不允许跳转到其它页面**、tabBar 不渲染、部分交互组件会弹 toast「请前往小程序使用完整服务」
  - 分享到朋友圈**只能从右上角菜单触发**，页面内自定义按钮无法触发；且必须先配好 `onShareAppMessage` 才显示菜单项
  - `imageUrl` 不带 token 和动态 query，否则卡片降级为纯文字链接
  - 来源：<https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/share-timeline.html>、<https://www.linkedin.com/help/lms/answer/a522902>（字段定义）、<https://m.php.cn/faq/2415962.html>（限制清单）

### ⑧ 生成海报
- **是什么**：把一条动态渲染成图片（内容 + 作者头像昵称 + 小程序码），存到相册，用户手动发朋友圈。
- **参考**：小程序 canvas 生成海报的通行做法 + `scene` 参数做渠道追踪。
- **适配度**：🔶 中。**价值不如⑦**——海报是「用户自己费劲做的替代方案」，而且第一批内容大概率没人愿意做。
- **成本**：**2 人日**（canvas 绘制 + 小程序码带 scene + 保存相册授权 + 各种踩坑：需设 `ctx.scale(dpr,dpr)` 否则图发虚、网络图必须先 `downloadFile` 否则静默不绘制、二维码留白不足扫不出、绘制尺寸要按设计稿 2 倍）。
- **建议**：**放到二期或不做**。先把⑦（转发）做掉，传播路径更短。

## 5. 推荐落地组合

### 5.1 第一期必做（性价比高，合计 ~7.5 人日）

| 项 | 内容 | 成本 | 理由 |
|----|------|------|------|
| 1 | **标题 title** | 0.5 | 字段已在库、INSERT 已写入，只差一个 input。**不花代价，白捡一个能力** |
| 2 | **链接预览卡片 + 小程序卡片** | 2.0 | 名片场景的核心转化能力（动态 → 名片某页）。企微已有成熟的 `link` 四字段结构可抄 |
| 3 | **名片模块引用** | 1.5 | **差异化，竞品抄不了**。用户零成本，转化路径最短 |
| 4 | **可见范围三态**（公开/仅自己/仅登录可见） | 1.5 | 从 bool 升级为枚举。⚠️ 需同步改 `card.js:548`、`card.js:2116` 和 4 处测试 |
| 5 | **定时发布**（用户手动选时间） | 2.0 | 用户明确诉求。抄公众号/小红书交互：到点前可改可取消 |
| 6 | **编辑 + 删除** | 1.5 | 内容发布的兜底。没有它，任何新形态（定时/卡片）都会放大误发的后果 |

**顺序建议**：1 → 4（先把地基的地基改对）→ 2+3（内容形态）→ 5（时间维度）→ 6（兜底）。

### 5.2 第二期（合计 ~10 人日）

| 项 | 成本 | 理由 |
|----|------|------|
| 视频 | 3 | 价值高但成本高；建议先统计现有动态里「纯文字」占比，验证图片到底够不够 |
| 动态转发（`onShareTimeline`） | 1.5 | 传播杠杆最大，但强依赖动态详情页（可与②③的卡片页合并做） |
| 话题标签 | 2 | 需要公域流量才有意义，可以观察后再上 |
| @提及 | 2.5 | 通知链路（订阅消息逐次授权）是主要成本 |
| 客户分组 | 2.5 | **前置依赖：需先确认访客是否有可识别身份**。若没有，此项降级为「按内容分类可见」而非「按人」 |
| 投票 | 2.5 | to B 场景（客户满意度/意向调研）意外合适，可与⑤客户分组打包做 |
| 草稿箱（独立入口） | 1.5 | 一期先用「关闭弹窗自动存草稿」的轻量版；独立列表页可延后 |
| 位置 | 1 | 先做成「名片地址一键带入」而非独立选择器，成本可压到 0.5 |

### 5.3 暂不做（明确理由）

| 项 | 不做的理由 |
|----|-----------|
| **文件 / PDF 附件** | 企业 IM 场景需求，不是名片场景需求。访客看名片不需要收文件，小程序内预览 PDF 体验也差 |
| **「撤回」语义** | 全平台共识是「已发不可撤回」（企微 API 文档明说、公众号立即群发不可撤、知乎只有删除）。并且名片是**主页性质**，撤回等于主页开个洞，比删掉更糟。**做「编辑 + 删除」就够** |
| **「不给谁看」名单型黑名单** | 需要用户有「好友关系」，我们只有「访客」。访客是谁我们不知道，屏蔽无意义 |
| **独立长文章编辑器** | LinkedIn 之所以有（超 3000 字符引导写 Article），是因为它有公域推荐流量。我们没有，且写长文的名片主人极少 |
| **动态互相评论 / @回复楼中楼** | 已有评论一/二级评论即可。楼中楼在小程序里性能差、体验重 |
| **自动发布 / 定时任务调度 / 批量发帖机器人** | 用户已明确否掉。本轮全部能力都是「用户手动一次发布」 |
| **第三方服务商视角的批量运营（企业统一创建内容 → 成员确认发表）** | 企微那套是**给企业管理员**用的，我们是**给名片主人自己用的**。我们没有「成员」概念，抄过来没有使用场景 |
| **海报生成** | 是「转发」能力的低效替代品。优先级应低于⑦，且首批用户不会用 |

## 6. 风险与坑

### 6.1 微信平台限制（最容易白做的部分）

| 风险 | 详情 | 应对 |
|------|------|------|
| **分享卡片图片限制** | `imageUrl` 必须 HTTPS 可直访；好友 5:4、朋友圈 1:1；有体积上限，超了直接失败；不传则微信自动截页面顶部（可能截到 loading/灰屏/评论区） | 后端统一加一个「分享图裁切 + 压缩」服务，前端只管传原图 URL |
| **朋友圈卡片无摘要字段** | `onShareTimeline` 不支持 desc，标题就是全部文案，且 48 字符截断不换行 | 标题文案要短。**建议动态的 title 就是为转发卡片设计的** |
| **单页模式限制** | 从朋友圈打开进入单页模式：无登录态、不允许跳其它页面、tabBar 不渲染、部分组件点击弹 toast | 动态详情页必须为单页模式做适配（判断 `scene === 1154`）。不做的话分享出去就是半残页 |
| **只有右上角菜单能分享到朋友圈** | 页面内自定义按钮只能触发 `onShareAppMessage`（好友/群），对朋友圈无效。且必须先定义了 `onShareAppMessage` 才显示菜单项 | 不要设计「点按钮分享到朋友圈」的交互 |
| **web-view 域名白名单** | 不在小程序后台「业务域名」里的 URL，web-view 也打不开 | 链接卡片**优先只支持跳自家内页**；必须支持外链时走复制链接兜底 |
| **视频号挂载小程序的资格门槛（参考警示）** | 要求小程序已认证 + 已备案 + 已上架 + 主体一致 + 类目在开放列表 + 30 天日活达标；单视频号最多关联 10 个小程序 | 我们**不要走「动态挂载到视频号」这条路**，太重。我们只要「动态里放一张指向自家小程序页的卡片」，不依赖任何平台挂载能力 |

### 6.2 内容审核风险（一期就要处理，不能拖）

| 风险 | 详情 |
|------|------|
| **内容安全 API 是报备审核的硬门槛** | 微信明确：**提供 UGC 自定义发布内容功能的小程序，必须在小程序内接入官方「内容安全检测接口」校验文本/图片**，未接入官方接口的小程序**无法通过代码审核** |
| 配额限制 | `msgSecCheck`：单 appId **4000 次/分钟、200 万次/天**；`mediaCheckAsync`：单 appId **2000 次/分钟、20 万次/天**；传入的 openid 须在 **120 分钟内**访问过小程序，否则报 61010 |
| **新增内容形态会放大审核面** | 每加一种形态（视频/卡片/位置/投票），审核对象就多一类。视频走 `mediaCheckAsync` 是**异步**的，需要处理「先发布后回调判定」的中间态 |
| 人工兜底 | 官方接口对部分违规内容识别效果有限，**必须保留人工复审入口**。企微要求敏感词过滤 + 人工复审双保险 |

来源：<https://fuwu.weixin.qq.com/community/operate/doc/00002a6a0b8d98a965993666a51001>、<https://developers.weixin.qq.com/community/develop/doc/0006c4e249430083561f47d1251409>

### 6.3 工程风险

| 风险 | 说明 |
|------|------|
| **改 visibility 会炸现有链路** | `card.js:548` 的 `d.visibility='public'` 过滤、`:2116` 的 `visibility === 'private' ? 'private' : 'public'` 归一、以及 `server/test/card-voice-dynamic.test.js:64,70,80,93` 四处断言都要同步改。**升枚举不是加个 case 了事** |
| **定时发布会漏数据** | 现有所有列表查询都是 `ORDER BY created_at`，没有时间条件。加 `scheduled_at` 后必须统一加 `status='active' AND (scheduled_at IS NULL OR scheduled_at <= now)`。**漏一处就提前曝光** |
| **卡片跳转与单页模式冲突** | 链接卡片在小程序内跳自家内页 → 正常；但如果这条动态是被分享到朋友圈、从单页模式打开的，**跳转会直接被禁**。需要做场景值判断 |
| **性能：9 图 + 卡片 + 视频的列表渲染** | 名片页动态列表是公域被访问最频繁的页面。加了 title / 卡片 / 封面图后单条数据体积变大。建议：卡片和视频**只存关键字段，列表页不做详情渲染**，点进详情页再加载完整数据 |
| **草稿的存储位置** | 微博草稿只存本地、换手机即失——不要抄这个坑。我们有服务端，草稿存服务端 |
| **动态删除的孤儿数据** | 软删（`status='deleted'`）最安全，现有查询已带 `status='active'`，可直接复用。但要注意「我赞过/我评论过」这类历史记录是否要一并隐藏 |

---

## 7. 一句话结论

用户说的「太简单」有两层，答案不是同一条路：
- **内容形态层** —— 最该补的不是视频，是**链接卡片 + 名片模块引用**（我们独有的差异化）。因为名片场景的价值在转化，链接比图片能多带一整步转化。
- **发布方式层** —— 最该补的不是定时，是**可见范围从 bool 升到枚举**。定时发布是显性诉求（用户能感知到），可见范围是隐性刚需（发错人比发不出去更可怕），两者都要做，但可见范围是**必须先改的地基**。
- **不要学过头** —— 文件附件、撤回、名单型黑名单、独立长文、批量运营，这些都是社交平台/企业 IM 的形态，我们不是。
