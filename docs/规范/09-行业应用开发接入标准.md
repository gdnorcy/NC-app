# 行业应用开发接入标准（360全景 / 零壹系统云）

> 适用范围：外部开发者（含其他 AI 系统）为本系统开发**应用中心的一级行业应用**——与「智能名片 / 商城 / 超级表单 / 360全景」同级的新应用（例如：防伪溯源）。本系统负责人收到源码后按本标准的「交付清单」逐项验收并整合入库。
>
> 一句话原则：**一个行业应用 = 在应用中心注册 + 租户可开通 + 租户后台管理页 + C 端页面 + 独立数据模型**，代码增量合并进 monorepo，必须遵守仓库既有铁律，禁止自造目录、自造数据源、自造鉴权。

---

## 1. 系统架构总览（必须先读）

```
零壹系统云（monorepo，npm workspaces）
├── server/          # 后端：Node.js + Express + SQLite(better-sqlite3)
│   └── src/
│       ├── app.js           # 所有路由挂载点（新增路由必须在这里注册）
│       ├── db.js            # 建表 + 迁移（新增表必须在这里追加，幂等）
│       ├── config.js        # 端口/上传/DB路径等配置
│       ├── routes/          # 路由工厂 createXxxRouter(db) 按业务分文件
│       ├── services/        # 业务服务层（可选，复杂逻辑放这里）
│       └── data/            # SQLite 库文件 panorama.db（git 忽略，不入库）
├── web-app/         # C 端（H5 + 微信小程序双端）：uni-app + Vue3
│   └── src/
│       ├── pages/           # 页面目录（card/cardMain/mall/panorama/superForm/share/live/viewer）
│       ├── pages.json       # 页面注册 + 分包配置
│       ├── components/      # 公共组件（SIcon/TplThumb/…）
│       ├── utils/           # API 封装（cardApi.js 等，token 管理）
│       └── static/          # 静态资源
└── web-admin/       # 管理后台（平台总后台 + 租户后台双入口）：Vue3 + Vite
    └── src/
        ├── main-admin.js        # 平台总后台入口（/admin）
        ├── main-customer.js     # 租户后台入口（/customer）
        ├── router/admin.js      # 总后台路由
        ├── router/customer.js   # 租户后台路由
        └── views/
            ├── admin/           # 总后台页面（AppCenter.vue 应用中心等）
            └── customer/        # 租户后台页面（apps/<应用>/ 下）
```

**三个包的关系**：后端一个库服务所有端；C 端是用户（名片访客/买家/表单填写者）看到的小程序/H5；管理后台是租户（商家/企业）配置业务的后台。**一个行业应用（如防伪溯源）= 应用中心可开通的一级应用**，由以下六件套组成（对照智能名片/商城落地方式）：

| # | 组成 | 落地位置 |
|---|---|---|
| 1 | **应用注册** | `apps` 表 INSERT（code/name/icon/category/sort_order/enabled）→ 应用中心（AppCenter.vue）展示 |
| 2 | **租户开通** | `solutions`（组合包）+ `projects.solutions` 开通 + `tenant.js hasSolution` 判定；`solution_apps` 建立应用-方案关联 |
| 3 | **权限点** | `app_menus` 注册菜单权限（app_id 关联）+ `solution_permissions` 挂授权 |
| 4 | **租户管理页** | `web-admin/src/views/customer/apps/<code>/` + `router/customer.js` 路由 + 应用内 Tab（CardTabs 模式） |
| 5 | **C 端页面** | `web-app/src/pages/<code>/` + `pages.json` 分包注册（H5 + 微信小程序同源） |
| 6 | **数据模型** | 业务表（必带 `tenant_id`）+ 后端路由 `/api/<code>` 挂载 |

缺任一环，应用在应用中心/租户侧就"看得见开不通"或"开得通用不了"。**总后台配置归属铁律**：行业应用配置放应用中心 → 该应用 → 管理（`/apps-center/:code/manage`），禁止进平台公共区。

## 2. 技术栈与运行环境（铁律）

| 项 | 约定 |
|---|---|
| 后端 | Node.js（>=18），Express，better-sqlite3，JWT(jsonwebtoken) |
| C 端 | uni-app + Vue3 + Vite，一套代码出 H5 与微信小程序 |
| 管理后台 | Vue3 + Vite + Element Plus（ElMessage/ElMessageBox），Pinia |
| 数据库 | SQLite 单文件（server/data/panorama.db），**git 忽略**，数据变更走迁移 SQL |
| 脚本 | python3（本项目脚本均用 python3，勿用 python2） |
| 包管理 | 根目录 `npm run xxx`（workspaces 名：server / web-app / web-admin） |
| 源码风格 | ESM（`import` / `export`），**禁止 CJS `require()` 混用**（本仓库 `"type": "module"`） |

**SQLite 方言红线（最常踩）**：SQLite **不支持** MySQL 的列级 `COMMENT '...'` 语法，写进去启动即报 `near "COMMENT": syntax error`；同理禁 `ENGINE=` / `AUTO_INCREMENT=` / `ON UPDATE CURRENT_TIMESTAMP` / `TINYINT` / `DATETIME` 等专有类型与语法。字段说明一律写进 SQL 注释 `-- xxx`。

**常用命令**：
```bash
npm run build:admin      # 构建管理后台（直出 server/public/admin，无需同步）
npm run build:mobile     # 构建 C 端 H5（自动同步 server/public/card 与 mall）
npm run build:mp-weixin -w web-app   # 构建微信小程序（产物 web-app/dist/build/mp-weixin）
npm run verify           # 验证构建产物完整性
npm test                 # 后端测试（全量用串行：node --test --test-concurrency=1 server/test/*.test.js）
npm run test:frontend    # 前端单元测试
```

## 3. 后端接入标准

### 3.1 数据层（db.js 迁移）
- 所有建表/迁移**只能**写在 `server/src/db.js` 的 `migrate()` 函数**尾部**（幂等 `IF NOT EXISTS` / `colExists` 包裹），**禁止**插进已有 SQL 字符串中间（会语法错误导致启动即崩）。
- 表名/字段名：小写 + 下划线；业务表**必须有 `tenant_id INTEGER NOT NULL`**（多租户隔离铁律，见 §6）。
- 平台级数据（模板/套餐/公共配置）`tenant_id = 0`。
- 变更已上线表结构 → 额外产出迁移 SQL 文件放 `server/data/migrate-<日期>-<主题>.sql`（git 忽略），并**在交付清单中附执行说明**。
- 🔴 **交付的 `.sql` 文件不会被自动执行**：SQLite 无外部迁移执行器，整合方是把它**逐条搬进 `db.js` 的 `migrate()` 尾部**。因此交付 SQL 必须满足：①**纯 SQLite 方言**（禁 MySQL `COMMENT` 等专有语法，见 §2）②**可整段 `db.exec()` 执行**③**幂等**（`IF NOT EXISTS` / `INSERT OR IGNORE`）。
- 🔴 **迁移必须落到 `db.js` 而非只给 SQL 文件**：「交了一份 .sql」不等于「迁移已生效」；整合验收以 `db.js` 里能读到新表 + `schema_marks` 留痕为准。

### 3.2 路由（routes/ 工厂模式）
- 每个业务一个文件 `server/src/routes/xxx.js`，**默认导出工厂函数** `export function createXxxRouter(db)`。
- 在 `server/src/app.js` 挂载，路径约定：平台/公共用 `/api/<业务>`，需登录的租户接口套 `requireAuth`，C 端公开接口不套（参考现有：`/api/card`、`/api/mall`、`/api/super-form` 挂载方式）。
- **响应格式**：成功 `res.json({ ...业务字段 })`；失败 `res.status(4xx/5xx).json({ error: '中文错误信息' })`。
- **鉴权**：统一从 `req.user` 取身份（JWT 已由中间件解析）；**禁止自建 token/自定义中间件**（oauth 等系统级能力除外，需先与负责人确认）。
- 🔴 **租户标识字段口径 = `req.user.customerId`**：本项目 `requireAuth` 解析出的 JWT 载荷字段是 `customerId`（`server/src/auth.js`），**不存在 `req.user.tenant_id` / `req.user.tenantId`**。写错的后果是 `tenantId` 恒为 `0` → 所有带 `tenant_id = ?` 的查询查不到数据、或直接 401。正确写法：`Number(req.user?.customerId ?? 0)`。
- 🔴 **公开端与租户后台端分两处挂载**：C 端公开接口挂 `/api/<code>/public`（不套鉴权或套宽松鉴权）；租户后台接口挂 `/api/customer/<code>`（套 `requireAuth`）—— 后者与后台 `customerApiCall` 的 baseURL `/api/customer` 对齐。若把后台接口挂在 `/api/<code>/admin`，后台页须自行拼 `customerApiCall` 之外的路径，易漏 token 注入。

### 3.3 应用注册与租户开通（应用中心）
- 新增应用必须在 `server/src/db.js` 的迁移中注册：
  `INSERT OR IGNORE INTO apps (code, name, description, icon, category, sort_order, enabled) VALUES ('<code>', '<名称>', '<描述>', '<图标key>', '<分组>', <排序>, 1)`
- `code` 全小写连字符（如 `super-form`、`trace`），全局唯一；`category` 为应用中心分组名（基础功能/高级功能/全端渠道…）。
- **租户开通链路（照抄智能名片/商城落地方式）**：`solutions` 组合包授权（`solution_apps` 关联 apps.id）+ `projects.solutions` 存开通码 + `tenant.js hasSolution` 判定接口可用；演示方案（code='demo'）自动纳入全部应用。
- **权限点**：在 `app_menus` 注册该应用菜单（module/module_label/key/label/sort_order，`UNIQUE(app_id, key)`），并挂进对应 `solution_permissions`；分配权限弹窗按 `app_menus.app_id → apps.id` 分组展示。
- 🔴 **应用-方案关联必须给可执行 SQL，不能只给注释示例**：交付物里常见 `solution_apps` 只写一行注释「开通关系由目标平台补」→ 整合后应用中心看得到、租户开不了。正确写法是给出实际的 `INSERT OR IGNORE INTO solution_apps (solution_id, app_id) SELECT id, (SELECT id FROM apps WHERE code='<code>') FROM solutions WHERE code IN ('demo', '<目标方案>')`（`demo` 方案自动纳入全部应用）。
- 🔴 **`app_menus.app_id` 必须用子查询取 `apps.id`**，不能硬编码数字 id（不同库的自增 id 不一致，写死会挂到别的应用上）：`INSERT OR IGNORE INTO app_menus (app_id, module, module_label, "key", label, sort_order) SELECT id, '<module>', '<模块名>', '<key>', '<标签>', <排序> FROM apps WHERE code='<code>'`。
- **总后台配置项归属铁律**：行业应用相关配置**必须放在应用中心 → 该应用 → 管理**，**禁止**塞进平台公共区；只有全端通用的配置才放公共区（平台默认配置/全端渠道保持原位置）。

### 3.4 API 规范（对 C 端与后台一视同仁）
- REST 语义：GET 查询 / POST 创建 / PUT 更新 / DELETE 删除；URL 名词复数 + id（`/api/xxx/items/:id`）。
- 列表接口统一分页参数 `page` / `pageSize`（默认 1 / 20），响应 `{ list, total }`。
- 时间统一 ISO 字符串；金额单位**分**（整数），前端展示时转换。
- 幂等：创建类接口可接受客户端幂等键或在 SQL 层用唯一约束防重。
- 上传：文件走 `/uploads` 静态托管（config.uploadsDir），返回 `/uploads/<file>` 相对路径。

## 4. C 端接入标准（web-app，H5 + 微信小程序）

### 4.1 页面注册与分包
- 新增页面在 `web-app/src/pages.json` 注册；**主包只放启动必需页**，业务页一律进分包（现有分包：panorama / mall / card / superForm…），分包单包 < 2MB。
- 页面路径用 `pages/<业务>/<页面>`（与现有结构一致），**禁止**新建顶层目录（如 `pages/mynewapp/` 应改为并入既有分包或新增分包 root）。
- 🔴 **同一页面禁止同时在 `pages` 与 `subPackages` 里各注册一次**：路径重复会被 uni 编译成两个同名页面（路由指向不确定 / 产物重复膨胀）。交付的 `pages.json` 片段若两处都有，必须删掉主包那一份，只留分包注册。
- 🔴 **`pages.json` 是整文件替换，不是片段合并**：交付方应交付**可直接替换的完整 `pages.json`**，或在片段里明确标注「合并到 subPackages 数组的哪一项下」。只给一个孤立的 `pages.json.snippet.json` 而不说合并位置，整合时极易漏项。

### 4.2 样式铁律（小程序端尤其重要）
- **CSS 变量必须挂 `:root, page` 双选择器**（`token.scss`）；只挂 `:root` 时小程序所有 `var(--primary)` 失效 → 页面颜色全丢。
- 图标一律用 `SIcon` 组件（内部 `background-image` + `background-size:contain` 实现）；**禁止** `<image>` 渲染无尺寸 SVG（小程序按固有尺寸撑爆布局导致文字竖排）。
- **禁止 `<i>/<b>/<small>` 等 HTML 标签选择器做样式**（小程序端编译成无标签 view，选择器失配）；一律 `<text class="xxx">` + 类选择器。
- SCSS 规则必须块级闭合；前块未 `}` 闭合会误编译成后代选择器 → 样式静默全丢。
- 单位用 rpx；颜色取 `token.scss` 变量，不硬编码。

### 4.3 装修组件（设计中心）
- 若插件需要「页面装修」能力：组件**必须注册进 `componentRegistry` 数组**（组件库分组/搜索/计数都读它），通用样式 key 进 `commonStyleSchema`；**新增组件后必须跑** `python3 scripts/check-mall-components.py`（有输出不许说完成）与 `node scripts/check-editor-components.mjs`（数据组件无真实数据源/占位假数据直接构建失败）。
- 数据类组件**必须在编辑器内拉真实数据**（对齐 C 端 DesignPage 的参数规则），禁止占位假数据交付。
- 复刻对标（人人商城/EweiShop/菜鸟云等）时**必须先读 `docs/复刻检查清单.md` 逐条打勾**，并对标截图目录齐全（`docs/对标截图/<组件名>/`）才许开工。

### 4.4 API 调用
- 复用 `web-app/src/utils/` 下的 API 封装（cardApi.js 等），token 存 `localStorage.<业务>_token`（card_token / customer_token 等），**禁止页面内散写 fetch 和 token**。
- H5 走同源相对路径（/api/xxx）；小程序端 API 基址为配置文件中的服务器地址（局域网 IP + 端口，发布时替换域名）。
- 🔴 **基址必须来自 `utils/apiBase.js`，禁止在业务封装里硬编码 `/api/xxx`**：本项目 API 基址单一来源是 `web-app/src/utils/apiBase.js` 的 `MP_API_BASE` / `H5_API_BASE` / `IS_MP_WEIXIN`（构建期由 `.env` 注入，MP 端必须是完整 URL）。业务封装应基于 `createApiClient(baseURL, options)` 封装（见 `utils/apiClient.js`），由基址 + `/api/<code>` 拼出端点。写死 `/api/trace` 会导致 H5 端在非同源部署（独立域名/端口）下 404，且小程序端缺 host。
- 🔴 **API 基址读取有 MP 编译红线**：`import.meta.env` 只能直接访问，**严禁** `typeof import.meta !== 'undefined' && import.meta.env` 防御式写法——vite 在 MP（CJS 输出）下会把裸 `import.meta` 垫成 `require("url")`，微信运行时无此内置模块 → app.js 启动即崩（连全部页面未注册）。且运行时探测（`typeof window === 'undefined' && typeof wx !== 'undefined'`）优于条件编译，条件编译在 vitest/node 直跑源码时会双分支留存导致重复声明。
- 🔴 **封装里每个方法都必须有后端真实路由（死接口零容忍）**：交付的 `traceApi.js` 曾出现 `traceHistory()` 调 `/public/history` 而后端并无该路由 → 运行时必 404。整合前应逐个方法反查 `routes/xxx.js` 是否有对应端点，**前端封装与后端路由必须一一对齐**（可在交付清单里列出「方法 ↔ 路由」对照表）。

## 5. 租户管理后台接入标准（web-admin）

### 5.1 页面与路由
- 租户后台页面放 `views/customer/apps/<应用>/`；在 `router/customer.js` 注册路由。
- **应用内业务页统一收敛在应用内 Tab 导航（CardTabs 模式）**；**侧边栏禁止新增应用级菜单**，选项卡栏常驻。
- 后台组件统一 Element Plus；布局/菜单/表格/表单遵循 `docs/规范/07-UI设计.md`（飞书/Ant Design Pro 审美、令牌化）。

### 5.2 API 调用规范
- `adminApi` baseURL=`/api/admin`、`customerApiCall` baseURL=`/api/customer`，**调用时 URL 不得重复前缀**。
- 响应拦截器已解包，组件内直接取 `res.xxx`，**禁止 `res.data.xxx`**；`catch(e)` 直接 `ElMessage.error(e)`，禁止 `e.response?.data?.error`。
- 🔴 **禁止裸 `fetch`（含禁止自建 request 封装）**：交付的后台页若直接 `fetch('/api/trace/admin/...')`，则**不会带上 `customer_token`**，接口一律 401，且错误处理方式也与项目约定不符。必须走 `customerApiCall`（`web-admin/src/api/index.js`），它已封装 token 注入、baseURL、响应解包与统一错误提示。
- 🔴 **后台页必须挂 `AppPageHeader`**（页头组件），与既有租户后台页保持一致的标题/面包屑结构；缺失会让页面在导航体系里显得外挂。

### 5.3 权限接入（三处同步，必读）
- 侧边栏渲染源 = `CustomerLayout.vue` 写死菜单（非动态）；改菜单必须三处同步：`CustomerLayout.vue`（渲染）+ `menuPermissions.js`（守卫）+ `menuPermissions.test.js`（断言）。
- 分配权限弹窗按应用分组依据 = `app_menus.app_id → apps.id`（**禁止用 module 匹配 app code**）；`menu_key` 含冒号前缀（如 `card:overview`），前端勾选标识 `${app_code}:${menu_key}`，切分按第一个冒号。
- 新应用权限点：在 `app_menus` 注册（`app_id + module + module_label + key + label + sort_order`），并把 menu_key 挂到对应 `solution_permissions`。

## 6. 鉴权与多租户（红线）

- 平台账号：`accounts`（一人一号，跨租户复用）+ `tenant_members`（租户侧属性）。
- 登录：`POST /api/auth/login`（`{username|phone, password}`）；C 端业务有独立登录链路（如名片 `wx-login`），沿用既有模式，**禁止自创账号体系**。
- **所有业务数据查询必须带 tenant_id 过滤**（`WHERE tenant_id = ?`），读租户配置从 `projects.config` / 应用配置表取。平台级数据 tenant_id=0。
- 🔴 **tenant_id 的来源只有一个：JWT 载荷的 `customerId`**。`requireAuth` 解析后 `req.user = { id, username, role, customerId }`（`server/src/auth.js`）。**禁止**从请求体/查询串取 tenant_id（越权）；**禁止**使用 `req.user.tenant_id` / `req.user.tenantId`（不存在）。C 端公开接口若需定位租户，走 code/serial 等业务键反查，或用租户侧配置的公开 token 机制，不接受前端直传 tenant_id。
- 最后管理员保护、成员/角色权限加固等见 `docs/规范/01-账号权限.md`（涉及权限改动必须先读）。

## 7. 构建 / 测试 / 交付标准

### 7.1 每次改动后的铁律
- **每次改动后创建 git commit**（commit message 前缀约定：`feat:` / `fix:` / `refactor:` / `docs:` / `chore:`，例 `feat(card): 模板市场替换11套新皮肤`）。
- **每次改动后编写/更新测试**，交付前全部测试通过（后端串行全量、前端 vitest；新增纯函数必须配测试）。
- 构建验证：`npm run build:admin` + `npm run build:mobile`（或小程序 `build:mp-weixin`）+ `npm run verify`。
- 🔴 **「测试通过」≠「功能可用」**：交付的应用必须额外验证「应用中心看得到 / 租户开得通 / C 端页面进得去」三条链路，缺一即为未完成。
- 🔔 **后端全量测试可能 OOM（exit 137）**：78 个测试文件一次性 `node --test` 会被内存杀掉。分 4 批（每批 ~20 文件）串行跑：`ls test/*.test.js | awk '{n=int((NR-1)/20)+1; print > ("/tmp/srv-b" n ".txt")}'`，再 `node --test --test-concurrency=1 $(cat /tmp/srv-b1.txt | tr '\n' ' ')`。

### 7.2 交付物清单（整合验收打勾用）
提交给本系统负责人（通过 Git 仓库或源码包）时必须包含：

- [ ] **源码增量**：只交付本次应用涉及的新增/修改文件（可 patch/diff，或完整目录），**说明基于哪个 commit / 日期**。
- [ ] **文件清单与实际文件一一对应**：清单里列出的每个文件都必须在包内实际存在；包内实际存在的每个文件（**尤其 `services/` 下的工具模块**）也必须在清单里出现。常见漏项：算法/生成/奖励等 service 模块只出现在代码里、没写进清单 → 整合方按清单核销时看不到，只能靠通读全目录才能发现。交付清单应给出**逐文件路径 + 一行职责说明**。
- [ ] **数据迁移**：`migrate-<日期>-<主题>.sql`（新表/新列/种子数据），含回滚说明；**纯 SQLite 方言**、幂等、可整段执行。
- [ ] **应用注册与开通**：apps 表 INSERT 语句（code/name/icon/category/sort_order）+ app_menus 权限点清单（用子查询取 app_id）+ **可执行的 solution_apps 开通关联**（禁止只给注释示例）+ 租户开通方式说明。
- [ ] **路由挂载点**：`app.js` 新增挂载行（精确到行），并注明各段的鉴权要求（公开 / requireAuth）与租户标识取值方式。
- [ ] **页面注册**：pages.json **完整替换文件**或**明确标注合并位置**的片段；小程序分包体积说明（<2MB）；同一页面不得在主包与分包重复注册。
- [ ] **测试**：新增/修改的测试文件清单 + 运行结果（后端全量通过数、前端通过数）；新写的纯函数模块必须配测试（交付物里未在清单列出的 service 模块同样需要）。
- [ ] **构建验证**：`npm run build:admin` / `build:mobile`（或 `build:mp-weixin`）通过截图或日志。
- [ ] **真机/模拟器验收截图**：关键页面截图（C 端小程序模拟器截图级验收、后台页面截图）。
- [ ] **应用中心/租户开通截图**：应用中心出现新应用、租户后台开通后出现该应用及管理入口。
- [ ] **文档**：涉及对标复刻的附「复刻检查清单」打勾结果；涉及权限的附权限矩阵。
- [ ] **未完成项清单**：明确列出**哪些功能未做、为什么、影响范围**（交付物自带的 `delivery-checklist.md` 里勾选框为空的项，必须逐条说明是「待目标平台完成」还是「原系统未找到对应分支」）。**有未完成项不阻塞交付，但必须显式说明**——整合方与验收人需据此判断是否可上线。
- [ ] **平台适配说明**：凡是依赖目标平台能力的（微信支付/红包、短信、订单系统、IP 归属地、zip 打包等第三方依赖），列出「需要平台提供什么、缺了会怎样」。禁止把外部系统无法在本平台运行的模块伪装成已完成。

### 7.3 已知基线（整合方会检查）
- 服务器正确重启姿势（`lsof -nP -iTCP:3000` → kill → `cd server && nohup node src/index.js`）——整合方负责，插件方无需处理。
- 本地 curl 必须 `--noproxy '*' http://127.0.0.1:3000/api/health`（本机代理会 502）。
- 数据库/上传文件 git 忽略，不入库；入库的只有代码。
- `docs/规范/02-构建部署.md` 有全部踩坑记录（构建前必读）。

## 8. 协作分工流程（跨 AI 系统）

```
① 需求拆解（负责人）
   负责人把「新应用」（如防伪溯源）拆成模块级任务包，每包附：
   - 应用定义（code/name/icon/category/sort_order/分组归属）
   - 数据模型（表结构草案，必带 tenant_id）
   - API 契约（方法/路径/参数/响应示例）
   - 页面清单（应用中心卡片、租户开通、租户管理页、C 端页面）
   - 验收标准（对照 §7.2 清单）

② 外部开发（同事/其他 AI 系统）
   严格按本标准的 §2~§6 开发（重点是 §3.3 应用注册与开通链路），交付 §7.2 清单全部产物。

③ 源码整合（负责人，即本 AI）
   收到源码后：
   1. 核对交付清单逐项打勾（缺项先补，不静默跳过）
   2. 🔴 **先做「平台适配核对」再落代码**：按 §10 速查表逐条扫一遍交付物
      （SQL 方言 / tenant 字段口径 / 后台 fetch / pages 双注册 / API 基址 /
       死接口 / solution_apps / app_menus.app_id / 文件清单对账 / 硬编码色值），
      把问题**一次性列全**再改，避免"改一个发现一个"来回返工。
   3. 合并进 monorepo（server / web-app / web-admin 各自落位）
      —— 迁移必须**搬进 `db.js` 的 `migrate()` 尾部**，不能只留 .sql 文件
   4. 跑迁移 → 重启服务 → 全量测试（串行）→ 前端测试
   5. 构建三端产物 → 真机/模拟器验证（应用中心可见、租户开通可用、C 端可达）
   6. git commit + 通知用户验收

④ 验收（用户）
   负责人给结论 + 未决项清单（如：某页面需用户登录态实测）
```

**分工红线**：外部系统只产出「代码增量 + 文档」；**数据库、构建产物、部署、Git 合并、发布由本系统负责人统一执行**，避免多写者冲突。

**适配责任划分**：交付方按 §2~§6 开发并**自查 §10 速查表**；整合方仍须独立复核（外部交付物无法保证零偏差，漏审成本远高于复核成本）。发现不合规项时**先修适配、再谈上线**，不得「先合了再说」。

## 9. 快速上手示例（最小应用骨架）

以新增应用「防伪溯源」（code=`trace`）为例（仅示意，勿照抄到生产）：

```js
// server/src/routes/trace.js —— ESM（本仓库 "type": "module"），禁 require()
import express from 'express';

export function createTraceRouter(db) {
  const router = express.Router();

  // 公开段：C 端扫码校验等，无需登录
  router.get('/public/ping', (req, res) => res.json({ pong: true }));

  // 租户后台段：租户标识一律取 req.user.customerId（本项目无 tenant_id 字段）
  router.use('/admin', (req, res, next) => {
    const tenantId = Number(req.user?.customerId ?? 0);
    if (!tenantId) return res.status(401).json({ error: '未登录或无租户身份' });
    req.tenantId = tenantId;
    next();
  });
  router.get('/admin/ping', (req, res) => res.json({ pong: true, tenantId: req.tenantId }));

  return router;
}
```

## 10. 常见交付缺陷速查（整合方踩坑记录，反向约束交付方）

以下每条都是真实交付中出现过的缺陷，**在 §7.2 交付前必须自查**：

| # | 缺陷 | 后果 | 自查方法 |
|---|---|---|---|
| 1 | 迁移 SQL 含 MySQL `COMMENT '...'` | SQLite 报 `near "COMMENT": syntax error`，服务启动即崩 | 逐条 `db.exec()` 试跑 |
| 2 | 后端取 `req.user.tenant_id` / `tenantId` | 本项目无此字段 → tenantId 恒 0 → 查不到数据或 401 | grep `req.user.` 全部取值 |
| 3 | 后台页用裸 `fetch` | 不带 `customer_token` → 全部 401 | grep `fetch(` |
| 4 | `pages.json` 同一页面主包+分包双注册 | 编译出重名页面、路由不确定 | grep 页面路径在两处出现 |
| 5 | C 端 API 基址硬编码 `/api/xxx` | 非同源部署 404；MP 端缺 host | grep `'/api/` 字面量 |
| 6 | 前端封装调了后端不存在的路由（死接口） | 运行必 404 | 方法 ↔ 路由逐条对照 |
| 7 | `solution_apps` 只给注释示例 | 应用中心可见、租户开不了 | 找 `solution_apps` 是否为注释 |
| 8 | `app_menus.app_id` 硬编码数字 | 挂到别的应用上，权限错位 | 看是否用 `SELECT id FROM apps` |
| 9 | `service/` 下的工具模块未列入交付清单 | 整合方按清单核销时看不到，漏合或漏测 | 清单 vs 实际文件逐一对账 |
| 10 | 交付 `pages.json.snippet.json` 片段但不说合并位置 | 整合时漏注册 → 页面不可达 | 要求完整文件或标注位置 |
| 11 | 页面硬编码颜色 | 违反 token 口径，暗色/品牌色不跟随 | grep `#` 十六进制色值 |
| 12 | 依赖微信支付/短信/订单等外部能力却未声明 | 上线后功能不可用却被当成已完成 | 交付清单「平台适配说明」 |
