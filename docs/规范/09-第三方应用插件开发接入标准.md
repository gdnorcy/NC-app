# 第三方应用插件开发接入标准（360全景 / 零壹系统云）

> 适用范围：外部开发者（含其他 AI 系统）为「零壹系统云」编写**行业应用插件**（如：智能名片、商城、超级表单、360 全景、以及未来新增应用）时的开发与交付标准。本系统负责人收到源码后按本标准的「交付清单」逐项验收并整合入库。
>
> 一句话原则：**插件 = 一段可合并进 monorepo 的代码增量**（后端路由 + 数据迁移 + C 端页面 + 租户管理页 + 应用注册），必须遵守仓库既有铁律，禁止自造目录、自造数据源、自造鉴权。

---

## 1. 系统架构总览（必须先读）

```
零壹系统云（monorepo，npm workspaces）
├── server/          # 后端：Node.js + Express + SQLite(better-sqlite3)
│   └── src/
│       ├── app.js           # 所有路由挂载点（新增路由必须在这里注册）
│       ├── db.js            # 建表 + 迁移（新增表必须在这里追加，幂等）
│       ├── config.js        # 端口/上传/DB路径等配置
│       ├── routes/          # 路由工厂 createXxxRouter(db) 按业务分文件
│       ├── services/        # 业务服务层（可选，复杂逻辑放这里）
│       └── data/            # SQLite 库文件 panorama.db（git 忽略，不入库）
├── web-app/         # C 端（H5 + 微信小程序双端）：uni-app + Vue3
│   └── src/
│       ├── pages/           # 页面目录（card/cardMain/mall/panorama/superForm/share/live/viewer）
│       ├── pages.json       # 页面注册 + 分包配置
│       ├── components/      # 公共组件（SIcon/TplThumb/…）
│       ├── utils/           # API 封装（cardApi.js 等，token 管理）
│       └── static/          # 静态资源
└── web-admin/       # 管理后台（平台总后台 + 租户后台双入口）：Vue3 + Vite
    └── src/
        ├── main-admin.js        # 平台总后台入口（/admin）
        ├── main-customer.js     # 租户后台入口（/customer）
        ├── router/admin.js      # 总后台路由
        ├── router/customer.js   # 租户后台路由
        └── views/
            ├── admin/           # 总后台页面（AppCenter.vue 应用中心等）
            └── customer/        # 租户后台页面（apps/<应用>/ 下）
```

**三个包的关系**：后端一个库服务所有端；C 端是用户（名片访客/买家/表单填写者）看到的小程序/H5；管理后台是租户（商家/企业）配置业务的后台。**一个行业应用 = 在这三层各加一块 + 在 apps 表注册**。

## 2. 技术栈与运行环境（铁律）

| 项 | 约定 |
|---|---|
| 后端 | Node.js（>=18），Express，better-sqlite3，JWT(jsonwebtoken) |
| C 端 | uni-app + Vue3 + Vite，一套代码出 H5 与微信小程序 |
| 管理后台 | Vue3 + Vite + Element Plus（ElMessage/ElMessageBox），Pinia |
| 数据库 | SQLite 单文件（server/data/panorama.db），**git 忽略**，数据变更走迁移 SQL |
| 脚本 | python3（本项目脚本均用 python3，勿用 python2） |
| 包管理 | 根目录 `npm run xxx`（workspaces 名：server / web-app / web-admin） |

**常用命令**：
```bash
npm run build:admin      # 构建管理后台（直出 server/public/admin，无需同步）
npm run build:mobile     # 构建 C 端 H5（自动同步 server/public/card 与 mall）
npm run build:mp-weixin -w web-app   # 构建微信小程序（产物 web-app/dist/build/mp-weixin）
npm run verify           # 验证构建产物完整性
npm test                 # 后端测试（全量用串行：node --test --test-concurrency=1 server/test/*.test.js）
npm run test:frontend    # 前端单元测试
```

## 3. 后端接入标准

### 3.1 数据层（db.js 迁移）
- 所有建表/迁移**只能**写在 `server/src/db.js` 的 `migrate()` 函数**尾部**（幂等 `IF NOT EXISTS` / `colExists` 包裹），**禁止**插进已有 SQL 字符串中间（会语法错误导致启动即崩）。
- 表名/字段名：小写 + 下划线；业务表**必须有 `tenant_id INTEGER NOT NULL`**（多租户隔离铁律，见 §6）。
- 平台级数据（模板/套餐/公共配置）`tenant_id = 0`。
- 变更已上线表结构 → 额外产出迁移 SQL 文件放 `server/data/migrate-<日期>-<主题>.sql`（git 忽略），并**在交付清单中附执行说明**。

### 3.2 路由（routes/ 工厂模式）
- 每个业务一个文件 `server/src/routes/xxx.js`，**默认导出工厂函数** `export function createXxxRouter(db)`。
- 在 `server/src/app.js` 挂载，路径约定：平台/公共用 `/api/<业务>`，需登录的租户接口套 `requireAuth`，C 端公开接口不套（参考现有：`/api/card`、`/api/mall`、`/api/super-form` 挂载方式）。
- **响应格式**：成功 `res.json({ ...业务字段 })`；失败 `res.status(4xx/5xx).json({ error: '中文错误信息' })`。
- **鉴权**：统一从 `req.user` 取身份（JWT 已由中间件解析）；**禁止自建 token/自定义中间件**（oauth 等系统级能力除外，需先与负责人确认）。

### 3.3 应用注册（apps 表 + 应用中心）
- 新增应用必须在 `server/src/db.js` 的迁移中注册：
  `INSERT OR IGNORE INTO apps (code, name, description, icon, category, sort_order, enabled) VALUES ('<code>', '<名称>', '<描述>', '<图标key>', '<分组>', <排序>, 1)`
- `code` 全小写连字符（如 `super-form`），全局唯一；`category` 为应用中心分组名（基础功能/高级功能/全端渠道…）。
- **应用中心展示**由 apps 表驱动（`web-admin/src/views/admin/AppCenter.vue`），租户开通由 `solutions`（组合包）+ `tenant.js hasSolution` 判定，**新增应用必须同步**：开通关系（solution_apps / projects.solutions）、权限点（app_menus，见 §7.3）。
- **总后台配置项归属铁律**：行业应用相关配置**必须放在对应应用之下**（应用中心 → 该应用 → 管理），**禁止**塞进平台公共区；只有全端通用的配置才放公共区（平台默认配置/全端渠道保持原位置）。

### 3.4 API 规范（对 C 端与后台一视同仁）
- REST 语义：GET 查询 / POST 创建 / PUT 更新 / DELETE 删除；URL 名词复数 + id（`/api/xxx/items/:id`）。
- 列表接口统一分页参数 `page` / `pageSize`（默认 1 / 20），响应 `{ list, total }`。
- 时间统一 ISO 字符串；金额单位**分**（整数），前端展示时转换。
- 幂等：创建类接口可接受客户端幂等键或在 SQL 层用唯一约束防重。
- 上传：文件走 `/uploads` 静态托管（config.uploadsDir），返回 `/uploads/<file>` 相对路径。

## 4. C 端接入标准（web-app，H5 + 微信小程序）

### 4.1 页面注册与分包
- 新增页面在 `web-app/src/pages.json` 注册；**主包只放启动必需页**，业务页一律进分包（现有分包：panorama / mall / card / superForm…），分包单包 < 2MB。
- 页面路径用 `pages/<业务>/<页面>`（与现有结构一致），**禁止**新建顶层目录（如 `pages/mynewapp/` 应改为并入既有分包或新增分包 root）。

### 4.2 样式铁律（小程序端尤其重要）
- **CSS 变量必须挂 `:root, page` 双选择器**（`token.scss`）；只挂 `:root` 时小程序所有 `var(--primary)` 失效 → 页面颜色全丢。
- 图标一律用 `SIcon` 组件（内部 `background-image` + `background-size:contain` 实现）；**禁止** `<image>` 渲染无尺寸 SVG（小程序按固有尺寸撑爆布局导致文字竖排）。
- **禁止 `<i>/<b>/<small>` 等 HTML 标签选择器做样式**（小程序端编译成无标签 view，选择器失配）；一律 `<text class="xxx">` + 类选择器。
- SCSS 规则必须块级闭合；前块未 `}` 闭合会误编译成后代选择器 → 样式静默全丢。
- 单位用 rpx；颜色取 `token.scss` 变量，不硬编码。

### 4.3 装修组件（设计中心）
- 若插件需要「页面装修」能力：组件**必须注册进 `componentRegistry` 数组**（组件库分组/搜索/计数都读它），通用样式 key 进 `commonStyleSchema`；**新增组件后必须跑** `python3 scripts/check-mall-components.py`（有输出不许说完成）与 `node scripts/check-editor-components.mjs`（数据组件无真实数据源/占位假数据直接构建失败）。
- 数据类组件**必须在编辑器内拉真实数据**（对齐 C 端 DesignPage 的参数规则），禁止占位假数据交付。
- 复刻对标（人人商城/EweiShop/菜鸟云等）时**必须先读 `docs/复刻检查清单.md` 逐条打勾**，并对标截图目录齐全（`docs/对标截图/<组件名>/`）才许开工。

### 4.4 API 调用
- 复用 `web-app/src/utils/` 下的 API 封装（cardApi.js 等），token 存 `localStorage.<业务>_token`（card_token / customer_token 等），**禁止页面内散写 fetch 和 token**。
- H5 走同源相对路径（/api/xxx）；小程序端 API 基址为配置文件中的服务器地址（局域网 IP + 端口，发布时替换域名）。

## 5. 租户管理后台接入标准（web-admin）

### 5.1 页面与路由
- 租户后台页面放 `views/customer/apps/<应用>/`；在 `router/customer.js` 注册路由。
- **应用内业务页统一收敛在应用内 Tab 导航（CardTabs 模式）**；**侧边栏禁止新增应用级菜单**，选项卡栏常驻。
- 后台组件统一 Element Plus；布局/菜单/表格/表单遵循 `docs/规范/07-UI设计.md`（飞书/Ant Design Pro 审美、令牌化）。

### 5.2 API 调用规范
- `adminApi` baseURL=`/api/admin`、`customerApiCall` baseURL=`/api/customer`，**调用时 URL 不得重复前缀**。
- 响应拦截器已解包，组件内直接取 `res.xxx`，**禁止 `res.data.xxx`**；`catch(e)` 直接 `ElMessage.error(e)`，禁止 `e.response?.data?.error`。

### 5.3 权限接入（三处同步，必读）
- 侧边栏渲染源 = `CustomerLayout.vue` 写死菜单（非动态）；改菜单必须三处同步：`CustomerLayout.vue`（渲染）+ `menuPermissions.js`（守卫）+ `menuPermissions.test.js`（断言）。
- 分配权限弹窗按应用分组依据 = `app_menus.app_id → apps.id`（**禁止用 module 匹配 app code**）；`menu_key` 含冒号前缀（如 `card:overview`），前端勾选标识 `${app_code}:${menu_key}`，切分按第一个冒号。
- 新应用权限点：在 `app_menus` 注册（`app_id + module + module_label + key + label + sort_order`），并把 menu_key 挂到对应 `solution_permissions`。

## 6. 鉴权与多租户（红线）

- 平台账号：`accounts`（一人一号，跨租户复用）+ `tenant_members`（租户侧属性）。
- 登录：`POST /api/auth/login`（`{username|phone, password}`）；C 端业务有独立登录链路（如名片 `wx-login`），沿用既有模式，**禁止自创账号体系**。
- **所有业务数据查询必须带 tenant_id 过滤**（`WHERE tenant_id = ?`），读租户配置从 `projects.config` / 应用配置表取。平台级数据 tenant_id=0。
- 最后管理员保护、成员/角色权限加固等见 `docs/规范/01-账号权限.md`（涉及权限改动必须先读）。

## 7. 构建 / 测试 / 交付标准

### 7.1 每次改动后的铁律
- **每次改动后创建 git commit**（commit message 前缀约定：`feat:` / `fix:` / `refactor:` / `docs:` / `chore:`，例 `feat(card): 模板市场替换11套新皮肤`）。
- **每次改动后编写/更新测试**，交付前全部测试通过（后端串行全量、前端 vitest；新增纯函数必须配测试）。
- 构建验证：`npm run build:admin` + `npm run build:mobile`（或小程序 `build:mp-weixin`）+ `npm run verify`。

### 7.2 交付物清单（整合验收打勾用）
提交给本系统负责人（通过 Git 仓库或源码包）时必须包含：

- [ ] **源码增量**：只交付本次插件涉及的新增/修改文件（可 patch/diff，或完整目录），**说明基于哪个 commit / 日期**。
- [ ] **数据迁移**：`migrate-<日期>-<主题>.sql`（新表/新列/种子数据），含回滚说明。
- [ ] **应用注册**：apps 表 INSERT 语句（code/name/icon/category/sort_order）与 app_menus 权限点清单。
- [ ] **路由挂载点**：`app.js` 新增挂载行（精确到行）。
- [ ] **页面注册**：pages.json 新增页面/分包条目；小程序分包体积说明（<2MB）。
- [ ] **测试**：新增/修改的测试文件清单 + 运行结果（后端全量通过数、前端通过数）。
- [ ] **构建验证**：`npm run build:admin` / `build:mobile`（或 `build:mp-weixin`）通过截图或日志。
- [ ] **真机/模拟器验收截图**：关键页面截图（C 端小程序模拟器截图级验收、后台页面截图）。
- [ ] **文档**：涉及对标复刻的附「复刻检查清单」打勾结果；涉及权限的附权限矩阵。

### 7.3 已知基线（整合方会检查）
- 服务器正确重启姿势（`lsof -nP -iTCP:3000` → kill → `cd server && nohup node src/index.js`）——整合方负责，插件方无需处理。
- 本地 curl 必须 `--noproxy '*' http://127.0.0.1:3000/api/health`（本机代理会 502）。
- 数据库/上传文件 git 忽略，不入库；入库的只有代码。
- `docs/规范/02-构建部署.md` 有全部踩坑记录（构建前必读）。

## 8. 协作分工流程（跨 AI 系统）

```
① 需求拆解（负责人）
   负责人把插件拆成模块级任务包，每包附：
   - 数据模型（表结构草案）
   - API 契约（方法/路径/参数/响应示例）
   - 页面清单（页面名/路由/交互要点/对标参考）
   - 验收标准（对照 §7.2 清单）

② 外部开发（同事/其他 AI 系统）
   严格按本标准的 §2~§6 开发，交付 §7.2 清单全部产物。

③ 源码整合（负责人，即本 AI）
   收到源码后：
   1. 核对交付清单逐项打勾（缺项先补，不静默跳过）
   2. 合并进 monorepo（server / web-app / web-admin 各自落位）
   3. 跑迁移 → 重启服务 → 全量测试（串行）→ 前端测试
   4. 构建三端产物 → 真机/模拟器验证
   5. git commit + 通知用户验收

④ 验收（用户）
   负责人给结论 + 未决项清单（如：某页面需用户登录态实测）
```

**分工红线**：外部系统只产出「代码增量 + 文档」；**数据库、构建产物、部署、Git 合并、发布由本系统负责人统一执行**，避免多写者冲突。
