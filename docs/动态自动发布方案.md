## 一、现状诊断

### 1.1 「为什么现在没有自动发布」——不是缺定时器，是地基没铺

平台当前**完全不存在**自动发布/定时发布/素材库/排期能力。这不是功能没做，而是**发布链路本身有四个断点**，任何一个不补上，「定时发布」都会把错误定时地放大。

| 断点 | 现状 | 后果 |
|---|---|---|
| ① cardId 未传 | `POST /api/card/dynamics`（`routes/card.js:1988`）INSERT 时 `card_id` 依赖请求传入 | `card_id=NULL` → 公开列表按 `card_id=? AND visibility='public'` 过滤（`routes/card.js:546`）→ **动态永不上名片页** |
| ② 可见范围不落库 | 表有 `visibility` 字段（`db.js:1140`，DEFAULT 'public'），但 `toDynamic(row)` 序列化时**不返回该字段** | 用户选「公开」，回显却是「仅自己可见」——即已报缺陷的根因 |
| ③ 无图片入口 | `web-app/src/pages/card/dynamic.vue` 底部弹窗只有 textarea + 可见范围 | 「动态」退化为纯文字，无法承载真实营销内容 |
| ④ 无数据源抽象 | 动态创建逻辑**内联在路由里**，`card_dynamic` 的 INSERT 全库 3 处（路由 / seed / 测试夹具） | 无 service 层可复用，定时任务只能去抄路由代码，逻辑必然分叉 |

### 1.2 项目里已有的可复用资产（重要，改变了方案的成本结构）

代码核查发现，此前未被记录的基建：

| 资产 | 位置 | 对方案的意义 |
|---|---|---|
| **自研持久化任务队列** | `server/src/jobs.js`：`bg_jobs` 表 + `enqueueJob` / `claimNextJob` / `failJobRetry` / `startJobWorker`（轮询 2000ms，指数退避 30s×attempts，`MAX_ATTEMPTS=3`） | 方案 A **不需要引入 node-cron / bullmq / Redis**，也不需要常驻新进程。已具备幂等领取（`claimNextJob` 原子置 running）、失败重试、任务查询 |
| Worker 已接入主进程 | `server/src/index.js` 已 `startJobWorker(db, {'scene-tiling': ...})` | 只需注册新 handler，不用改启动流程 |
| 已有周期性任务先例 | `index.js` 中分销结算 `setInterval(10min)` | 「到点扫描」模式在本项目已被验证 |
| 对象存储与图片处理 | 依赖含 `ali-oss` / `qiniu` / `multer` / `sharp` | 图片上传、压缩、缩略图**几乎零新增成本** |
| 埋点数据表 | `db.js:1170+` `analytics_events`（含 `tenant_id`/`solution`/`event_type`） | 效果追踪可复用，不必新建 |
| 第三方平台代开发 | 依赖含 `miniprogram-ci` | 属主—代开发授权链路已通 |

### 1.3 真正的硬约束：`card_dynamic` 没有租户字段

`db.js:1131-1144` 的建表语句中，`card_dynamic` **只有 `user_id` 和 `card_id`，没有 `tenant_id` / `customer_id`**。

这意味着：**定时发布任务天然无法按租户查询**。要按租户隔离，只能走 `card_id → cards → customer_id` 间接关联，多一次 JOIN；而一旦某条动态的 `card_id` 为 NULL（正是缺陷①），它就**不属于任何租户**，在多租户 SaaS 里是不可管控的孤儿数据。

**这是三个方案都必须先解决的前置项**，且优先级高于定时发布功能本身。

### 1.4 「自动发布不是加个定时器就完事」的连锁依赖

按依赖顺序排列，前一环不解决，后一环无意义：

```
① 动态创建逻辑抽 service 层  ← 否则定时任务与手动发布两套 INSERT，行为分叉
      ↓
② card_id / tenant_id 强约束  ← 否则定时任务无租户边界（见 1.3）
      ↓
③ 图片上传 + 内容安全检测    ← 否则定时发布的内容形态太弱，且触碰审核红线
      ↓
④ 草稿/定时分离的数据模型      ← 否则「定时发布」只能改 created_at，等于伪造发布时间
      ↓
⑤ 任务调度 + 幂等 + 失败可见   ← 否则重复发布、失败静默
      ↓
⑥ 效果数据回流                ← 否则无法回答「定时发布有没有用」
```

**特别强调④**：当前 `card_dynamic.created_at` 的默认值是 `datetime('now')`，且**没有 `scheduled_at` 字段**。如果定时发布只是「到点改一下 created_at」，那么动态列表排序、点赞时间线、互动统计全部要跟着改造——用一条 UPDATE 伪装发布时间是技术债的起点。正确做法是引入独立的任务表，发布时才真正 INSERT。

### 2.1 微信官方规则（**本节准确性最高，也最影响方案选择**）

#### (1) 《微信公众平台运营规范》3.27「非真人自动化创作行为」——2026 年 3 月 27 日新增

规则原文（转载官方规范条文）：

> **3.27 非真人自动化创作行为**
> 违规内容：公众号和服务号不得利用 AI、脚本、接口或其他自动化方式，替代真人完成内容创作、发布等流程，包括但不限于以下情况：
> - 3.27.1 脱离真实创作者表达，利用人工智能等方式生成、改写、拼接或者搬运内容的行为；
> - 3.27.2 通过脚本、程序托管等自动化方式批量、连续发布内容的行为；
> - 3.27.3 传播非真人自动化创作的教程、方法或服务的行为。
>
> 处理规则：对于违反上述规范的，平台将根据违规程度对相关内容采取流量限制、删除等处罚措施；对账号采取能力限制、封禁等措施。

来源：[规范条文转载（微信官方社区/荆楚网）](https://ima.qq.com/wiki/?shareId=8a49e04a576a6e6ea5043b9b4c8c4e04cfb0e5a709a264c3f09d8ee12873ad38d13b9f4e7e2b6b5c6b3e0f0d1a&mediaId=wechatarticle_9bd3e3a6c63721a75a4ea0151f8cd8a1_dd92b37bbd8fbb9bf2fe1ac1727911067461198219994055&action=openDetailDrawer&webFrom=10000171)、[第一财经报道（含微信团队回应）](https://www.yicai.com/news/103125654.html)、[光明网转载](https://m.gmw.cn/2026-04/10/content_1304412022.htm)、[澎湃新闻](https://m.thepaper.cn/newsDetail_forward_32956345)、[腾讯新闻](https://news.qq.com/rain/a/20260410A01NQY00)

真实处罚案例：公众号「爆了么AI」被封禁，提示「该账号存在非真人自动化创作行为，已被停止使用」，同一公司的小程序也一并被封（[环球网](https://3w.huanqiu.com/a/a7835f/4R8C2JjdcfX)）。

**对本项目的关键推论（必须准确理解，不要过度引申）：**
- 3.27 条文面的主体是**「公众号和服务号」**。本项目 C 端是**小程序**，不直接落入 3.27 的适用范围。
- 但两点必须警惕：① 案例中「公众号 + 小程序」被**连带**处置；② 微信团队的原话是「反对完全由自动化程序替代真人完成内容生产的行为」——这是一条**取向声明**，未来是否延伸到小程序侧，官方未明确。
- **可安全落地的边界**：3.27.1 约束的是「内容生产」环节（AI 替代真人创作）。而「定时发布」是**分发环节**——真人先创作、确认、定时间，机器只负责到点写入。这与 3.27.2「通过脚本、程序托管等自动化方式**批量、连续**发布内容」有实质区别：后者指向无人值守的批量灌水。
- **必须规避的三条线**：AI 生成内容直接发布（踩 3.27.1）、无人审核的批量定时群发（踩 3.27.2）、把「自动发布能力」作为卖点对外宣传（踩 3.27.3）。
- 同平台更早的《微信公众号和服务号推荐运营规范》也已不鼓励「通过简单指令生成套路式、碎片式信息从而大批量发布的低质灌水内容」（[第一财经](https://www.yicai.com/news/103125654.html)）。

**机制总结（去掉包装）**：这类工具的「自动发布」本质是**持有平台登录态 + 在官方后台执行已排好的操作**，官方后台的草稿/定时队列才是真定时源。它们**不是**平台开放接口的调用方，因此所有「保持登录、别改密码、别在本机清进程」的注意事项本质上都是对脆弱的登录态的补偿。

| 层级 | 代表 | 原理 | 风险 |
|---|---|---|---|
| 初级 | 按键精灵、AutoIt、油猴脚本 | 录制鼠标坐标重复操作 | 网页改版即失效；无法过验证码 |
| 中级 | 指纹浏览器、社群群控系统 | 调用底层接口 / 模拟多设备 | **极高**：平台对非官方 API 调用打击严厉，极易降权封禁 |
| 高级 | RPA + AI Agent（如实在 Agent、UiPath） | CV 识别屏幕元素 + 大模型生成内容，像真人操作浏览器 | 相对最低，但需持续维护 |

**平台风控的实际检测维度**（[51CTO 分析](https://blog.51cto.com/u_16213590/14961590)）：
1. **行为频率**：单位时间操作次数、间隔是否过于均匀（机器典型特征）、是否 7×24 不间断
2. **行为模式**：操作路径是否过于规律、点击位置是否过于集中、文本是否有模板化痕迹
3. **用户特征**：IP 地址异常、设备指纹异常、账号行为历史

**一个值得警惕的行业数据点**：某连锁超市 20+ 门店做多平台评论同步时，单 IP 长时间访问相同平台账号导致**封禁率高达 30%**；引入 IP 池轮换后封禁率降低 85%。（[企编云案例](http://www.qib.cn/articles/19910-rpa-ip.html)）

⚠️ **该数据来自厂商自述，无第三方验证，仅可作为「风险量级存在」的参考，不可作为决策依据。**

**结论**：RPA 在微信生态里是**已被官方点名的违规方向**（见 2.1(5)），且没有可靠公开来源能证明它在大规模账号下稳定可用。**本项目不应把 RPA 作为方案的一部分。**

### 2.4 AI 内容生成 + 素材库 + 智能排期 + 一键多平台分发

真实产品的闭环形态：

| 产品 | 闭环链路 | 来源 |
|---|---|---|
| **KAWO 科握** | 内容规划 → 审批 → 排期 → 发布全链路；**素材库**（图片/视频/文案统一存储、标签检索、自动归档）；可视化日历共享的**智能排期**；**多级审批**（支持微信小程序随时审批）；AI 推荐最佳发布时间、定时/批量/**错峰发布**；数据仪表盘 + 竞品对标 + 周报月报自动生成。宣称服务 500+ 品牌 | [产品页](https://annazlib.com/sites/882.html) |
| **智域蒲公英 AI+ v3.0** | 明确的 AI Agent 工作流六步：**选题**（灵感工厂自动获取）→ **创作**（基于知识库生成初稿）→ **适配**（为不同平台/账号生成适配版本）→ **审核**（提交人工审核工作流）→ **分发**（审核通过后自动按排期分发）→ **监测**（发布后自动回收数据生成报告）；另有 GEO 优化、跨平台数据看板（触达→互动→转化→成交四层漏斗 + 异常预警） | [发布公告](http://pgy.sinobasedm.com/resource/product-news/pgy-ai-plus-v3-release-announcement.html) |
| **Postiz + LLM 工作流**（技术博客实践） | 选题生成器（积压池 <20 条自动补）→ 创意智能体（文本 + 视觉生成，组装完整内容包）→ 排期智能体（按各平台正确时段推送，记录帖子 ID）→ 反馈智能体（每 3 天拉表现数据更新记忆库）；人工唯一环节是每周 10 分钟批准选题 | [实践文章](https://www.jxxy.net/ai/articles/sairahul1-2066809666592718879) |

**三个成熟产品的共同特征（这是"真实形态"而非想象）：**
1. **人工审核是不可绕过的闸门**，不是可选步骤——三家都有显式的审核环节或人工批准环节
2. **「适配」是一等公民**，同一素材针对不同平台/账号生成不同版本，不是原样搬运
3. **排期 ≠ 定时发布**：排期包含日历视图、冲突提示、错峰策略、跨平台时区对齐
4. **效果回流必须带 content/post ID 回链**，否则数据看板无法归因到具体内容

**但请注意**：上述产品全部服务于**抖音/小红书/公众号/视频号等自有平台账号**，其分发环节落在 2.1(5) 所述的灰色地带或依赖平台开放接口。它们**没有、也不可能**把内容分发进「客户自己的第三方代开发小程序」。**这个空白正是本项目的机会，也是方案 C 的技术难点所在。**

## 三、三个可选方案

### 方案 A：轻量定时发布（手动发布 + 图片 + 定时）

#### 适用阶段与量级
- 阶段：当前版本（缺陷修复 + 最小可用运营能力）
- 用户量级假设：≤ 500 租户；日发布动态量 ≤ 5,000 条；峰值到点并发 ≤ 200 条/分钟

#### 功能范围
1. 动态创建逻辑抽 `services/dynamic.js`，统一 `createDynamic()`
2. `card_id` 必填 + 服务端兜底（取用户当前名片）
3. `toDynamic` 补 `visibility`
4. 图片上传入口（≤9 张/条，沿用现有 OSS/COS + sharp 压缩）
5. 发布前内容安全检测（文本 msgSecCheck + 图片 mediaCheckAsync）
6. 定时发布：选「立即 / 定时」，定时走服务端任务，到点真实 INSERT
7. 我的动态列表增加「待发布」分组与取消/立即发布操作

#### 技术实现路径

**新增表（1 张）：**

`dynamic_schedule` —— 排期任务表，与 `card_dynamic` 分离。字段建议：
`id` / `tenant_id`（新增租户字段）/ `user_id` / `card_id` / `title` / `content` / `images` / `visibility` / `scheduled_at`（UTC ISO8601）/ `status`（pending|published|failed|canceled）/ `attempts` / `last_error` / `published_dynamic_id`（回写实际生成的动态 id）/ `idempotency_key`（唯一）/ `created_at` / `updated_at`

**为什么不复用 `bg_jobs`**：bg_jobs 通用但**不承载业务状态**，没有 `scheduled_at` / `published_dynamic_id` / 可见范围，且 payload 塞业务字段无法索引查询。用它做触发器、这张表做业务源，worker handler 只做「到点查 pending → 调 `createDynamic()`」。

**不新增接口？** 需新增：
- `POST /api/card/dynamics/schedule`（创建排期）
- `GET /api/card/dynamics/schedule`（我的排期列表）
- `DELETE /api/card/dynamics/schedule/:id`（取消）
- `POST /api/card/dynamics/schedule/:id/publish-now`（立即发布）
- 改造 `POST /api/card/dynamics`，接受 `images` 真实入库

**定时任务**：**不引入新依赖**。复用 `server/src/jobs.js`，在 `index.js` 的 worker handler map 注册一个 `dynamic-publish` handler，逻辑为：查询 `dynamic_schedule` 中 `status='pending' AND scheduled_at <= now` 的到期项 → 逐条调用 `createDynamic()` → 回写 `published_dynamic_id` 并置 `status='published'`。

**⚠️ 但必须先补 jobs.js 的一个缺陷**：`claimNextJob` 目前**一次只领一个任务**（`LIMIT 1`），且 `startJobWorker` 的 handler 是单条处理。若 200 条同时到期，串行处理会积压。方案 A 的处理方式：在 `dynamic-publish` handler 内部**批量取到期项**（如一次 50 条），把「批量扫描」与「单任务队列」解耦，不必改动通用队列语义。

**幂等设计（三重）：**
1. `dynamic_schedule.idempotency_key` 唯一索引（建议 `sha256(tenant_id + user_id + content + scheduled_at)`）
2. 置 `status='publishing'` 时用条件更新 `WHERE id=? AND status='pending'`，靠 SQLite 单写者保证只有一个 worker 抢到
3. `published_dynamic_id` 非空即视为已完成，重复执行直接返回

**失败重试**：`createDynamic` 抛错 → `attempts+1`，按 30s / 60s / 120s 退避重排（与 `jobs.js` 的 `RETRY_BASE_MS=30_000` 保持一致），超 3 次置 `failed` 并在小程序端对用户可见。

**图片内容安全检测（必须做，不能后置）**：
`mediaCheckAsync` 是**异步**接口，需在「开发-接口设置」配消息推送 URL 接收 `wxa_media_check` 回调。设计为：排期创建时图片即标记 `pending_check`，回调 `pass` 才允许发布；`risky` 直接置 `canceled` 并退款/提示；`review` 走人工。**注意**：`media_url` 必须是**不含参数的可直接下载公网地址**，否则下载失败（[社区反馈](https://fuwu.weixin.qq.com/community/develop/doc/000e26cc2748086452a3afadc64c00)）。

#### 工作量估算（人日）

| 项 | 人日 |
|---|---|
| `services/dynamic.js` 抽取 + 三处 INSERT 统一 | 1.0 |
| `card_dynamic` 加 `tenant_id` + 数据回填 + 索引 | 0.5 |
| 修 cardId 兜底、`toDynamic` 补 visibility | 0.5 |
| 图片上传接口 + 前端选择器 + 压缩 | 2.0 |

| `dynamic_schedule` 表 + CRUD 接口 | 1.5 |

| 测试（47 个测试文件下**当前无任何动态测试**，需从零建） | 1.5 |
| **合计** | **12 人日**（区间 8–11 天为熟练期估法，12 天含联调与灰度） |

#### 运维复杂度
- **常驻进程**：无。复用现有 Node 进程内 worker（`timer.unref()` 已调用，不阻塞退出）
- **外部服务**：仅微信内容安全接口（必需，官方审核要求）；对象存储已有
- **失败重试/幂等**：见上
- **监控**：`queryJobs` 已有管理端查询能力，需补一个「失败排期」列表
- **新增运维面**：内容安全接口的 `access_token` 管理（2 小时有效期，需缓存刷新）；每客户小程序 AppSecret 的安全存储

#### 风险与合规注意事项
- ⚠️ **类目资质**：动态属 UGC。若小程序申报类目为「社交-社区/论坛」，需《非经营性互联网信息服务备案核准》等 3 选 1 资质（[官方答复](https://developers.weixin.qq.com/community/develop/doc/000eae311009b80bf8ebaf0215c000)）。**多租户代开发模式下，任一租户的小程序因类目问题被驳回，都需要平台侧协助整改**——这是运营成本，不在开发工日内，但必须提前和商务对齐。
- ⚠️ 定时发布是**分发自动化**，非内容生产自动化，不落入 3.27.1；但**不得宣传为「无人值守自动运营」**，避免触碰 3.27.3。

#### 明确的取舍
- **牺牲**：素材库、草稿箱、审核队列、AI 能力、多平台分发全部不做；发布仍需人工逐条操作，只是可以「提前写好、定点放出」。
- **换来**：把已知的四个断点全部修掉，动态功能从「不可用」变成「可用」；技术面几乎零新增架构成本（复用现有队列）；合规面干净（不引入 RPA、不引入 AI 生成）；**8–12 人日内可见效**。

### 方案 B：内容运营（素材库 + 草稿箱 + 排期 + 审核队列）

#### 适用阶段与量级
- 阶段：有 3+ 家客户明确提出「多人运营 / 需要统一内容池」后
- 用户量级假设：500–3,000 租户；单租户有专职运营；日排期任务 ≤ 50,000 条

#### 功能范围
1. 方案 A 全部内容
2. **素材库**：图片/文案集中存储、打标签、检索、复用、引用计数（素材被删除时禁止引用其草稿）
3. **草稿箱**：动态草稿独立状态，支持多人协作编辑（冲突检测：基于 `updated_at` 版本号乐观锁）
4. **排期日历视图**：按周/月展示所有排期，冲突提示、容量视图
5. **审核队列**：草稿 → 提交审核 → 管理员/运营审核 → 通过后进入排期；驳回带意见
6. **角色权限**：租户内「运营者 / 审核者 / 管理员」三级，复用现有租户后台账号体系
7. **数据看板**：按动态统计曝光/互动，复用 `analytics_events`

#### 技术实现路径

**新增表（4–5 张）：**
- `dynamic_material`（素材：类型、URL、标签、归属租户、引用计数）
- `dynamic_draft`（草稿：内容、素材引用 JSON、版本号、编辑者、状态 draft|in_review|approved|rejected）
- `dynamic_review_log`（审核流水：审核人、动作、意见、时间）
- `dynamic_schedule`（沿用方案 A，扩展 `draft_id` 字段）
- 可选 `dynamic_role`（若现有租户账号体系无角色字段）

**新增接口**：素材 CRUD + 上传、草稿 CRUD + 版本冲突处理、审核提交/通过/驳回、排期日历查询（按时间范围）、角色权限中间件扩展。

**定时任务**：沿用方案 A 的 `dynamic-publish` handler，**新增前置闸门**——只发布 `status='approved'` 的排期。

**幂等**：沿用方案 A 三重设计，额外在 `dynamic_draft → dynamic_schedule` 转换处保证「一次转换只产生一条排期」。

**失败重试**：沿用。额外：审核流转失败（并发审批）用乐观锁版本号拒绝，不进重试队列。

#### 工作量估算（人日）

| 项 | 人日 |
|---|---|
| 方案 A 全部 | 12 |
| 素材库（表 + 接口 + 前端 + 引用计数与删除保护） | 6 |
| 草稿箱（表 + 接口 + 版本冲突 + 前端） | 5 |
| 审核队列 + 流水 + 三级角色权限 | 6 |
| 排期日历视图（含冲突提示） | 4 |
| 数据看板 | 3 |
| 测试 | 4 |
| **合计** | **40 人日**（区间 30–38 天，不含设计稿） |

#### 运维复杂度
- **常驻进程**：无
- **外部服务**：同方案 A（内容安全 API + 对象存储）
- **新增运维面**：
  - 素材存储成本（需配 CDN + 生命周期策略，否则 OSS 账单随租户数线性增长）
  - 审核 SLA：若客户运营提交后无人审核，排期会空转。**需产品侧约定审核责任归属，并提供「超时自动提醒」**
  - 素材合规：素材库是风险的**沉淀地**，违规素材会反复被复用。需在入库时就做内容安全检测，而非只在发布时检测
- **失败重试/幂等**：同方案 A
- **多租户隔离**：素材库与草稿箱都是**强租户隔离**对象，查询必须强制带 `tenant_id`，且需专项测试覆盖（当前项目**无动态相关测试**，测试基线为零）

#### 风险与合规注意事项
- ⚠️ **素材库的合规责任放大**：素材一旦入库，就可能被批量复用。若某素材违规被检测出，所有引用它的草稿都需下架。需设计「素材级封禁」而非「草稿级封禁」。
- ⚠️ 审核队列是「代客户审核第三方内容」，平台需明确免责边界（审核不通过 ≠ 平台认可）。
- ⚠️ 仍不触碰 3.27：素材库和审核都是**强化**真人创作，与 3.27 方向一致。

#### 明确的取舍
- **牺牲**：AI 能力（不做）、多平台分发（不做）；增加了一套需要客户自己「用起来」的重流程——如果客户没有专职运营，**素材库和审核队列会变成空壳**。
- **换来**：面向 B 端收费的正当性（运营团队是 SaaS 付费的典型理由）；把单点发布升级为可协作的内容资产体系；多租户内容资产的复用价值。

### 方案 C：AI + 全域（AI 生成 + 智能排期 + 多平台分发）

#### 适用阶段与量级
- 阶段：需等 3.27 条规则对小程序侧的适用边界明朗，且有标杆客户愿意为「全域分发」付费
- 用户量级假设：3,000+ 租户，其中 5% 有专职内容预算

#### 功能范围
方案 B 全部，加：
1. **AI 文案生成**：基于租户品牌资料（名片信息）+ 素材，生成动态文案；模板化提示词库
2. **AI 配图生成**：文生图/图生图
3. **智能排期建议**：基于本租户历史动态的曝光/互动数据推荐发布时间（排除低活时段）
4. **效果复盘**：周报/月报，指出哪类文案/时段表现更好
5. **一键多平台分发**：把同一条动态分发到客户自有公众号/视频号/抖音/小红书

#### 技术实现路径

**新增表（6–8 张）**：`dynamic_ai_profile`（品牌语料）、`dynamic_ai_job`（生成任务）、`dynamic_channel`（渠道授权与配置）、`dynamic_channel_task`（分发任务与结果）、`dynamic_insight`（效果指标快照），加上方案 B 的 5 张。

**新增接口**：AI 生成、素材生成、渠道 OAuth 授权绑定、分发任务、数据回流。

**定时任务**：在方案 B 的 `dynamic-publish` 之后新增 `channel-dispatch` 链路。

**关键技术难点（必须诚实评估）：**
1. **「多平台分发」在本项目里没有干净的技术路径。**
   - 视频号：**无第三方发布 API**，只能 RPA → 违反微信规则，见 2.1(5)。
   - 公众号：需每个客户在小程序内做**公众号 OAuth 授权**，把公众号的群发/素材权限集授权给本平台。这是可行的，但：授权是逐权限集的；`authorizer_access_token` 2 小时有效期需刷 `refresh_token`；群发次数受**订阅号 1 次/天、服务号 4 次/月**硬限制（2.1(3)）——**排期再密也发不出去**。
   - 抖音/小红书等站外平台：各有开放平台，但企业资质审核周期 + 类目权限申请是主要成本；且**这部分能力不解决本项目的核心场景**（客户的名片小程序）。
2. **AI 生成内容直接撞 3.27.1。** 「脱离真实创作者表达，利用人工智能等方式生成、改写、拼接内容」——若 AI 生成的动态直接发布到客户小程序，虽非公众号，但**同一风险模型**。可行路径只有一条：AI **起草**，人工**确认并改写**，系统留存「人工确认」记录。这也让「一键生成一键发布」的产品形态不成立。
3. **模型成本与租户隔离**：`dynamic_ai_profile` 存客户品牌语料，需明确数据归属与跨租户**绝对禁止**共享（企业客户最敏感的隐私点）。LLM 调用按 token 计费，需配额与降级。

#### 运维复杂度
- **常驻进程**：**需要**。渠道分发的 RPA/浏览器自动化进程需常驻（需 Playwright + 无头浏览器 + 登录态维持），是多实例、有状态、易失效的运维对象
- **外部服务**：LLM API + 图像生成 API + 多个平台开放平台 + 代理/IP 池
- **失败重试/幂等**：方案 A/B 的机制仍适用，但**渠道分发无法保证幂等**——网络超时后无法判断平台侧是否已发布，可能重复发布。这是所有 RPA 分发工具的固有缺陷
- **监控**：登录态失效检测、IP 健康度、内容安全接口配额、LLM 配额与费用告警——**至少 4 个新的告警维度**
- **成本结构**：LLM token + RPA 机器成本 + IP 代理成本，均随租户数线性增长

#### 风险与合规注意事项
- ⚠️ **AI 生成内容 = 3.27.1 的直接风险面**，必须做「AI 起草 + 人工确认 + 留痕」
- ⚠️ **RPA 分发视频号 = 微信公开点名禁止的方向**，一旦被检测，处置的是**客户的视频号**，商务上无法兜底
- ⚠️ 对外宣传若含「AI 自动发布」「无人值守」，直接触碰 3.27.3（传播非真人自动化创作的教程、方法或服务）
- ⚠️ 站外平台对「电子名片 + 动态」这种内容形态的接受度未知，可能被判定为营销号批量发布

#### 明确的取舍
- **牺牲**：合规确定性（引入 RPA 与 AI 两条明线）、交付确定性（渠道接入受制于第三方审批周期）、运维可控性（常驻进程 + 登录态）、巨额前期投入的回收能见度。
- **换来**：一个对标 KAWO / 智域蒲公英的完整故事，和「全域营销」的定价叙事。
- **判断**：**在 3.27 规则边界未明、且方案 A/B 的需求尚未验证之前，这个投入无法被证明是合理的。**

## 四、推荐与实施路线图

### 4.1 推荐：方案 A 立即启动，B 挂起为付费包，C 暂缓

**理由一：本项目的架构特殊性使方案 C 的核心价值归零。**

本项目是**每客户一个小程序 + 微信第三方平台代开发模式**。这意味着：

1. **动态的落点是平台自有数据库**（`card_dynamic`），不是微信生态的开放接口。发布行为**不消耗任何平台发布配额**，不触碰群发次数限制，也不受视频号 7 天/30 天的原生定时窗口限制——**方案 C 中最难的「多平台分发」问题，在本项目的主场景里根本不存在**。
2. **方案 C 的最大卖点恰恰是本项目最不需要的**。市场上 KAWO / 智域那类产品解决的是「一个运营同时管 20 个平台账号」，而本项目的客户痛点是「在我的名片小程序里持续发内容」。前者是**渠道广度**问题，后者是**内容持续性**问题——**不能把前者当卖点来卖后者**。
3. **代开发模式的授权复杂度会放大方案 C 的成本**。渠道分发要求每个客户逐一完成公众号/视频号的权限集授权，而 `authorizer_access_token` 2 小时有效、需 `refresh_token` 刷新、**平台侧不支持服务商主动解除授权**（2.1(6)）——这在 N 个租户上是 N 份运维负担，而不是一份。

**理由二：缺陷①②③说明当前连「能发」都没做到，谈「自动发」是本末倒置。**

用户报的是「选公开却显示仅自己」，根因是 `toDynamic` 漏字段；而 `card_id=NULL` 会导致公开动态永不上名片页。这两个 bug 的修复成本合计不到 1 人日，却直接决定动态功能是否可用。**先把地基补齐，再谈自动化。**

**理由三：方案 A 的边际成本被现有基建压到了极低。**

`server/src/jobs.js` 已经提供了持久化队列、原子领取、指数退避重试、任务查询；`index.js` 已经接好了 worker；对象存储和图片处理依赖齐备。**方案 A 的增量几乎全部在业务代码（service 抽取、图片入口、定时任务 handler、前端交互），而非架构。**

**理由四：方案 A 是唯一能验证需求真伪的方案。**

如果客户在有了「定时发布」之后仍然不用，说明真实需求不是「定时」而是「素材复用 / 多人协作 / AI 提效」——那时 B 或 C 的立项才有需求依据。**在没有排期需求的情况下先建素材库，是把假设当需求。**

### 4.2 分阶段路线图

#### 阶段 0：地基修复与数据隔离（前置，不可跳过）

| 交付物 | 验收标准 | 依赖项 |
|---|---|---|
| `services/dynamic.js`，统一 `createDynamic()` | `card_dynamic` 的 INSERT 全库收敛到 1 处；路由、seed、测试夹具全部改为调用 service | 无 |
| `card_dynamic` 新增 `tenant_id` + 回填 + 索引 | 存量数据 100% 有正确 tenant_id（可按 `card_id → cards.customer_id` 回填，NULL 的单独归档）；无 tenant_id 的动态为 0 条 | 确认 `cards` 表客户关联字段 |
| 修 `cardId` 兜底 + `toDynamic` 补 `visibility` | 不传 cardId 时自动取用户当前名片；接口返回含 visibility；「选公开显示仅自己」复现步骤不再复现 | 阶段 0 第 1 项 |

#### 阶段 1：方案 A 落地（8–12 人日）

| 交付物 | 验收标准 | 依赖项 |
|---|---|---|
| 图片上传链路 | 单条动态 ≤9 图；前端可预览/删除/排序；服务端 sharp 压缩后存 OSS；无 OSS 时降级为不传图 | 阶段 0 |
| 内容安全检测 | 文本走 msgSecCheck；图片走 mediaCheckAsync 且配好回调路由；`risky` 拦截、`review` 转人工；**检测未通过的内容不允许发布** | 需在小程序后台配消息推送 URL |
| `dynamic_schedule` 表 + CRUD | 幂等键唯一索引生效；同一幂等键重复提交返回已有排期 | 阶段 0（tenant_id） |
| `dynamic-publish` worker handler | 到点后真实 INSERT `card_dynamic`；`published_dynamic_id` 正确回写；批量扫描（一次 50 条）避免积压 | 阶段 0（service 层） |
| 幂等与重试 | 三重幂等验证通过；进程重启后任务不丢不重；连续失败 3 次后置 failed 且用户可见 | — |
| 前端定时发布交互 | 可选立即/定时；我的动态分「待发布/已发布」；待发布可取消/立即发布；定时发布强制先过内容安全 | — |

| 租户隔离测试 | 租户 A 无法看到/取消/发布租户 B 的排期（含越权 ID 遍历测试） | 阶段 0 |

**关键验收标准（必须逐条实测，不接受口头确认）：**
1. 定时任务在**服务进程重启**后仍能正确发布（验证 `bg_jobs` + `dynamic_schedule` 的持久化）
2. 同一排期任务**重复触发 3 次，`card_dynamic` 只有 1 条记录**
3. 内容安全返回 `risky` 的动态，**在排期到点后不会被发布**
4. 到点瞬间模拟 200 条任务积压，全部在 5 分钟内处理完
5. 跨租户越权访问排期 ID，返回 404/403 且不泄露任何内容

#### 阶段 2：观察期（4–6 周，不做新功能）

**唯一目标：验证排期功能是否真被使用。**

- 埋点：排期创建数、排期发布数、发布成功率、取消率、平均提前量（创建时间 vs 排期时间）
- 判定门槛：
  - **≥30% 的活跃租户使用过排期功能** → 启动方案 B 立项评估
  - **<10%** → 暂停，把资源投回动态的基础体验（互动能力：点赞/评论通知），不建素材库

#### 阶段 3（条件触发）：方案 B

**触发条件**：阶段 2 达标 **且** 至少 2 家客户书面表达「需要多人运营/统一内容池」。

**必须先回答的前置问题：**
1. 素材的存储成本谁承担？（建议包含在套餐内，设租户级配额）
2. 审核责任如何界定？（需法务出免责条款）
3. 内容安全检测策略是否从「发布时检测」前移为「入库时检测」？（建议前移，否则素材库成为风险沉淀地）

#### 暂不启动：方案 C

**重新评估的触发条件（需同时满足）：**
1. 微信官方就 3.27 条对小程序侧 UGC 自动化的适用边界有明确公开说明
2. 阶段 2 数据显示 ≥30% 租户有跨平台分发诉求
3. 有客户愿意为「全域分发」单独付费，且能接受「发布到客户自有公众号会受群发次数限制」这一硬约束

## 五、风险清单

| # | 风险 | 影响 | 概率 | 缓解措施 |
|---|---|---|---|---|
| 1 | **内容被判定「非真人自动化创作行为」（3.27）** | 客户小程序功能受限/下架；平台代开发模式下一客户出事影响面观感 | 中（若方案 C 引入 AI 直接生成） | 方案 A/B 严格限定在「分发自动化」，**不引入 AI 生成内容**；对外文案禁用「AI 自动发布/无人值守」表述；建立宣发话术白名单 |
| 2 | **类目资质不匹配（UGC 需社交类目资质）** | 客户小程序提审被驳回或功能被限 | 中高（每客户小程序独立审核） | 阶段 0 时同步审计各租户现有类目；商务合同前置说明 UGC 类目要求；准备资质材料模板 |
| 3 | **图片内容安全未接入导致审核不通过** | 小程序版本提审被驳回，要求整改 | 高（不做必然触发） | 阶段 1 强制包含 msgSecCheck + mediaCheckAsync；`media_url` 必须是**无参数公网地址**（否则下载失败）；配置消息推送回调并验证连通性 |
| 4 | **发布失败无感知** | 客户以为已发布，实际未发；信任流失 | 中高（`bg_jobs` 现有 `MAX_ATTEMPTS=3` 后置 failed **无任何用户侧通知**） | 失败必须在小程序端对用户可见；管理后台失败列表 + 人工重试；关键租户加企业微信/飞书 webhook 告警 |
| 5 | **重复发布（幂等失效）** | 同一内容出现多条，对外事故 | 低（有三重设计）但影响大 | `idempotency_key` 唯一索引；`WHERE status='pending'` 条件更新抢占；`published_dynamic_id` 非空即完成。**必须写并发压测** |
| 6 | **时区处理错误** | 动态在错误时间出现（差 8 小时），客户投诉 | **高**（见下） | ⚠️ **代码现状：`db.js` 用 `datetime('now')` = UTC，`tenant.js` 的 `today()` 用 `toISOString()` = UTC，而目标用户在中国 UTC+8**。排期表必须显式约定：① 存储一律 UTC ISO8601；② 租户时区字段（默认 `Asia/Shanghai`）；③ 排期 UI 按租户时区展示与提交；④ 单元测试覆盖跨 UTC 日界与跨年边界 |
| 7 | **夏令时/时钟漂移** | 定时任务提前或延后触发 | 低（中国无夏令时；但服务器 NTP 漂移会导致批量偏差） | 租户侧不做夏令时处理（Asia/Shanghai 无 DST）；服务器启用 NTP；worker 依赖数据库 `run_at` 比较而非内存计时 |
| 8 | **租户隔离被击穿** | 租户 A 的任务影响租户 B（数据泄露事故） | 低（若无 tenant_id 则**必然发生**） | `card_dynamic` 与所有新增表**强制**带 `tenant_id`；所有查询强制带租户条件；越权 ID 遍历测试纳入必测项；管理后台跨租户操作需显式切换租户上下文 |
| 9 | **任务积压** | 定时动态延迟发布，到点不准 | 中（`claimNextJob` 是 `LIMIT 1` 串行） | `dynamic-publish` handler 内部批量取（一次 50 条）；handler 执行加耗时监控；积压量超阈值告警；单次处理上限防止长事务阻塞 SQLite 单写者 |
| 10 | **SQLite 单写者竞争** | 发布高峰期写锁等待，定时任务与用户请求互相拖慢 | 中 | `card_dynamic` 写入量估算（日 5,000 条约等于峰值 7 条/分钟，远低于 SQLite 能力）；批量提交；避免在事务中做外部调用（内容安全接口调用必须在事务外） |
| 11 | **素材/图片违规内容沉淀** | 一张违规图被反复复用，影响面放大 | 高（仅方案 B/C） | 素材级封禁而非草稿级封禁；入库即检测；引用计数防止删除被引用素材 |
| 12 | **用户到期/停用后任务仍执行** | 已冻结租户仍在发布内容 | 中 | worker 执行前校验 `tenantState(db, tenantId)`，非 active 则置 canceled；复用现有 `tenant.js` |
| 13 | **对外宣称能力与实际不符** | 客户预期落空；踩 3.27.3 | 中 | 上线前核对宣传物料与实际功能边界；不使用「无人值守」「全自动」表述 |
