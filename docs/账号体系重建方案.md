# 成员管理・账号体系一步到位重建方案

> 版本：v1.0（待评审） ｜ 日期：2026-09-18
> 对标：云菜鸟「员工 / 角色 / 岗位 / 部门」账号体系（已 1:1 细读）
> 关联：门店管理独立应用（store）负责人（超管）并入统一账号体系（方案 A）

## 一、现状盘点与痛点

### 1.1 当前实现



| 项         | 现状                                                                                 | 位置                                       |
| --------- | ---------------------------------------------------------------------------------- | ---------------------------------------- |
| 账号表       | `users`：username/phone/password\_hash/password\_salt/role/status/customer\_id      | server/src/db.js                         |
| 角色枚举      | 硬编码 4 个：`admin`（平台超管）/`operator`（平台运营）/`tenant_admin`（租户管理员）/`tenant_member`（租户成员） | server/src/auth.js                       |
| 鉴权        | JWT 登录 + `requireAuth` + `requireRole(roles)` 按角色硬编码放行                             | server/src/auth.js                       |
| 成员页面      | `Members.vue`（107 行）：账号 / 角色二选一（管理员 / 成员）/ 绑定企业 / 手机号 / 移除                         | web-admin/src/views/customer/Members.vue |
| 应用 / 菜单权限 | 方案化两级：`solution_apps`（租户开通应用）+ `solution_permissions`（app+key 菜单授权）                | 现有方案体系                                   |
| 门店负责人     | `store` 表 3 字段（owner\_name/owner\_account/**owner\_password 明文**），无登录账号            | server/src/routes/store.js               |

### 1.2 核心痛点



1. **角色硬编码、不可扩展**：只有 4 个角色，租户无法自建角色；新增「门店超管」等角色要改代码。

2. **角色即权限、无权限点**：`tenant_admin` 是否拥有某菜单由方案授权决定，成员级别无法细分（云菜鸟可给员工勾菜单权限）。

3. **账号无组织维度**：没有部门 / 岗位，无法做「主管看部门数据 / 员工看个人数据」的数据范围控制。

4. **门店负责人无账号**：负责人只是信息字段，无法登录后台；明文密码是安全隐患；门店端 P1（订单 / 库存 / 提现）无账号可用。

5. **单租户假设**：users 表隐含一人一租户，未来 SaaS 多租户 / 多企业身份难以扩展。

6. **无身份概念**：云菜鸟的「后台管理员 / 小程序管理员 / 推广员 / 消息推送」多身份，本地完全没有对应模型（推广员目前挂在分销体系，与成员脱节）。

## 二、对标云菜鸟账号体系（1:1 细读结论）

云菜鸟商户后台「员工」模块实际结构（URL 与字段均为实测）：

### 2.1 员工列表（/staff/staff/list）



* 顶部：**添加部门** + 部门筛选（全部 / 默认…）+ 搜索 + **添加员工**

* 列表列：ID ｜ 用户信息（姓名 / 昵称 / 手机）｜ 岗位 ｜ 管理员账号 ｜ 权限 ｜ 身份（小程序管理员 / 推广员…）｜ 状态（启用中 / 停用）｜ 操作（编辑 / 删除）

### 2.2 添加 / 编辑员工（/staff/staff/info.html）字段全集



```
基础信息

&#x20; 员工姓名（必填）

&#x20; 所属部门（必填，默认）

&#x20; 部门权限（单选）：主管（可查看部门数据）/ 员工（仅可查看个人数据）

&#x20; 员工岗位（必选，默认）

&#x20; 权限身份（多选）：后台管理员 / 小程序管理员 / 推广员 / 消息推送

&#x20; —— 勾选「后台管理员」时出现 ——

&#x20; 登录账号（必填）

&#x20; 登录密码（必填）

&#x20; 所属角色（多选，角色=菜单权限组）
```

### 2.3 角色（/index/user\_role/part）



* 列表：ID / 角色名称 / 添加时间 / 操作（编辑 / 分配权限 / 删除）

* 新增角色：仅「角色名称」

* **分配权限弹窗**：按一级菜单分组勾选二级菜单（总览 / 商品 / 内容 / 订单 / 用户 / 设计 / 系统 / 员工 / 财务 / 应用 → 各二级菜单项），即**菜单级 RBAC**

### 2.4 岗位（/staff/post/list）



* 列表：ID / 排序 / 岗位名称；新增：排序 + 岗位名称

### 2.5 部门（员工列表页「添加部门」）



* 弹窗：排序 + 部门名称

### 2.6 云菜鸟模型总结



```
员工（staff）= 用户信息 + 组织（部门/岗位）+ 身份（后台管理员/小程序管理员/推广员/消息推送）+ 角色（菜单权限组）

角色（role）= 菜单权限勾选集合（RBAC）

部门（department）= 数据范围维度（主管/员工）

岗位（post）= 组织标签（排序+名称）
```

**局限（我们不照搬的部分）**：① 员工模型单租户（`?appletid=` 绑死一个商户），不便于多租户 / 多企业；② 权限只到菜单级，无按钮 / 数据级；③ 部门仅一层（无层级树）；④ 岗位 / 角色没有内置预置数据（演示数据为 0）。

## 三、目标模型：统一账号体系（本地设计）

### 3.1 核心原则



1. **账号与身份分离**：登录凭据（账号）与业务身份（成员、角色、门店负责人）解耦，一人可多身份、多租户。

2. **角色自定义**：内置角色 + 租户自建角色，角色挂权限点（复用现有 app\_menus 体系）。

3. **权限两级叠加**：租户方案授权（开通哪些应用 / 菜单）× 成员角色授权（能用哪些菜单）→ 有效权限取交集；超管全量。

4. **门店负责人即成员**：创建门店时把负责人建成账号 + 成员 +`store_admin` 角色，密码哈希化，废弃明文。

5. **兼容存量、平滑迁移**：现有 users 存量账号迁移到新模型，登录 / 鉴权接口保持兼容。

### 3.2 概念模型



```
accounts（登录账号，全局唯一凭据）

&#x20;  │ 1:N（多租户/多企业可复用）

tenant\_members（租户成员：账号在某租户下的业务身份）

&#x20;  │ 1:N

member\_roles（成员-角色关联，多对多）──── roles（角色：租户内置+自定义）

&#x20;                                             │ 1:N

&#x20;                                       role\_permissions（角色-权限点关联）── app\_menus / 权限点注册表

&#x20;  │（可选 P1）

member\_department / member\_post（部门/岗位，组织维度）

&#x20;  │（门店维度）

store.owner\_member\_id（门店负责人 = 某租户成员 + store\_admin 角色）
```

### 3.3 权限身份（对标云菜鸟 4 种，本地落地）



| 云菜鸟身份  | 本地落地                         | 说明                       |
| ------ | ---------------------------- | ------------------------ |
| 后台管理员  | PC 客户后台登录（本方案核心）             | 按角色菜单权限进入 customer 后台    |
| 小程序管理员 | C 端小程序管理员身份（核销 / 会员 / 订单）    | P1：C 端鉴权加身份判定            |
| 推广员    | 分销体系身份（dist\_user\_relation） | 保持分销体系现状，成员可关联推广身份，P1 打通 |
| 消息推送   | 接收订阅消息（短信 / 模板消息）            | P1：消息订阅表关联成员             |

P0 只做「后台管理员」身份 + 多身份字段预留；P1 再逐项落地其余身份。

## 四、数据表设计

### 4.1 新表（createDb 迁移，幂等）



```
\-- 1) 登录账号（替代 users 作为登录凭据；存量 users 迁移至此）

CREATE TABLE IF NOT EXISTS accounts (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; username TEXT UNIQUE,

&#x20; phone TEXT UNIQUE,

&#x20; password\_hash TEXT NOT NULL,

&#x20; password\_salt TEXT NOT NULL,

&#x20; status TEXT NOT NULL DEFAULT 'active',        -- active / disabled

&#x20; created\_at TEXT NOT NULL DEFAULT (datetime('now')),

&#x20; updated\_at TEXT NOT NULL DEFAULT (datetime('now'))

);

\-- 2) 租户成员（账号在某租户下的业务身份；account 可挂多个 tenant\_member）

CREATE TABLE IF NOT EXISTS tenant\_members (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; tenant\_id INTEGER NOT NULL,

&#x20; account\_id INTEGER NOT NULL,

&#x20; name TEXT NOT NULL DEFAULT '',                -- 姓名（员工姓名）

&#x20; nickname TEXT NOT NULL DEFAULT '',

&#x20; avatar TEXT NOT NULL DEFAULT '',

&#x20; status TEXT NOT NULL DEFAULT 'active',        -- active / disabled

&#x20; identities TEXT NOT NULL DEFAULT '\[]',        -- JSON：\["backend\_admin","mini\_admin","promoter","notify"]

&#x20; created\_at TEXT NOT NULL DEFAULT (datetime('now')),

&#x20; updated\_at TEXT NOT NULL DEFAULT (datetime('now')),

&#x20; UNIQUE (tenant\_id, account\_id)

);

CREATE INDEX IF NOT EXISTS idx\_tm\_tenant ON tenant\_members(tenant\_id);

CREATE INDEX IF NOT EXISTS idx\_tm\_account ON tenant\_members(account\_id);

\-- 3) 角色（租户级；内置角色 builtin=1 不可删）

CREATE TABLE IF NOT EXISTS roles (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; tenant\_id INTEGER NOT NULL,                    -- 0 = 平台内置（供默认注入）

&#x20; code TEXT NOT NULL DEFAULT '',                 -- tenant\_admin / tenant\_member / store\_admin / custom

&#x20; name TEXT NOT NULL,

&#x20; scope TEXT NOT NULL DEFAULT 'tenant',          -- tenant 租户级 / store 门店级

&#x20; builtin INTEGER NOT NULL DEFAULT 0,

&#x20; created\_at TEXT NOT NULL DEFAULT (datetime('now')),

&#x20; UNIQUE (tenant\_id, code)

);

\-- 4) 成员-角色关联

CREATE TABLE IF NOT EXISTS member\_roles (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; member\_id INTEGER NOT NULL,

&#x20; role\_id INTEGER NOT NULL,

&#x20; created\_at TEXT NOT NULL DEFAULT (datetime('now')),

&#x20; UNIQUE (member\_id, role\_id)

);

\-- 5) 角色-权限点关联（复用 app\_menus 的 module/key 作为权限点）

CREATE TABLE IF NOT EXISTS role\_permissions (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; role\_id INTEGER NOT NULL,

&#x20; app\_code TEXT NOT NULL,

&#x20; menu\_key TEXT NOT NULL,

&#x20; created\_at TEXT NOT NULL DEFAULT (datetime('now')),

&#x20; UNIQUE (role\_id, app\_code, menu\_key)

);

\-- 6) 部门（P1，先建表）

CREATE TABLE IF NOT EXISTS departments (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; tenant\_id INTEGER NOT NULL,

&#x20; name TEXT NOT NULL,

&#x20; sort\_order INTEGER NOT NULL DEFAULT 0,

&#x20; created\_at TEXT NOT NULL DEFAULT (datetime('now')),

&#x20; UNIQUE (tenant\_id, name)

);

\-- 7) 岗位（P1，先建表）

CREATE TABLE IF NOT EXISTS posts (

&#x20; id INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20; tenant\_id INTEGER NOT NULL,

&#x20; name TEXT NOT NULL,

&#x20; sort\_order INTEGER NOT NULL DEFAULT 0,

&#x20; created\_at TEXT NOT NULL DEFAULT (datetime('now')),

&#x20; UNIQUE (tenant\_id, name)

);
```

### 4.2 存量表改造



```
\-- users 保留（兼容总后台 admin/operator 与历史数据），租户账号迁移进 accounts+tenant\_members

\-- store 表：owner\_password 明文字段废弃（内容清空）；新增 owner\_member\_id（关联 tenant\_members）

\-- 迁移脚本：seedMigrationAccounts(db)

\--   1) users 中 role IN ('tenant\_admin','tenant\_member') 且 customer\_id 非空

\--      → 建 accounts（复用原密码哈希/盐），建 tenant\_members（tenant\_id=customer\_id，name=username）

\--      → 注入内置角色：tenant\_admin → 角色 tenant\_admin；tenant\_member → 角色 tenant\_member

\--   2) users 中 admin/operator 保留原表（平台总后台账号），不动

\--   3) 既有 store.owner\_account 非空的：按手机号匹配已有账号，无则建账号（密码由超管重置），绑定 store\_admin 角色
```

### 4.3 内置角色（seedStore 风格，tenant\_id=0 平台注入 + 每租户首次初始化时复制）



| 角色 code         | 名称    | scope  | 权限（app\_menus 权限点）   |
| --------------- | ----- | ------ | -------------------- |
| `tenant_admin`  | 租户管理员 | tenant | 全量（allPermissions）   |
| `tenant_member` | 普通成员  | tenant | 空（由管理员分配）            |
| `store_admin`   | 门店管理员 | store  | store 应用全部菜单 + 基础工作台 |

> 初始化：租户首次访问成员管理时，
>
> `ensureBuiltinRoles(tenantId)`
>
>  注入上述 3 角色（幂等）。

## 五、角色与权限设计

### 5.1 权限点注册



* **权限点来源**：复用现有 `app_menus`（app\_code + module/key + label），新增功能菜单自动成为权限点，无需单独维护。

* **权限树**：一级 = 应用（app），二级 = 菜单（key），同云菜鸟「一级分组勾选二级菜单」。

### 5.2 有效权限判定（两级叠加）



```
member.effective(app, key) =

&#x20;   tenantHasApp(app)                            -- solution\_apps 方案授权

&#x20;   && (member.role == tenant\_admin              -- 租户超管全量

&#x20;       || member.roles.any(r => r.has(app,key)) -- 角色权限点

&#x20;       || member has allPermissions flag)
```



* 租户超管（tenant\_admin）：全量，不受角色限制。

* 门店管理员（store\_admin）：登录后进入**门店端工作台**（只看到自己门店数据），P1 实现。

* 普通成员：仅被分配的菜单。

### 5.3 前端菜单过滤



* 现有 `menuPermissions`（web-admin 权限矩阵）扩展：登录后取 `/api/customer/members/me` → `{ roles, perms }`，前端按 `perms` 过滤侧边栏 / 路由；超管全量。

* 后端 `requirePerm(app, key)` 中间件（新建）：`requireAuth` 之后校验有效权限，替代 / 补充现有 `requireRole`。

## 六、门店负责人融合（方案 A 落地）

### 6.1 创建门店时的负责人逻辑（StoreManage 三步弹窗改造）



| 项      | 设计                                                                                                                                                                    |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 负责人来源  | 二选一：**新建负责人账号**（默认）/ **选择已有成员**                                                                                                                                       |
| 新建账号   | 用负责人手机号 + 密码 → 创建 `accounts`（哈希）→ 创建 `tenant_members`（name = 负责人姓名，identities=\["backend\_admin"]）→ 绑定 `store_admin` 角色 + `member_roles` → `store.owner_member_id` 关联 |
| 选择已有成员 | 从本租户 `tenant_members` 下拉选，直接绑定 store\_admin 角色（如无则提示先建）                                                                                                               |
| 密码安全   | 创建 / 编辑弹窗不再存明文；密码只写入 accounts，重置走「重置密码」操作                                                                                                                             |
| 存量门店   | 迁移脚本：owner\_account 按手机号建账号，密码重置为随机并提示超管重置                                                                                                                            |

### 6.2 门店负责人登录后



* 登录 → `accounts` 校验 → 找到 tenant\_members + store\_admin 角色 → 签发 token（含 memberId/storeId）

* 前端：登录后检测 `store_admin` → 进入**门店端工作台**（P1：门店订单 / 库存 / 提现 / 业绩，对齐 nshop 门店端）

* P0 期：store\_admin 登录后暂时进入客户后台（仅可见 store 应用菜单），门店端工作台 P1 单独排期

### 6.3 成员管理联动



* 成员管理列表增加「门店负责人」列（该成员是否绑定某门店）

* 禁用成员 → 对应门店负责人同时失效（门店标记负责人失效，不可用该账号登录）

* 移除门店负责人 → 保留成员账号，仅解除 store\_admin 角色与 store 关联

## 九、存量迁移策略



| 数据                                  | 迁移动作                                             | 风险              |
| ----------------------------------- | ------------------------------------------------ | --------------- |
| users(tenant\_admin/tenant\_member) | → accounts + tenant\_members + 内置角色              | 无（保留原密码哈希，登录不断） |
| users(admin/operator)               | 保留原表不动（平台账号）                                     | 无               |
| store.owner\_account                | 匹配账号 / 建账号 + store\_admin 角色 + owner\_member\_id | 存量门店密码需重置（提示超管） |

## 十一、后期扩展方向（适合系统升级的设计）



1. **多租户账号复用**：accounts 全局唯一 + tenant\_members 挂多租户 → SaaS 多店铺 / 多商户同一手机号登录天然支持。
