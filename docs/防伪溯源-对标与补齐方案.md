## 3. 分批方案（建议三批 + 一个前置）

### 前置（阻塞项，需你先定）
按上面"甲/乙/丙"三选定对标依据。**不定这一项，UI 级 1:1 无从谈起**；但丙不阻塞 P0。

### P0 —— 把"后端已有"铺到前台（建议先做：风险最低、收益最大）
**范围**：A 类 7 项 + C1 + C2 + C3（即 A1-A7、奖品配置、API 白名单、商城类型）。
**为什么先做这批**：这些都是"**后端已经能跑、只差一层 UI**"，不碰算法、不改数据结构、不引新依赖 → 风险最低。做完这批，你眼里"该有的功能"基本就出现了。
| # | 改什么 | 落点 |
|---|---|---|
| P0-1 | 后台页面从 3 个 Tab 扩到 **6 个**：批次管理 / 防伪码记录 / **数据统计** / **查询与异常记录** / **奖品与对接配置** / 系统设置 | `web-admin/.../apps/trace/index.vue`（把"设置"Tab 拆开） |
| P0-2 | **奖品/红包配置编辑器**（C1，本批最要命的一项）：活动开关、是否要手机号、是否要短信码、金额、概率、发完文案 | 同上，批次弹窗内新增"奖励配置"分区 + 或独立 Tab |
| P0-3 | **第三方 API 对接配置**（C2）：IP 白名单、apiKey 生成与回显（**必须脱敏**，按记忆 §10：租户自己的密钥走 encryptSecret + maskSecretValue） | 同上 |

### P1 —— 契约里真需要的（按需，做完 P0 再评）
| # | 改什么 | 说明 |
|---|---|---|
| P1-1 | 批次码段规则 `GET/POST /batch-rules` | 表已建、只差路由 + UI；**代理码段/溯源补充是真实业务**（多级经销），建议做 |
| P1-2 | zip 导出 | 引 `fflate` 依赖（Node 22 自带 `node:zlib`，也可不引依赖）；**先确认有没有人真的要 zip**（txt/html 已能导出） |
| P1-3 | 签名算法 md5 → `HMAC-SHA256` | 契约明确建议；🔴 **改签名 = 破坏性变更**：所有已对接的第三方调用方必须同步改 → **先确认有没有在跑的调用方**，没有可以先不动（留 md5 也非漏洞，它有 IP 白名单 + 32 位 key 双因子） |

### P2 —— 建议**先决策、不现在做**（这两个不是"缺口"，是要不要的增量）
| # | 项 | 为什么建议先别做 |
|---|---|---|
| P2-1 | 微信消息适配（B2-B4） | 需要公众号/模板消息链路 + 消息队列异步；**没有真实运营场景就做 = 空头能力**（记忆 §5 判据：后台有表单、C 端有入口、服务端零消费点 → 空头）。**先答：我们的租户有公众号吗？有没有人在扫码后要收通知？** |
| P2-2 | 对外开放 API（B5） | 这是**对外系统契约**，要有授权体系 + 限流 + 版本兼容；**先答：有没有真实的外部调用方？** |
