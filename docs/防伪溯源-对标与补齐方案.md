## 3.5 源码解密后新增（`plugin/*.dec.php` 精读，取代 §1 的"未读"边界一部）

### 🔴 算法逐位核对结果：**我们的算法与对标站 1:1 一致**（好消息，且它修正了我的差距定性）
`1asdaredg.dec.php` = 原 `Fw_SuanFa_V2_dada` 生成算法。与我们 `server/src/services/traceCode.js` 逐项对齐：| 项 | 对标站 | 我们 | 判定 |
|---|---|---|---|
| 权重表 WI（22） | `[7,19,...,17]` | 同 | ✓ |
| 权重表 WU（22） | `[5,7,...,5]` | 同 | ✓ |
| 常量 ZM | `38742938235627364287` | 同 | ✓ |
| pi / pu | `k1.k3` / `k2.k4` | 同 | ✓ |
| 清洗 6 字符 | 空格/./,/-/－/全角空格 | 同 | ✓ |
| 取流水号 | `substr(a, strlen(m1), m5-m4-strlen(m1))` | 同 | ✓ |
| 拼 b | `substr(a.k5.ZM,0,20)` | 同 | ✓ |
| 循环 | `k=(b[i]+pi[i])*pu[i]*337; t+=(k+wi[i])*wu[i]` | 同 | ✓ |
| m4=4/5/6/7 四分支 | `fmod(t,887)` / `8893` / `t*t,78487` / `938351` | 同（4/5 用 t、6/7 用 t*t） | ✓ |

**结论：已生成的防伪码是对的 → 算法这块不是缺口、不用返工。**（浮点也安全：t 最大 ~1.3e8、t*t ~1.7e16，远小于 double 的 2^53；PHP `fmod` 与 JS `%` 同精度。）

### 一处我们有理由的**刻意偏离**（1:1 反而会引入漏洞）
对标站**默认码制的 k1..k5 是空串**（`module.php:37` 序列化默认实证）。我们填了真默认值（`DEFAULT_CODESET`：k1='0123456789' 等）。原因（我们代码注释 lines 11-16 已写明）：空码表 → `digitAt` 返 0 → 校验位变成**与码内容无关的常量** → 攻击者拿任一真码、改流水号与批次号、保留原校验位即通过 → **防伪形同虚设**。→ **建议：这个偏离保留，不"对齐"回去。**

## 9. 出码链路事实核验（2026-10-29，逐行读一手 PHP 源码后的更正）

> 起因：有人说「对标系统的真实逻辑是 创建批次 → 批量生成 SN 入库 → 循环调 `/cgi-bin/qrcode/create` 拿 ticket → 拼扫码短链/二维码图片；只要有一次返回 48001 就弹窗『访问公众平台接口失败，api 功能未授权』」。
> **核查结论：该描述与对标系统一手源码不符**，三条都不成立。下表是可复核的源码证据。

### 9.1 三条描述逐条核对

| 描述 | 源码实证 | 判定 |
|---|---|---|
| 循环调用 `/cgi-bin/qrcode/create` 拿 ticket | 全目录 `grep -rn "qrcode/create" --include="*.php"` → **命中 0 次**。对标实际用的是 `barCodeCreateDisposable`（扫普通条码·**临时码**，`expire_seconds=1800`、`scene_id` 自增），全目录**仅 1 处**调用：`site.php:51-76` | ❌ **不成立** |
| 「有任一次返回 48001 → 弹窗 api 功能未授权」 | 全目录 `grep -rnE "48001\|api unauthorized\|功能未授权"` → **命中 0 次**。对标在无权限时是**静默降级**：`queryBarCodeActions()` 先探测，无权限直接跳过该分支，不报错 | ❌ **不成立** |
| 「生成一批 SN 码**入库**」 | `pdo_insert` 全量调用只有两类表：`zmcn_fw_batch`（批次元信息）、`zmcn_fw_history`（操作日志）。**SN 本身不入库**，只在内存循环里生成并写进导出的 txt/html，计数用 `UPDATE ... SET num = num + N` | ❌ **不成立**（但方向上**与我方一致**） |

### 9.2 对标系统实际的两条码链路

```
链路 A：印在产品上的码（批量）
  创建批次 → 扣库存(cocom) → 内存循环生成 SN(算校验位) → 累加 num → 导出 txt/html
  html 里的二维码 = 本地 PHP 渲染的普通二维码：
    <img src='./index.php?c=platform&a=url2qr&do=qr&url=...' />   ← 不碰微信、不出 ticket
  码内容 = f.php?co=<SN>&i=<uniacid>   或   http://p.url.cn/<fwqrsn>/<SN>

链路 B：消费者扫码落地页（按需，每次扫码生成一张临时码）
  消费者扫码 → 落地页发现未关注 → queryBarCodeActions() 探权限
    → 有权限：barCodeCreateDisposable(scene_id 自增, 1800s) → 存 qrcode 表 → showqrcode?ticket=...
       （用途：引导用户关注公众号，把溯源结果用图文消息推给用户）
    → 无权限：静默跳过，用普通二维码兜底
```

**关键区分**：对标系统里「微信出码」和「印在产品上的码」是**两件不同的事**——
微信出码只服务于**关注引导**（临时码，30 分钟失效），产品上的码是**本地渲染的普通二维码**。
把它理解成「批量一物一码 = 批量调微信出码」是把两条链路混成了一条。

### 9.3 与我方现状的对照

| 维度 | 对标系统 | 我方现状 | 是否需改 |
|---|---|---|---|
| SN 是否入库 | 否 | 否（只在消费者首次扫码查询时落 `trace_codes`） | ✅ 已一致 |
| 批次数计数 | `UPDATE num = num + N` | 同 | ✅ 一致 |
| 产品上的二维码怎么来 | 本地 PHP 端点 `url2qr` 渲染（**微擎框架自带**，部署即有 → 对标自己导出是正常图） | 同为本地渲染，但改用 `qrcode` 库生成 **SVG data URI 内联** | ✅ 同构且更稳（见 §9.6） |
| 微信带参码 | 仅落地页按需生成**临时码**（引导关注） | `POST /codes/:id/mp-qr` 按需单码，走真 `qrcode/create`（永久码） | ⚠️ 我方是不同定位 |
| 批量出码 + ticket 缓存 | **没有** | **没有** | 若做=**新增能力**，不是「对齐对标」 |
| 48001 提示 | 无 | 已补：中文提示 + `GET /trace/mp-qr/capability` 能力预检 + 后台状态标签 | ✅ 我方更完备 |

### 9.4 由此产生的取舍

「一物一码 + 批量微信带参二维码」是**对标系统没有、我们要新增**的能力。三条硬约束：
1. **微信侧配额**：`qrcode/create` 有每日调用上限，批量出码必然要**分批 + 断点续跑 + ticket 持久化**，不能循环一把梭。
2. **失败语义要改**：对标式「一次 48001 整批中止」在批量场景下体验极差（已出码的不算、没出码的算谁的？）。我方应按**单码失败跳过 + 整批汇总报告 + 可重试**来做。
3. **SN 入库是重构**：要做「码 → ticket」映射就必须把 SN 入库，这会推翻当前「SN 不入库、扫码才落库」的口径（那个口径是**防伪**属性的一部分：未被扫过的码不存在于任何台账，泄露面更小）。

> ⚠️ **待你拍板**：是否要做「批量一物一码 + 微信带参码」。做 = 接受 SN 入库 + 引入 ticket 持久化表 + 分批重试机制；
> 不做 = 维持现状（本地二维码印码 + 按需单码出带参码），**P0/P1/P2 已落地的部分不受影响**。

2. **激活粒度差异（真实但影响有限）**：对标判据是「该批次下有没有 type=9 的**绑定行**」，
   绑定行带 `code` 字段且用 `instr(:c2, code)` 模糊匹配 → 语义上支持「同批次只激活某几串码」。
   我们是「批次级」（`UNIQUE(tenant_id, batch_id)`）。
   → 对标更细，但**依赖外部模块才能产生这种行**；在「只有防伪插件」的前提下对标其实**只能整批放行**。
   我方批次级在**同等条件下能力不低于对标**，且不依赖外部模块。
3. **导出缺 ZIP**：对标导出 `application/zip`（内含 txt），我方只给单个 txt/HTML → 大批量场景体验更差。
   → ✅ **本轮已补**：新增 `server/src/services/zip.js`（**零新依赖**，用 `node:zlib` 的 `crc32` 手写
   store 模式 ZIP；不引 archiver/jszip 是为了不给部署面加风险）。
   ① `GET /batches/:id/export?format=zip` → 真实 `application/zip` 文件下载；
   ② `POST /batches/:id/generate-codes` 带 `format=zip` → base64 + `encoding:'base64'`（JSON 传二进制的唯一正道）；
   ③ 后台生成弹窗新增「打包格式」单选（原始文件 / ZIP 压缩包）。
   **已用系统 `unzip -t` + macOS `ditto` 实测可解压、内容字节级一致**（不是只跑单测）。
   ⚠️ 踩过的坑：ZIP local header 里**漏拼 `data` 本体** → 文件里没有数据、unzip 报 "bad CRC"（CRC 值本身是对的，
   容易误判成 CRC 算法错）；supertest 读二进制响应**必须 `.buffer(true)` + 自定义 parse**，否则 `res.body` 被按 utf8 破坏。
4. **单批上限**：对标 100，我方 10000 —— 我方是有意放宽，但**未在 UI 说明「分批生成会跨号段」**。
   → ✅ **本轮已补**：生成弹窗加提示「分多次生成会连续占用本批次的流水号段（不会重号）」。

#### E. 结论

- **生码 / 出码 / 入库 三条主干，与对标同构**（含「SN 不入库」「扫码才落库」这两个最容易被误判的关键点）。
- 我方**多出**的：P0 印刷锁定、P1 试印分区（对标没有）、48001 中文提示 + 能力预检、SVG 内联（不依赖任何服务端端点）、
  **激活链路自闭环**（对标只能开闸不能写激活记录）。
- 我方**少于**对标的：① 导出 ZIP（**本轮已补**）；② 码级激活绑定（对标可细到单串码，但依赖外部模块才有数据）。
- **我方刻意不同的**：单批上限 10000 vs 100；带参码定位（给码出码 vs 引导关注）。

#### 9.6.3 印刷场景仍需注意的两点（不是 bug，是交付说明）

1. **URL 必须是绝对地址**：防伪码印在包装上给消费者扫，相对路径被手机相机扫出来打不开。
   → 我方 `traceQueryUrl` 已强制绝对地址（`settings.siteroot` 优先，否则用请求头 origin）。
   ⚠️ **运营前置条件**：租户必须配 `siteroot` 或平台配 `siteRoot`，否则会退化成相对路径 `/card/#/...` → 扫出来打不开。
   **这应当印在码包页面上给运营看**（本轮未做，见 §9.6.4）。
2. **hash 路由的兼容边界**：`/card/#/pages/trace/index?co=...` 依赖 hash 模式。
   主流扫码 App（微信/支付宝/相机）都能正确处理 `#` 后的参数；但**个别第三方扫码工具或老旧 RIP 软件**
   可能只取 `#` 之前的部分 → 落到溯源页但**丢失 `co` 参数**。
   → 缓解已在做：码面下方印明文码，用户可手输；后续可考虑把参数从 hash query 改为**服务端短码跳转**
   （`/card/trace?co=xxx` → 302 到 hash 页），彻底绕开 hash 兼容问题（**未做，待排期**）。

#### 9.6.4 待补（低成本，建议做）

理由：URL 配错是**印完才发现**的典型事故（印 10 万个码，扫出来打不开 → 全废），
而码包是运营自己下载的 → 在码包里提示，是成本最低的拦截点。

并注明「二维码下方同时印有防伪明文码，二维码磨损或反光时可手动输入查询」；
取不到绝对地址（未配 `siteRoot`/`siteroot`）时显示 ⚠️ 警示而非给相对路径。
`scanBaseOf()` **复用 `traceQueryUrl` 的基址判定**（另写一套拼法会让「提示地址 ≠ 二维码实际地址」→ 提示反而骗人）。

## 11. 生成评估：数量上限 / 速度 / 安全性（2026-10-29 实测）

用户三问：① 生成码数量会不会受限；② 生成速度会不会受影响；③ 安全性对标哪些可吸收、哪些必须修正。
已全部落到代码实证 + 真实跑分（Node v22，Mac 本地，`qrcode` 依赖正常解析，无生产缺口）。

### 11.1 数量上限——会受限，但全是分层的合理上限

| 层 | 上限 | 代码位置 | 性质 |
|---|---|---|---|
| 单次请求·正式单码 | **10,000** | traceGenerate.js:289 | 软（设计封顶） |
| 单次请求·试印单码 | 1,000 | :289 + `DEMO_SERIAL_RESERVED` | 软 |
| 单次请求·套标 | **100 套** | :357 | 软 |
| 批次试印累计 | 1,000 | :299 | 软 |
| 单批次流水号空间 | **10^m3 − 1000**（默认 m3=6 → ≈999,000） | traceCode.js `demoSerialBase` | **硬（结构）** |
| 租户批次空间 | 10^m2（默认 7 → 10^7 批） | m2 | 硬（结构） |
| 租户库存 cocom | −888=不限，否则数值 | `deductCocom` | 业务 |
| 平台生成闸门 | open / platformOnly / closed | genMode | 业务 |

**结论**：数量确实受限，但都是合理分层。
- 最影响"大批量"的两道：① 单次 **1 万封顶**——做 10 万要发 10 次请求（有意为之，防单请求占满）；② 单批次流水号空间默认约 **100 万/批**（顶部的 1000 被试印预留段永久占掉）。
- 若业务需要单批上千万：把 m3 调到 8 → 10^8−1000 ≈ 1 亿/批；调到 9 → 约 10 亿/批。m2/m3/m4/m5 都在后台码制里可调，无需改代码。
- 对标单批只封 **100**（太紧，大批量要分上百次）；我方 10000 是有意放宽（已在生成弹窗提示"分多次会连续占号段、不重号"）。

### 11.2 速度——txt 路径几乎无感，HTML-QR 路径是真实瓶颈

实测（mock DB，shuffle 开启=真实默认；HTML-QR 用 `qrcode` 库生成内联 SVG）：

| 路径 | 1 万码耗时 | 10 万码耗时 | 10 万码输出体积 |
|---|---|---|---|
| 纯算号（理论下限） | — | 219 ms | 0 |
| 正式 txt（codetype 6） | 40 ms | **380 ms** | **2 MB** |
| 试印 txt | 4 ms / 1k | — | — |
| **HTML-QR（codetype 4，最重）** | **6,914 ms** | **67,640 ms** | **1,229 MB** |

**结论**：
- **txt / 数据路径**：完全不受影响。10 万码 < 0.4 秒、2 MB，放心用。
- **HTML-QR（给印刷厂的二维码图）确实受影响**，且是唯一的真实瓶颈：
  1. 单次封顶 1 万就要 **6.9 秒**，做到 10 万 = **67.6 秒单请求**（有 HTTP 超时/连接中断风险）；
  2. 输出是**单个巨型 HTML**——10 万码 = **1.2 GB**，浏览器和排版软件基本打不开、传不了。
  - 根因：每个码一张内联 SVG（base64），100 个码 ≈ 126 MB，且全部塞进一个 HTML 文件。
- 套标单次 100 套封顶；**注意**：套标要求批次配 `bbox/sbox`（套/子数量），否则当前逻辑会**静默生成 0 码**（已识别为小坑，生成前应校验批次是否具备套标维度）。

**对"速度会不会受影响"的回答**：取决于用哪种导出。给数据/URL 用 txt 极快；要二维码图用 HTML-QR 大批量会慢且产出不可用的巨型文件——这是我们要修的点（见 11.4）。

### 11.3 安全性——对标可吸收的 vs 必须修正的

**可吸收（对标做得对的，我们已对齐）：**
1. **k1~k5 校验位算法**——逐位数值运算 + 模 8893（质数，满周期），与对标 `Fw_SuanFa_V2` 逐项同构，浮点安全（t 最大 ~1.3e8，远小于 2^53）。✓
2. **库存 cocom 扣减 + −888 无限**——归一截断口径一致。✓
3. **SN 不入库**——仅内存生成 + 累加 `num`，消费者首扫才写 `trace_codes`（与对标 `zmcn_fw_batch` + `zmcn_fw_history` 一致）。✓
4. **48001 接口未授权**——中文提示 + 能力预检，比对标纯弹窗更优。✓

**必须修正（对标做得不好的，我们已修）：**
1. **印刷后码制锁定**：对标仅"人工约定不可改 K1~K5"；我们强制 `locked_at`（k1~k4 密钥 + m1~m5 结构全锁，zdl/publishNo 仍可改）。✅ 已完成
2. **试印/演示分区**：对标无；我们加顶部号段隔离 + 不扣库存 + 不锁码制 + 红条标注 + 扫码 `is_demo` 打标 + 统计排除。✅ 已完成
3. **激活闸门（先印后绑）**：对标无；我们加 P2（三条扫码路径全接 + 经销商自助激活 + 口令密文 + 失败限流）。✅ 已完成
4. **二维码出码**：对标依赖 PHP `url2qr` 端点（导出依赖服务端、易裂图）；我们改本地 `qrcode` 库内联 SVG（自包含、离线可印、已 jsQR 实测解码通过）。✅ 已完成
5. **每租户密钥**：对标可能共用/手填；我们用 `crypto.randomInt` 每租户独立随机 k，并禁止空码表（空码表 = 校验位退化为常量，等于无防伪）。✅ 已完成
6. **枚举/爆破防护**：我们加 `zdl` 错误次数上限（超 → 429）+ 激活 PIN 单 IP >20 限流 + mp-qr 签名校验（`ke!==sign` 拦截）。对标缺失或弱。✅ 已完成
